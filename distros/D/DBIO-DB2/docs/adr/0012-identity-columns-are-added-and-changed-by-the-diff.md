# ADR 0012 — Identity columns are added and changed by the diff; what Db2 refuses, the diff refuses

- Status: accepted
- Date: 2026-10-25
- Tags: diff, ddl, identity

Implemented with karr k45 (point 3). Decided by the maintainer: build what the server
takes, refuse the rest loudly.

## Context

`Diff::Column` could not do anything with an identity column on an existing table.
`ADD COLUMN` wrote the column without the identity clause (and Db2 refused it,
SQL0193N), and a difference in `is_auto_increment` between two existing columns was not
seen: `DBIO::Diff::Compare::changed_column_fields` does not compare it, so `upgrade`
left the table as it was and the follow-up diff stayed empty only because nothing
looked.

Measured live (Db2 12.1.5, `DBD::DB2` 1.92, `t/71`; a table with a primary key, empty
and with two rows alike unless said). `pending` is
`SYSIBMADM.ADMINTABINFO.REORG_PENDING`:

| Statement | Result |
|---|---|
| `ADD COLUMN n INTEGER NOT NULL GENERATED ALWAYS AS IDENTITY` (with or without `(START WITH 1, INCREMENT BY 1)`) | SQL0104N |
| `ADD COLUMN n INTEGER NOT NULL` | SQL0193N |
| `ADD COLUMN n INTEGER NOT NULL DEFAULT 0` | ok, pending N, rows hold 0 |
| `ALTER COLUMN n SET GENERATED ALWAYS AS IDENTITY` while the column has a default (`DEFAULT 0`, `DEFAULT 7`) | SQL0190N |
| ... after `ALTER COLUMN n DROP DEFAULT` | ok, pending N; existing rows keep their value (0), the next insert gets 1 |
| `SET GENERATED` on `INTEGER`, `SMALLINT`, `BIGINT`, `DECIMAL(10,0)`, all `NOT NULL` | ok, pending N |
| ... on `DECIMAL(10,2)`, `VARCHAR(10)`, `DOUBLE` | SQL0846N |
| ... on a nullable `INTEGER` | SQL0270N |
| ... on a nullable column after `SET NOT NULL` | ok, also while the table is reorg-pending; the next `INSERT` waits for the `REORG` (SQL0668N) |
| ... on a column that is an identity already | SQL0190N |
| ... on a second column of a table that has an identity | SQL0372N; after `DROP IDENTITY` of the first, ok |
| `ALTER COLUMN n DROP IDENTITY` | ok, pending N, the column stays `NOT NULL`, takes explicit values; on a column that is none: SQL0190N |
| `SET DATA TYPE BIGINT` on an identity column | SQL0270N |
| `DROP COLUMN` of an identity column | ok, pending Y (ADR 0008) |
| an existing row of value 5 beside a column made identity | the next insert gets 1 -- the counter starts at 1, not above the column |

## Decision

1. **An added identity column is three statements**: `ADD COLUMN ... NOT NULL DEFAULT
   0`, `ALTER COLUMN ... DROP DEFAULT`, `ALTER COLUMN ... SET GENERATED ALWAYS AS
   IDENTITY`. Existing rows hold 0.
2. **`Diff::Column` compares `is_auto_increment` itself** (truthiness; undef is 0). A
   change is `SET GENERATED ALWAYS AS IDENTITY` or `DROP IDENTITY` (no attributes: the
   model carries no `START` or `INCREMENT`, the default is the 1 and 1 `install_ddl`
   writes). In an `alter`, `DROP IDENTITY` is the first statement; `SET GENERATED` is
   the last, after the `SET NOT NULL` and the `DROP DEFAULT` the column needs (the
   target identity column has no default).
3. **What lets go of an identity goes first within a table**, a `DROP IDENTITY` or a
   `DROP COLUMN` of an identity column, ahead of the other column operations: one
   identity column per table.
4. **Refusals, at the time the operations are built**, with `croak` naming table and
   column: an identity over a type other than `SMALLINT`, `INTEGER`, `BIGINT`,
   `DECIMAL`/`NUMERIC` without scale; over a column that is not `NOT NULL`; a change of
   type of a column that is an identity on both sides. A change of type together with
   `DROP IDENTITY` is not refused (the type changes after the identity is gone).
5. **`reorg_recommended` is unchanged for the new statements**: `SET GENERATED`, `DROP
   IDENTITY` and the three statements of an added column leave the table usable (the
   table above), so they ask for none. A `SET NOT NULL` or type change travelling with
   them asks as before; unknown combinations still answer yes.

## Consequences

- Rows that exist when an identity column is added hold 0, and the counter of a column
  made identity starts at 1: if the column is also unique or the primary key, or holds
  values at or above 1, the inserts that follow can collide. Not handled; a maintainer
  call whether `RESTART WITH` above the maximum should be part of it.
- A column that is an identity before and after and changes its type cannot be
  altered by the diff; changing it by hand (drop the identity, change, set it again)
  restarts the counter.
- `START WITH` / `INCREMENT BY` / `BY DEFAULT` are not in the model: a column that is
  `GENERATED BY DEFAULT` is an identity like any other and is not touched.
- Tests: `t/70-diff-identity.t` (offline, catalog-shaped models), `t/71-identity-live.t`.

## Addendum 2026-10-25 — an identity column is not added to a table that holds rows (karr k54)

Hub decision of karr k54, on the first Consequence above (rows that exist hold 0): the
diff no longer leaves that to the maintainer. An identity column added to a table with
rows is **refused**; on an empty table it is added as described.

- The diff knows no rows, so `DBIO::DB2::Deploy` checks. `apply` (and with it `upgrade`)
  asks, once the diff is built and before its first statement, for each table that gets an
  added identity column (`Diff::Column::adds_identity`; the table is in both models)
  `SELECT 1 FROM "table" FETCH FIRST 1 ROW ONLY`. A row, and it croaks naming table and
  column, having executed nothing. `diff`, `as_sql` and `summary` stay reads and do not
  look.
- A changed `is_auto_increment` on an existing column (`SET GENERATED`) is not part of it:
  the rows keep their values there, only the counter question of the Consequences remains.
- A reorg-pending table cannot be read (SQL0668N reason code 7, found when `t/71` failed
  under the first version of this check). `upgrade` therefore makes the check after the
  `REORG` of pending tables (ADR 0008 addendum), which changes neither schema nor rows; a
  bare `apply` of such a diff onto a pending table fails with the server's SQL0668N.
- Tests: `t/76-identity-add-rows.t` (offline, recording handle), `t/77-identity-add-rows-live.t`;
  `t/71-identity-live.t` adds its column to an empty table now.

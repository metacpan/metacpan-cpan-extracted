=head1 NAME

textblocks - additional text widget subcommand for Tk distribution.

=head1 SYNOPSIS

  .widgetName block subcommand ?opt opt ...?
  .widgetName mark data markName ?value?
  .widgetName tag data tagName index ?value?
  .widgetName configure -getFlags integer

=head2 What else is in the widget?

The other difference with the stock Text widget is the object oriented
dump. It dumps a list of objects which represent the contents of the
widget in the given range. The temporary position for this command is

   .widget block list ?-values? from to

An object is a real object in Perl, and a list with a first element
being the I<class id> in TCL (the rest being the contests, in what
follows the first element of the rest is referenced as the first
element of the object).

The particular elements of the list represent:

=over 7

=item String

An object with contents being the string. Object class is
C<Tk::Text::String>, I<class id> is C<S>.

=item Marks

The contents is the name of the mark, the classes are
C<Tk::Text::MarkLeft> with I<id> C<L>, and C<Tk::Text::MarkRight> with
I<id> C<R>.  A mark that has a value (see L<Values>) is listed as a
list of the name and a copy of the value, C<[name, value]>, instead of
a reference to the name, as for tags.  When a list is inserted back
(the undo does this with its own lists), a mark element of this form
gives the mark that value (the value the mark had is freed when the
widget command returns); a reference to a name leaves the value of an
existing mark as it is.  The marks C<insert> and C<current> are not
set from a list, nor are their values.

=item Tags

The contents is the name of the tag, the classes are
C<Tk::Text::TagOn> with I<id> C<T>, and C<Tk::Text::TagOff> with
I<id> C<t>.  The start of a run of a tag that has a value (see
L<Values>) is a C<Tk::Text::TagOn> holding a list of the name and a
copy of the value, C<[name, value]>, instead of a reference to the
name; code that reads the name should accept both forms:

  my $name = UNIVERSAL::isa($elt, 'ARRAY') ? $elt->[0] : $$elt;

A run that is already on where the range starts has its
C<Tk::Text::TagOn> before the range, so the list mentions it only by
the C<Tk::Text::TagOff> at its end, or not at all.  With C<-values>
the list starts with a C<Tk::Text::TagOn> for each such run (with a
copy of the value if the run has one, the tag C<sel> excepted), so
that the list alone says which tags its text has.

=item Window

The contents is a list of the name of the window and the script to
create the window, followed by the options of the window as
option/value pairs: C<-window> (the path name, if the window exists),
C<-create> (if there is a script), C<-align>, C<-padx>, C<-pady> and
C<-stretch>; the class is C<Tk::Text::EmbWin> with I<id> C<W>.  Undo
re-creates the window segment from the options.

=item Image

The contents is a list of the name of the image in the widget,
followed by its options as option/value pairs: C<-image> (if it has
one), C<-align>, C<-padx> and C<-pady>; the class is
C<Tk::Text::EmbImage> with I<id> C<I>.  Undo re-creates the image
from the name and the options.

=item block

A block is dumped as a list of 

=over 10

=item type

The first element is a list of I<block name>, I<depth> and (optionally)
I<instance data> and I<node values>.  The node values are there when
a node of the block has a value (see L<Values>) and the whole block is
in the listed range; the third element is then C<undef> if the block
has no instance data.  They are written as the tree: a node as a list
of its value followed by its children, a leaf as a list of its value,
with C<undef> for a node without a value.  For a fraction with value
C<R> on the root and C<N> on the numerator the first element is

  ['Fraction', 0, undef, ['R', ['N'], [undef]]]

=item contents

The rest of the list represents the contents of the block in the same
form as the top-level dump, with exception for inter-leaf separators.

The inter-leaf separators are dumped as an object of class
C<Tk::Text::BlockSeparator>, with I<id> C<|>, the contents being the
"depth" of the separator: the level of the lowest node that holds the
leaves on both sides of it, counted up from the nodes directly above
the leaves.  The minimal possible depth is 0, for separators between
leaves of the same parent; in a tree whose leaves are equally deep, 1
is a separator between leaves whose parents are siblings, and so on.
The I<depth> in the first element is that of the root on the same
scale (0 for a fraction C<{num|den}>).

In a tree whose leaves are at different depths (a "ragged" tree, see
L<Ragged trees>) the depths are those of a uniform tree that the
widget keeps: every leaf is as deep as the deepest one, a shallower
leaf hanging from its parent through I<padding> nodes, which are not
nodes of the tree (no command names them).  The header's depth and
the depths of the separators count these too.  The separator before
a leaf with padding is a pair instead of a number: a reference to an
array (blessed into the same class, Perl only) of the depth and the
number of padding nodes directly above the leaf (its I<defect>).  A
first leaf with padding, which has no separator before it, gets the
pair C<[undef, defect]> in front of it.  Separators before leaves
without padding stay numbers, so the list of a tree whose leaves are
equally deep is as before.  With C<{x|2|3}> on line 2, the C<2|3> made
the leaves of a node S (C<R( x | S( 2 | 3 ) )>):

  [['F', 1], [undef, 1], 'x', 1, '2', 0, '3']   # R( x | S( 2 | 3 ) )
  [['F', 1], '2', 0, '3', [1, 1], 'x']          # R( S( 2 | 3 ) | x )

(the separators shown as their contents).  A program reads both
forms with

  my ($d, $defect) = UNIVERSAL::isa($sep, 'ARRAY') ? @$sep : ($$sep, 0);

At a separator of depth I<s>, both leaves next to it have defects of
at most I<s>.  A block that is a single leaf (see C<block flatten>)
has the depth -1, and no pair: C<[['F', -1], 'numden']>.

With C<-values>, a separator of a block that is not listed whole (the
range is inside the block, or cuts it) carries the values of what
I<begins> after it: it is a reference to an array (of the same class)
of its depth, the defect of the leaf after it (0 where the leaves are
equally deep), a copy of the value of that leaf, and copies of the
values of the nodes that begin with that leaf, from the lowest up: as
many as the depth says, less the defect.  C<undef> stands for a node
without a value.  In a table C<{a|b||c|d}> (rows of cells) with the
values C<B>, C<C>, C<D> on the cells and C<ROW2> on the second row,
the range from C<b> to C<c> is listed as

  'b', [1, 0, 'C', 'ROW2'], 'c'

and that of C<|b> as C<[0, 0, 'B'], 'b'>.  The code above that reads
the depth and the defect reads these too.  A block listed whole has
all its values in its header, as without C<-values>, and its
separators stay as they are.  The root, the first leaf and the nodes
that begin with the first leaf begin with the block: no separator
carries their values.  See L<Cut and paste with structure>.

=back

The object class in Perl is C<Tk::Text::Block>, the I<class id> is
C<B>.

=item Empty

An empty block is dumped in the same way with the object class being
C<Tk::Text::Empty>, the I<class id> being C<E>. The contenst is the
list of the block name, and (optionally) I<instance data>.

=back

=head2 What is a block?

A Block is an additional editable unit of information for inclusion
into widget. Block consists of I<block type>, I<block contents>, and,
possibly, I<block instance data>. I<Block contents> is a tree whose
leaves can contain anything that can be in a row in a text widget
(including other blocks). I<Block instance data> can be arbitrary data
as in a language variable.

The leaves of the tree may be at different distances from the root (a
"ragged" tree, since 2.06, see L<Ragged trees>).

=head2 Ragged trees

Until 2.05 every leaf of a block was at the same distance from the
root.  Since 2.06 the leaves may be at different depths: C<block
sprout> gives a part of a leaf (or a whole leaf) a node of its own,
C<block flatten> makes a node one leaf again, and the editing commands
keep the depths.  For example C<R( x | S( 2 | 3 ) )>, a root R whose
children are a leaf C<x> and a node S with the leaves C<2> and C<3>
(this notation is used below: C<|> separates siblings).

=over 5

=item *

I<Levels.>  The commands that name nodes count the I<real> ancestors
of a leaf: C<block nodedata index level> (and C<block flatten>) take
the leaf the index names as level 0, its parent as 1, and so on, and
a negative level counts down from the root (-1 the root, -2 its child
on the way to the leaf).  So the number of levels depends on the leaf:
in the example, C<x> has one level above it, C<2> has two.  C<block
at> and C<block of> give the structure of the real tree (a list of
lists, with a number for each leaf: C<[1, [1, 1]]> above), and so do
the arguments of the layout callback.  The places of node values
(L<Values>, L<Telling the program: -valuecommand>) are given the same
way: where the node's first leaf starts, and the node's level counted
from that leaf.

=item *

I<Padding.>  Internally the widget keeps the tree uniform: a leaf
shallower than the deepest one hangs from its parent through
I<padding> nodes, which are not nodes of the tree: no command names
them and they hold no values.  The user sees them in two places only:
in C<block list>, whose depths are those of the uniform tree (the
separator before a leaf with padding is a pair of the depth and the
number of padding nodes above the leaf, its I<defect>, see L<What else
is in the widget?>), and in the levels of C<block split>, which are
those of the uniform tree (in a leaf with padding, the lowest levels
cut only padding, see C<block split>).  The same real tree can have
several lists (consecutive leaves of the same parent may share their
padding or not); the undo gives back the padding exactly.

=item *

I<Editing.>  A newline typed in a leaf, or C<block split> at level 0,
makes a sibling of the leaf, at its depth.  A deletion that joins two
leaves of different depths first gives the shallower one nodes of its
own, one above the other, until both are equally deep, and then joins
them as in a tree whose leaves are equally deep (see L<Deletion of
text in blocks>): deleting from inside C<a> to inside C<y> in
C<C( a | B( y | z ) )> gives C<C( W( ay | z ) )>, the new node W
taking the value of B.  C<block insert> across leaves of different
depths makes the leaves of its range children of the new block's
single node, as for any range.  Every change is undone exactly: the
tree, the padding and the values come back.

=item *

I<Single leaves.>  C<block flatten> at the root makes the block a
single leaf, without nodes: its depth in C<block list> is -1, C<block
at> gives its structure as one number, C<block nodedata> at level 0
and -1 names the leaf, and the layout callback gets the leaf as its
single argument.  A change that gives it a second leaf gives it a root
again (see C<block flatten>).

=item *

I<Temporary choices.>  Which sequence of steps an edit uses (a
deletion wraps the shallower leaf, C<block flatten> follows a fixed
recipe), which values survive (C<block sprout> shares the former
leaf's value, the joins keep the start side's), and the
C<-valuecommand> events of these commands (C<copy>, C<new>, the
events told step by step) are provisional; see F<BUGS> 28.

=back

=head2 Indices in blocks

A block occupies the following place in the index space: 1 index unit
for the start of the block, then all the leaves separated by 1 index
separators, and 1 index for the end of the block. Thus a block with
one empty leaf occupies 2 index units.

An I<empty> block (without leaves) occupies 1 unit of the index space.

Note that a block (however complicated) always fits in one line of the
index space. In particular, the usual bindings for C<up> and C<down>
will move you out of a block. (You should expect it, since leaves of a
block I<may> be placed one under another, but may be not.)

=head2 String representation of blocks

The commands that convert block contents to string (C<.t get>,
selection and search) see the contents of a block as a string of the
same size as the size of block in the index space. The start of the
block looks like C<{>, end like C<}>, interleaf separators like C<|>.

An I<empty> block looks like C<.>.

Note that a string representation of a block (however complicated)
always fits in one line.

=head2 Insertion in blocks

Insertion changes contents of the block if the insertion point is
inside the block, i.e.,
after starting index of the block and before the ending position (and
not inside some other block contained in the given one). Note that it
is impossible to be inside an empty block.

If inserted text contains no newlines, it is added to the leaf of tree
the insertion point is in (i.e., at or after the start of, and before
the end of). If it contains newlines, then the resulting leaf is split
into several at the inserted newlines. All the new leaves have the
same parent node as the initial leaf, and its depth (in a block that
is a single leaf, the block gets a root, the parent of the leaves).
The C<-valuecommand> callback is told C<new> for each new leaf (see
L<Telling the program: -valuecommand>).

=head2 Destruction of blocks

When the block is destructed, it contents is merged into the
surrounding environment. Block's head and tail disappear, interleaf
separators behave like newlines. I.e., if block was contained in
another block, interleaf separators of deceased block became interleaf
separators of the parent block, otherwise they became line separators
in the text widget.

=head2 Deletion of text in blocks

=over 5

=item *

If the deletion range does not include any index unit occupied by the
block, the block does not change.

=item *

If a range contains a block as a whole, block is deleted. Registered
callback will be called I<(not implemented)>. Same happens if the
range contains all the block except either head or tail index.

=item *

Otherwise, if the range includes head or tail of the block, the block is
destroyed, and what remains of the contents is merged into enclosing
structure as is described in L<Destruction of blocks>.

=item *

If a range is completely contained inside some leaf, the inner
structure of the block does not change (but if a leaf becomes empty,
registered callback will be called I<(not implemented)>).

=item *

If the range contains leaves separators, two survived leaves are
merged together. If their parents were different, they are also merged
together, and the process continues until the common parent is
met. This is exact opposite to the C<block split ??> subcommand that
would create this separator.  If the two leaves are not equally deep
below their common ancestor (a ragged tree, see L<Ragged trees>), the
shallower one first gets new nodes above it, one level at a time (as
C<block sprout> with one index would give it), until both are equally
deep; then the nodes are merged in pairs as above.  (Leaves and nodes
that the range holds whole are deleted first, see L<Node values and
editing>.)  The C<-valuecommand> callback is told what the deletion
detaches and the nodes it makes (see L<Telling the program:
-valuecommand>).

=back

=head2 Cut and paste with structure

The string of a range (C<get>, the selection) has the delimiters of
blocks as characters: inserted again it is text, and makes no block
and no leaf.  The list of a range (C<block list>) has them as
elements: C<block paste> puts such a list in at an index, with one
command, and C<block cut> takes a range out as a list.

  my @piece = $text->blockCut('sel.first', 'sel.last');
  ...
  $text->blockPaste('insert', \@piece);

B<What a piece carries.>  A value travels with the delimiter that
begins its owner.  A separator of depth I<k> begins a leaf and I<k>
nodes (in a table of rows of cells, a cell separator begins a cell, a
row separator a cell and a row), and C<block list -values> puts their
values into its element; the head of a block begins the block, its
root, its first leaf and the nodes above that leaf, and a block that
is whole in the range has all its values in its header; the start of
a run carries the run's value.  So a piece of a block carries the
values of the leaves and nodes that begin in it, and no others: not
that of the leaf in which it starts.

B<block cut> returns that list and deletes the range as C<delete>
does (see L<Deletion of text in blocks>), but for one rule.  Where
C<delete> joins two leaves, or two nodes, the joined one keeps the
value of the start side if it has one, and else takes that of the end
side.  After C<block cut> it never takes the end side's: that value
is in the piece, with the separator that began its owner, and the
leaf and the nodes in which the range started are left as they were,
with or without a value.  (The values C<block cut> takes out go into
its undo step, as those a deletion drops.)

B<block paste> does what the undo of a deletion does with the list it
kept, at any place:

=over 5

=item *

Strings are inserted; the text gets the tags the list switches on for
it, and of the tags the list does not mention those of the place (as
text typed there would).  A run started in the list by C<[name,
value]> gets that value if it does not join a run that was there.

=item *

A separator is put in as C<block split> at its depth would put it:
the leaf at the place is cut, and so is every node above it up to
that depth, the tree getting more levels below its root if it has too
few.  The leaf after the separator gets the defect the element gives
(see L<Ragged trees>) where the tree at the place allows it.  Then
the new leaf and the new nodes get the values of the element.
Outside blocks a separator is a newline, and its values are not used.

=item *

A block is created with its type, its instance data, its contents
and, if the header has them, the values of its nodes.  If the widget
has no block type of that name the contents are put in without the
block.  An embedded image is created again under a new name; a window
given with C<-window> can only be in one place.

=item *

Marks are moved to where the list has them only with C<-marks>.

=back

What was at the place stays as it was: the leaf pasted into keeps its
value for its first part, and what followed the place in that leaf is
now the end of the last leaf the piece began.

B<Cut, then paste at the same place,> gives back the text, the trees
and the values, if the range cuts no block and the leaves of the
block around it are equally deep (F<t/cutpaste.t> checks it on random
documents); the marks come back with C<-marks>.  Two pieces of two
blocks can be exchanged in this way, also with no third place to keep
one of them: the second block may hold both for a moment.  A
separator keeps its depth, which is counted from the leaves: a row
separator of a table of rows of cells, pasted into a block with one
level, gives that block a second level.  A piece kept on a line
outside blocks loses the depths (its separators are newlines there);
a variable or a block keeps them.

What is not given back:

=over 5

=item *

A range that holds the head of a block without its tail, or the tail
without the head, cuts the block, and both commands delete as
C<delete> does: the block is dissolved.  The list has the part in the
range as a block of its own (of the same type, with a copy of the
instance data, without the values of the root and of the first leaf),
and pasting it makes that block.  C<edit undo> restores a cut block.

=item *

Where the leaves of the block are at different depths and the cut
joins a leaf with a deeper one, the shallower leaf first gets nodes
above it, as for any deletion; the paste does not take them out
again.  I<(Temporary, see F<BUGS> 36.)>

=back

The undo of C<block paste> deletes what the paste put in, as C<block
cut> would (so the leaf pasted into keeps what it had and gets back no
value of the piece), and takes away the levels the paste gave the
tree; the values of the piece wait in the undo step for the redo.

The C<-valuecommand> callback is told what C<block cut> detaches, as
for a deletion, but never C<move> for a join.  C<block paste> detaches
nothing, and the leaves and nodes it makes are not told C<new>,
whether they get a value from the list or not.  I<(Temporary: the
block type is not asked at the joins and splits of these commands;
which value a cell should keep when a piece ends in the middle of it
is a question for the type.  See F<BUGS> 36.)>

The methods C<clipboardCopy>, C<clipboardCut> and C<clipboardPaste>
of the Perl widget use these commands: see L<Tk::eText>.

=head2 Tags and blocks

Characters inside leaves can be tagged in the usual way. Interleaf
separators and tail of the block behave like end-of-lines when
tagged. C<tag names> at the start of a block reports the tags in
effect there; for drawing, a tag that switches off inside the block
does not style the block as a whole.

=head2 Bounding boxes

=over 5

=item *

If index in the text corresponds to a character in a leaf of a block,
it behaves as usual.

=item *

If the index corresponds to the interleaf separator or tail of a
block, the bounding box of the preceeding leaf is returned.

=item *

If the index corresponds to the head of the block, the bounding box
for the whole block is returned.

=back

Bounding box for anything I<invisible> is of size 0 and at the
upper-left corner of the block.

=head1 Display of blocks

The display of blocks is completely customizable. It is based on the
current configuration of the I<type> of displayed block.

=over 5

=item *

If no customization is registered for the block, then the tree
structure is ignored, all the leaves are drawn on the display one
under another, left justified, with wrap enabled, and the resulting
object is vertically centered about the middle of the ascent of the
default font. In what follows we refer to this behavior as I<default layout>.
(The tree structure does not change the places of the leaves, but
lines between the leaves and frames around them show it: see L<Split
lines and frames>.)

=item *

If the block registers a layout callback, it will be called when the
block is about to be drawn. This procedure takes the information on
the size the leaves take on the display, and returns information on
what size the block takes on the display and what should be relative
offsets of leaves in the resulting rectangle. I<Details are subject to
change.> No clipping is performed.

=item *

Layout callback can also specify which leaves I<should not> be shown
at all, and what additional details to show in the rectangle: stolen
lines (see C<block addline>) and ornaments (see L<Ornaments of
blocks>).

=item * I<(Not implemented)>

Block can also specify that some leaves have some additional tags.

=back

=head2 Split lines and frames

I<(Since 2.09.)>

Where the widget itself puts leaves of a block one under another, the
places of the leaves do not show the tree they are leaves of.  The
widget then draws what is hidden: between two leaves, lines that show
how deep in the tree the split between them is; around the leaves,
frames that show how many nodes with a single child are above them.

A I<stack> is a run of consecutive leaves of one block that the widget
lays out one under another:

=over 5

=item *

In a block that is laid out by default (its type has no layout
callback, or the result of the callback was refused), all the leaves
of the block are one stack.

=item *

In a block that is laid out by its callback, each element of the
result that describes leaves with a box (a list of 7 or 13 elements
whose I<repeat count> is at least 1, see L<Layout callback>) makes one
stack of the leaves it describes.  That may be one leaf, or a group of
leaves that the callback saw as one child with a I<repeat count> (see
L<Lying to layout callback>).  Leaves hidden with a list of one
element are in no stack.

=back

The I<box> of a stack is the smallest box that holds the boxes of the
display lines of its leaves, as C<bbox> gives them.  In the default
layout it is the box of the block.

B<Numbers.>  A number is drawn in binary, as one I<stroke> for each
bit that is set:

=over 5

=item *

bit 0 (the value 1): a dotted line, 1 pixel wide (1 pixel drawn, 2
left out);

=item *

bit 1 (the value 2): a dashed line, 1 pixel wide (4 pixels drawn, 3
left out);

=item *

bit 2 (the value 4): a solid line, 1 pixel wide;

=item *

bit 3 (the value 8): a solid line, 3 pixels wide;

=item *

each higher bit: one more solid line, 3 pixels wide.

=back

So 1 is a dotted line, 2 a dashed line, 3 a dotted line and a dashed
line, 4 a solid line.  The strokes of one number never touch: one row
(or column) of pixels is left free between two of them, so that two
strokes 1 pixel wide are 2 pixels apart.  All strokes have the colour
C<gray50>.

B<Split lines.>  For two consecutive leaves of the same stack, let
I<s> be the depth of the separator between them, as C<block list>
reports it (see L<What else is in the widget?>): 0 if both leaves have
the same parent, 1 if their parents are different children of one
node, and so on.  If I<s> is 0, nothing is drawn.  Otherwise I<s> is
drawn as horizontal lines across the box of the stack, from its left
side to its right side.  The lines start on the top row of pixels of
the lower leaf, that is, of its first display line, and go down: the
stroke of the lowest bit that is set comes first, and the strokes of
the higher bits follow one under another.

In a ragged tree (see L<Ragged trees>) I<s> is the depth in the
uniform tree that the widget keeps, and the two leaves may have
different I<defects> (the number of padding nodes directly above a
leaf, as C<block list> reports it).  If the upper leaf has the defect
I<dA> and the lower leaf the defect I<dB>, the left half of the width
of the box shows I<s> - I<dA> and the right half shows I<s> - I<dB>: on
each side, the depth of the separator counted from the parent of the
leaf that is on that side.  A half whose number is 0 draws nothing.
(A defect is never larger than I<s>.)  When the two numbers are equal,
as in a tree whose leaves are equally deep, the two halves are one
line across the whole width.  The left half is the first half of the
pixels of the width, rounded down.  In C<R( x | S( 2 | 3 ) )>, laid out
by default, the separator between C<x> and C<2> has the depth 1, C<x>
the defect 1 and C<2> the defect 0: a dotted line is drawn on the
right half only (C<2> is one level below the node where the two
leaves part, C<x> is a child of that node), and nothing between C<2>
and C<3>.

B<Frames.>  For each stack the widget looks for the node that the
stack is I<expected> to be: the node I<E> at the distance I<D> from
the root of the tree of the block, on the way from the root to the
first leaf of the stack.  I<D> is 0, so that I<E> is the root, in a
block that is laid out by default.  In a block that is laid out by its
callback, I<D> is the C<-layoutdepth> of the type: the nodes at that
distance from the root are the ones that the callback sees as children
with a I<repeat count> (with C<-layoutdepth 1>, the children of the
root; with C<-layoutdepth 0>, the root).  The stack has no frame

=over 5

=item *

if the type has a layout callback and no C<-layoutdepth> (the value
-1), or

=item *

if the first leaf of the stack is not deeper than I<D> (I<E> would be
that leaf itself), or

=item *

if the leaves of the stack are not exactly all the leaves below I<E>
(as when C<-layoutwidths> made the callback see several children as
one).

=back

Otherwise let I<n> be the number of nodes in the chain that starts at
I<E> and goes down for as long as the node has exactly one child (a
node or a leaf): I<E> if it has one child, that child if it is a node
with one child, and so on.  Padding nodes (see L<Ragged trees>) are
not nodes of the tree and are not counted.  For blocks that are laid
out by default:

  R( a | b )                  n = 0
  R( a )                      n = 1
  R( N( a | b ) )             n = 1
  R( N( a ) )                 n = 2
  R( N( a | b ) | M( c ) )    n = 0

A block that is a single leaf (see C<block flatten>) has no nodes:
I<n> is 0.  If I<n> is 0, nothing is drawn.  Otherwise I<n> is drawn as
frames around the box of the stack: for each stroke the outline of a
rectangle.  The frames start with the pixels next to the box, 1 pixel
outside it, and go outwards: the stroke of the lowest bit that is set
is the innermost frame, and the strokes of the higher bits are further
out, so that two frames 1 pixel wide are 2 pixels apart.  The dots or
dashes of a frame start at its top left corner.

B<What they are not.>  The lines and frames take no room: the block
and its leaves are laid out exactly as without them, and C<bbox>,
C<dlineinfo> and the pointer do not see them.  They are made anew at
every layout of the block.  They are drawn under the text of the
block, as the ornaments of the block with C<-layer under> are (see
L<Ornaments of blocks>), and before all of those.  As those, they are
clipped to the display line of the block and to the text area of the
widget: where a stack reaches the top, the bottom, the left end or the
right end of its display line, that side of its frames is outside and
is not drawn.  (A block that is as high as its line reaches the top
and the bottom of the line, unless the line has space above and below
it: C<-spacing1>, C<-spacing3>.)  They are not ornaments of the
program: C<ornament names> does not list them.

The option C<-splitlines> of the type of the block (see C<block
configure>), true by default, switches the lines and the frames off
for the blocks of that type:

  $text->blockConfigure('Fraction', -splitlines => 0);

=head1 Layout callback

Layout callback is the main component of the block.

I<Details are subject to change.>

A layout procedure takes a variable number of I<input arguments>. The
I<first element>
is a list containing the block name and widget name, (possibly with an
addition, say, if I<instance data> is present in the block, it will be
the next element). The I<second element> gives the horizontal offset of the start
of the block inside the ambient line (it can be different from the
absolute horizontal position if the block is inside some other
block). The I<remaining elements> specify the tree structure of the block and the
layout details of the leaves. Any child of the root node of the tree
provides one argument of the function (in a block that is a single
leaf, the leaf is the only argument).  In a ragged tree (see
L<Ragged trees>) the arguments follow the tree of the block: a node's
list holds the lists of its leaves and of its nodes side by side, in
their order.  All the arguments are lists,
and

=over 5

=item *

if the child is a leaf, then the list consists of the I<repeat count>
(necessarily 1), current C<y> offset inside the block, width, I<total
width>, height, baseline, and some additional data on the leaf I<(last
part is not implemented, but it will contain horizontal stretchability
of the leaf, vertical one and stretchability of the baseline)>.

=item *

If the child is a node, the list elements are themselves lists that
are obtained using the same rules recursively: if children are leaves,
the elements are lists of numbers, otherwise lists of lists.

=item *

If block is configured to lie to the layout procedure about its contents, it
can present several lines or a whole subtree of itself in the same
form as a single leaf. In this case the I<repeat count> above can be
bigger than 1.

=back

B<Summary:>

=over 1


=item Input arguments:

  {bname wname ...} ho {rc yo w tw h b hs vs bs} ...

=item Abbreviations:

BlockNAME, WidgetNAME, Horizontal Offset, Repeat Count, Y Offset,
Width, Total Width, Baseline. hs, vs, bs are currently not used.

=back


The return value of the callback must be a list. The length of the
list (counting multiplicities, see below) must be at least the number of
leaves plus one. The first element of the list specifies the layout
information on the block as a whole, the others specify layout
information for the leaves and (possibly) additional elements to show.

There are three possible formats of the elements in this list that
are lists of numbers (and should be of the form C<{dd ... dd}>), of
lengths 1, 7, or 13, and a fourth one, an ornament (see below). The first number is either I<repeat count>, or
I<id> of additional line to show (i.e., the same data as returned by
C<textWidget block addline index> command). Lists of different length have
the following meaning:

=over 5

=item 1:

the child is not shown at all. This format is prohibited for the
layout information of the block as a whole and for additional
lines. The only element of the list is the I<repeat count>.

=item 7:

If the block as a whole is not laid out yet, this is the information
about it, and all the elements but what describe width,
height and baseline are ignored.  If not all the leaves are laid out
yet, the first element is the I<repeat count>, what means the number
of leaves that are described by this list (it can be 0).

The remaining elements of the list provide x and y offsets of
the upper-left corner inside the ambient block, width, I<total width>,
height, and baseline of the block as a whole, or of a group of leaves,
or a leaf. If it describes a group of leaves, the leaves are laid out
as by default layout procedure. Width, height, and baseline
information is used for displaying background of the line.

If all the leaves are laid out, then this list describes an additional
element to draw if the first element is greater than 0, i.e. it is
considered a I<Block ID> of an additional drawing element, and the
rest specifies the layout of this element. If it is 0, then this
element of the list is ignored exactly as in other cases.

=item 13:

I<(not implemented, but accepted by the widget):> the first 7 elements
have the same meaning as above, the last 6 provide stretchability
x and y position of upper-left corner, width, I<total width>, height,
and baseline.

=back

The I<total width> above is the width of the leaf including the space
reserved for showing the background of the leaf terminator.

Any element but the first may also be an I<ornament> of the block
(I<new in 2.08, provisional>): a list whose first element is the name
of a type of ornament (C<line>, C<polygon>, C<rectangle>, C<oval>,
C<arc>, C<text>), followed by numbers, the coordinates of its points
(pairs I<x y>, in pixels from the top left corner of the block), and
then options and their values, as for C<ornament create> (see
L<Ornament subcommands>):

  ['line', 0,14, 3,20, 8,2, 30,2, -width => 1]     # a radical's stroke

An ornament is not a leaf (it is not counted among them) and may come
anywhere after the first element.  It is drawn with the block, every
time the block is drawn: with C<-layer under> (before the text of the
leaves, after the stolen lines returned before it in the list), or
over the text (the default, after the leaves).  See L<Ornaments of
blocks>.  A bad ornament (a coordinate that is not a number, an odd
number of coordinates, a wrong number of points for its type, a bad
option) is reported as other bad results are: a background error, and
the block is laid out as if it had no layout callback.


B<Summary:>

=over 1

=item Return list elements:

  {Block Layout} {Leaf0 Layout} ...
        {Leafn Layout} {Additional Element0 Layout} ...
        {Additional Elementn Layout}

=item Layout Styles

=over 4

=item

Block Layout - C<{ig ig ig w ig h b}>

=item

Show one or more leaves - C<{rc xo yo w tw h b}>

=item

Hide one or more leaves - C<{rc}>

=item

Show Additional Elements - C<{bi xo yo w tw h b}>

(C<w> is not very important), put after leaves.

=item

Ornament - C<{type x1 y1 ... ?-option value ...?}>, anywhere after the
block layout.

=back

=item Abbreviations:

IGnored, Width, Total Width, Height, Baseline, XOffset, YOffset,
Repeat Count, Block Id

=back

None of the returned data is used for clipping. However, it is used in
directing the mouse events and reporting bounding boxes (not that of
ornaments).

=head2 Lying to layout callback

It is possible to configure a block to lie about its structure to the
layout callback. This can greatly simplify writing the callback in
interpreted languages, if the default layout procedure is satisfactory for
I<parts> of a block. 

Setting the C<-layoutdepth> and/or C<-layoutwidths> options for a block
forces the layout procedure to be called with agruments corresponding
to modified tree structure. 

If C<-layoutdepth> is set, the depth of the tree is modified to be the
given number. If the true depth of the tree is too small, tree is
extended from the root side, if it too deep, the subtrees on the
maximal allowed depth level are mocked as lines with I<repeat count>.
In a ragged tree (see L<Ragged trees>) the true depth is that of the
deepest leaf, and a shallower leaf is presented inside lists of one
element down to the given depth, so that the callback sees every leaf
at that depth.

If C<-layoutwidths> is set, this can restrict the number of branches
going out of any node of the modified tree. The value of this option
should be a list, elements of this list are either numbers, or lists
of the form C<{min max}>. (A single C<number> is equivalent to a pair
C<{number number}>). N-th element of the list controls the number of
branches going out of nodes on the distance N from the root. If there
are too few branches, it adds branches that contain simulated groups
of leaves with I<repeat count> 0. If there are too many branches, it
groups several last brunches into one with appropriate I<repeat
count>. I<(Current implementation is buggy in interaction of
C<-layoutwidths> and C<-layoutdepth> if the depth of the node is less
than C<-layoutdepth>.)>


=head1 Block subcommands

=over 7

=item B<configure> I<blockName ?option value ... ?>

Standard procedure for creating and configuring block type. Currently
supported configuration options are

=over 14

=item B<-layoutcmd>

Layout callback.

=item B<-layoutdepth>

Depth of simulated tree for layout callback. Default -1.

=item B<-layoutwidths>

List of widths of levels of simulated tree for layout
callback. Default C<{}>.

=item B<-empty>

Boolean value that specifies that the blocks of this type contain no
leaves (I<empty> blocks).

=item B<-ornaments>

A list of ornaments drawn for every displayed block of this type
(I<templates>; new in 2.08, provisional), each C<{type point point
... ?-option value ...?}> as the arguments of C<ornament create>,
whose points are computed from the boxes of the block and of its

=item B<-splitlines>

Boolean value that specifies whether the split lines and frames are

=back

=item B<cget>

Standard configuration get procedure.

=item B<at> I<index>

Returns information in the block that starts at the given index or
"nothing" if there is no such block. Returned information is a list
consisting of block start index, block length in index space, block
name, block instance data, structure of the block. The latter is a
list (possibly of lists) with leaves being lengths of block leaves:
a node is a list of its children, in a ragged tree leaves and nodes
side by side (C<[1, [1, 1]]> for C<R( x | S( 2 | 3 ) )>); a block that
is a single leaf gives one number (see L<Ragged trees>).

=item B<of> I<index>

Returns information in the innermost block that contains the given index or
empty list if there is no such block. See C<at> subcommand for
description of return value.


=item B<delete> I<blockName ?blockName ...?>

Deletes the information on I<block types>. Error is returned if the
are blocks of the given types in the widget.


=item B<insert> I<blockName index1 ?index2?>

Inserts block of the given type in the widget. The block contains one
node, and all the leaves are immediate children of this node. If
I<index2> is not specified, creates a block with one empty leaf,
otherwise moves the contents of the widget between I<index1> and
I<index2> into the tree.

In the latter case I<index1> and I<index2> should be outside of any
block, or properly inside the same block. The newlines (or,
correspondingly, interleaf separators of enclosing block) are
converted into interleaf separators of newly created block.  This is
prohibited for I<empty> blocks.  An I<index2> before I<index1> is an
error.

More precisely: both indices outside of any block, or both inside the
same block (the innermost block around each is the same) are
accepted; ends in different blocks are an error.  A range inside a
block may cross leaves of that block, and nodes of its tree too.  The
leaves moved (whole, or the part of the first one after I<index1> and
the part of the last one before I<index2>) become immediate children
of the single node of the new block, in their order: whatever
structure they had in the enclosing block (the nodes above them) is
flattened, and the separators between them, whatever their depth,
become separators of depth 0 of the new block.  Blocks nested in the
range move into the new block unchanged.  In the enclosing block, the
parts of the first and the last leaf left outside the range (with the
new block between them) are one leaf, which stays where the first
leaf was; nodes left without leaves disappear, but the other nodes
are not joined.  With C<{ab|cd|ef|gh}> on line 1, whose root has two
nodes, one with the leaves C<ab> and C<cd>, the other with C<ef> and
C<gh>, C<block insert G 1.2 1.9> (over C<b|cd|ef>) gives
C<{a{b|cd|ef}|gh}>: the leaves C<b>, C<cd> and C<ef> of the new block
are children of its single node, and the root of the outer block
still has two nodes, one with the leaf C<a{b|cd|ef}>, the other with
C<gh>.  (What happens to the values of the nodes involved is in
L<Node values and editing>.)

Recorded for undo; see L<Undo and redo of block and tag changes>.

=item B<names>

Returns list of names of currently defined I<block types>.

=item B<split> I<index ?level?>

=over 5

=item *

If I<index> is outside of blocks, inserts newline.

=item *

Otherwise, if
I<level> is not specified, or is 0, is equivalent to insertion of
newline, i.e., splits the leaf into two with the same
parent.

=item *

If I<level> is positive, splits the leaf in two and changes the
structure of the tree.

=over 5

=item *

If I<level> is less than the distance from the leaf to the root,
splits the I<level>th parent (and all the parents of less order) in
two. The beginning of the split leaf goes to one node, the rest
(together with the leafs in the same node after the splitted one) goes
to another. Example of B<split 1> follows (the leaf marked B<X> is
split into two marked B<x>):

      ___		  ___
     / __       	 /  _
    / /         	/  /
 .-------X     	     .-------x
  \   \__	      \ \____x
   \_____	       \   \_
			\____

=item *

If I<level> is too big to proceed with the above procedure, the tree is
extended first: a new node is inserted between the root and all its
children (one for each level missing), so that the root, which stays
the root and keeps its value, has one child; the new node is then
split as above.

=back

=item *

In a ragged tree (see L<Ragged trees>) the levels are those of the
uniform tree the widget keeps, padding nodes included (as the depths
of C<block list>): a leaf with I<d> padding nodes above it (its
defect) has I<d> levels that cut only its padding, so C<block split>
at a level up to I<d> makes the new leaf a sibling of the leaf, as a
newline does, and each level above I<d> cuts one real node (its
parent, then the parent of that node, and so on).  For C<ax> in
C<R( ax | N( b | c ) )> on line 2 (one padding node above C<ax>),
C<block split 2.2 1> gives C<R( a | x | N( b | c ) )>, as C<block
split 2.2 0> does, and C<block split 2.2 2> inserts a node R1 between C<R> and its children
and splits it: C<R( R1( a ) | Y( x | N( b | c ) ) )>.  In a block
that is a single leaf, C<split> at level 0 gives the block a root
again, and at level 1 or more adds a root above the leaf first (see
C<block flatten>).

=back

Returns the number of levels added above the root (-1 outside of
blocks).  The new nodes and the new leaf have no values (the root keeps its
value when levels are added: they are inserted below it, see L<Node
values and editing>); the C<-valuecommand> callback is told C<new> for
each.  Recorded for undo; see L<Undo and redo of block and tag
changes>.  An I<index> on the last (dummy) line is taken as the end
of the line before it, as for C<insert>.


=item B<level> I<index ?level?>

I<index> must name a separator of a block (the innermost block that
holds it).  Without I<level>, returns the depth of the separator, as
C<block list> shows it: 0 between two leaves of the same lowest node,
1 between leaves whose lowest nodes are siblings, and so on.  With
I<level>, gives the separator that depth and returns nothing.  No text
moves, and no leaf changes; the nodes above the two leaves do:

=over 5

=item *

A higher depth cuts the nodes that hold both leaves, from the lowest
up, as C<block split> at that depth would have cut them when it put
the separator in: the part before the separator keeps the node's
value, the part after it is a new node without one.  If the tree has
too few levels, new nodes are inserted below the root first, as for
C<block split>.  In a table of rows of cells this makes a cell
separator a row separator: the row is cut in two.

=item *

A lower depth joins, on each level down to the new depth, the node
that ends before the separator with the node that begins after it, as
the deletion of the separator would join them: the joined node keeps
the value of the first if it has one, else it takes that of the
second, and the other value is freed (kept in the undo step).  The
two leaves stay two leaves, with their values.  The tree keeps its
number of levels (see C<block trim>).  In a tree whose leaves are at
different depths (see L<Ragged trees>) both leaves must have nodes of
their own down to the new depth: else the command fails, and C<block
sprout> can first give the shallower leaf a node.

=back

Deleting a separator and putting it in again with C<block split> at
another level gives the same tree, but joins the two leaves in
between, so that the value of the second leaf is lost; C<block level>
keeps it.  Recorded for undo (see L<Undo and redo of block and tag
changes>); the C<-valuecommand> callback is told C<new> for the nodes
a higher depth makes, and what a lower depth does to the values of
the nodes it joins, as for a deletion.

=item B<sprout> I<index1 ?index2?>

With one index, the leaf that I<index1> names (as C<block nodedata
index1 0> names it, see L<Which node, which run>) gets a new node
above it, whose only child it is (a I<wrap>):

  P( ... | L | ... )   ->   P( ... | N( L ) | ... )

With C<{num}> on line 2 (head 2.0, C<num> 2.1-2.3, the tail 2.4),
C<.t block sprout 2.1> gives C<R( N( num ) )> and returns 0.  It works
on any leaf, the only leaf of a block included, in nested blocks too
(the innermost block holding the index), and in a block that is a
single leaf (see C<block flatten>), which first gets a root:
C<R( N( leaf ) )>.  It is the same as the two-index form from the
delimiter before the leaf to just after the one after it, which
cannot name the only leaf of a block (that range belongs to the
enclosing structure).  The value of the leaf moves to the new node;
the leaf has none afterwards.  I<(Since 2.06; decision O8.)>

With two indices, the leaf that holds the range from I<index1> to
I<index2> gets a node of its own for that range: the leaf L, a child of the node P, becomes
three children of P, the text before the range (the I<start> piece),
a new node N holding the range as its only leaf (the I<middle> piece),
and the text after the range (the I<end> piece):

  P( ... | L | ... )   ->   P( ... | start | N( middle ) | end | ... )

So the leaves of the tree are no longer all at the same depth.  A
range that begins at the start of the leaf's text makes an empty start
piece; one that begins one position earlier, on the delimiter before
the leaf (the head of the block, or the separator before the leaf),
makes none.  In the same way a range that ends at the end of the
leaf's text makes an empty end piece, and one that ends just after the
separator (or the tail) after the leaf makes none: with both
delimiters, the leaf just gets a node above it.  With C<{num|den}> on
line 2 (head 2.0, C<num> 2.1-2.3, the separator 2.4, C<den> 2.5-2.7,
the tail 2.8):

  .t block sprout 2.2 2.3   ;# {n|u|m|den}: R( n | N( u ) | m | den )
  .t block sprout 2.1 2.4   ;# R( | N( num ) | | den ): two empty leaves
  .t block sprout 2.0 2.5   ;# R( N( num ) | den )
  .t block sprout 2.0 2.3   ;# R( N( nu ) | m | den )
  .t block sprout 2.2 2.2   ;# R( n | N( ) | um | den ): an empty middle

(C<R( a | N( b ) )> is a root R with a leaf a and a node N whose only
leaf is b.)  Where the range could be read with either of two leaves
(it holds just the separator between them), the leaf before the
separator is taken.  The range must not hold a separator (other than
the two delimiters), must not be reversed, and its ends must be in the
same block (a block nested wholly in the range moves into the middle
piece).  The separators go in as with C<block split> at level 0 (marks
and tags at the cuts behave the same).  Returns the number of
separators put in (0, 1 or 2).

The value of the former leaf (see L<Values>) goes to the start piece,
the new node and the end piece (those that are made) as the same
value: a reference shared, not a copy; the middle leaf gets none.
I<(These choices are temporary.)>

How the other commands work on such trees is in L<Ragged trees>.

Recorded for undo; see L<Undo and redo of block and tag changes>.
Refused while the C<-valuecommand> callback runs.

=item B<flatten> I<index level>

Flattens a node of the innermost block containing I<index> into one
leaf: the node I<level> levels above the leaf I<index> names, counted
as for C<nodedata> (0 the leaf itself, 1 its parent, and so on; -1
the root, -2 a child of the root on the way to the leaf).  Every
separator inside the node is deleted, and where the leaves on its two
sides are not equally deep, the deeper one loses the nodes that hold
it alone; then the node itself goes, its only leaf taking its place.
As steps: until the node's only child is a leaf, the separator inside
it farthest to the right whose two leaves are equally deep below their
common ancestor is deleted (the I<join> of L<Deletion of text in
blocks>, the nodes on the two sides merged in pairs); if there is
none, the deepest node inside it whose only child is a leaf (the one
farthest to the right among equally deep ones) is replaced by that
leaf (a I<pull out>); then the node itself is pulled out.  With
C<{num|den}> on line 2:

  .t block sprout 2.2 2.5    ;# {n|um|den}: R( n | N( um ) | den )
  .t block flatten 2.3 1     ;# R( n | um | den ), returns 0
  .t block flatten 2.3 -1    ;# {numden}: the block is one leaf, returns 2

Level 0 does nothing (and is not recorded for undo); a level beyond
the leaf's root is an error, worded as for C<nodedata> ("... has 1
level above this leaf").  Blocks nested in the text flattened stay as
they are.  Returns the number of separators deleted.

The values (see L<Values>): a join keeps the start side's value of
each pair merged, or takes the end side's if the start side has none
(as a deletion does); a pull out gives the leaf the node's value if
the node has one (the leaf's own goes), else the leaf keeps its own
(as C<block trim> does).  The values that go are kept in the undo
step.  I<(The choice of the steps and these rules are temporary.)>

Flattening at the root makes the block a single leaf, which is then
its own root: C<block at> gives its structure as one number (the
leaf's length), C<nodedata> at level 0 and at -1 names the leaf, the
layout callback gets the leaf as its single argument, C<block list>
gives the depth -1, and C<block trim> refuses it.  A newline in the
leaf (or C<block split> at level 0) gives the block a real root again,
with the two leaves as its children; C<block split> at level 1 or more
adds a real root above the leaf, as when a level reaches past the root
(the pieces are leaves of the new root; each level more adds one more
level, as before); C<block sprout> first gives the block a real root,
so that the result is C<R( start | N( middle ) | end )>.  The undo of
each of these makes the block a single leaf again.

Recorded for undo, one step (see L<Undo and redo of block and tag
changes>).  Refused while the C<-valuecommand> callback runs.

=item B<trim> I<index>

If the block at index has only one edge coming from the root, and this
edge does not end in a leaf, deletes the root. The resulting tree will
be 1 level more shallow. Returns error if out of block or the above
conditions are not met.  Recorded for undo; see L<Undo and redo of
block and tag changes>.

=item B<data> I<index ?data?>

Returns or sets I<instance data> information for the block at C<index>.

=item B<nodedata> I<index level ?value?>

Returns or sets the value kept with a node of the tree of the block
containing I<index>: the leaf I<index> names if I<level> is 0, its
parent if it is 1, and so on; the root if I<level> is -1, a child of
the root on the way to the leaf if it is -2, and so on (down to the
leaf itself).  The levels are counted for the leaf I<index> names:
in a tree whose leaves are at different depths (see L<Ragged trees>) the
number of levels above a leaf depends on the leaf.  Returns the
value (an empty result, C<undef> in Perl, if the node has none); with
I<value>, sets it and returns nothing, C<undef> removing the value.
See L<Values>, which tells which leaf a position names.

=item B<addline> I<index>

"Steals" the displayed structure of the line starting at
I<index>. Returns the I<id> of the resulting element. This I<id> can
be used in the return value of the layout callback to specify
additional elements used in drawing of the block. I<Beware that the
behaviour is undefined if the line contains something more complicated
than tagged characters.>

A stolen line is a picture: it keeps the size it had, stretched or
cut to the box the callback gives it.  Strokes that must follow the
size of what they decorate (the sign of a radical, the bar of a
fraction, the rules of a table) are simpler as ornaments of the block
(see L<Ornaments of blocks>); the demo uses stolen lines only for
glyphs (the delimiters of its C<LR> block) and backgrounds.

=item B<deletelines>

Deletes all the "stolen" lines.

=item B<list> ?B<-values>? I<from> I<to>

See L<What else is in the widget?>.  With B<-values> the list holds
what C<block paste> needs to put the range in again with its values:
the separators carry the values of the leaves and nodes that begin
after them, and the runs that are on where the range starts are
listed.

=item B<cut> I<index1 index2>

Returns the list of C<block list -values> for the range and deletes
the range.  See L<Cut and paste with structure> for how this deletion
differs from C<delete>.  An undo step of its own.  In a disabled
widget only the list is returned.

=item B<paste> I<index list> ?B<-marks>?

Puts the contents of I<list> in at I<index>, as one command.  I<list>
is a reference to an array of the elements of C<block list>, as
C<block list>, C<block list -values> and C<block cut> return them
(or made by the program).  Returns the indices of the start and of
the end of what was put in.  An undo step of its own; nothing is done
in a disabled widget.  With B<-marks> the marks the list names are
moved to their places in what is put in (C<insert> and C<current>
never are).  See L<Cut and paste with structure>.

=back

=head1 Ornaments

I<(New in 2.08, provisional: the names, the forms of points and the
behaviour may change.)>

An I<ornament> is a drawing primitive of the kind a canvas has (a
line, a polygon, a rectangle, an oval, an arc, a text) whose
coordinates are not
numbers but I<reference points>: points computed from the places where
the characters of the text are drawn.  The ornament is computed anew
whenever the text is redrawn, so it follows the text it refers to.  It
takes no room: the text is laid out as if it were not there, and it is
drawn over the text, or under it (over the backgrounds of tags).

=head2 Points

A point is a list whose first element says how it is computed:

=over 5

=item B<at> I<index> ?I<anchor>?

A place on the box of the character at I<index> (as C<bbox> would give
it, but not clipped to the window, and for the last character of a
display line only its own width, where C<bbox> gives it the rest of the
line; inside a block, the box of the character in its leaf).

=item B<range> I<index1> I<index2> ?I<anchor>?

A place on the smallest box that holds the boxes of the characters
from I<index1> up to, not including, I<index2> (for an empty range, the
box of I<index1> with no width).  Its baseline is that of its first
character.

=item B<line> I<index1> I<index2> I<n> ?I<anchor>?

A place on the piece of the range from I<index1> up to I<index2> that
is in its I<n>-th display line: the smallest box that holds the boxes
of the range's characters on that display line.  I<n> counts from 0
for the first display line of the range, and from -1 for the last; a
number beyond the range's display lines gives the nearest one.  Inside
a block, the display lines are those of its leaves.  The display lines
are taken in the order of the text (top-level lines from the top
down).  Only the display lines in the window are known: the part of
the range above the window is one piece (the stand-in of
I<index1>), the part below it another (the stand-in of I<index2>).

=item B<outline> I<index1> I<index2>

Allowed only as a point of a C<line> or a C<polygon> (an error
elsewhere, in C<ornament point> or inside another point): it stands for
all the corners of the outline of the range, the union of the pieces
of its display lines (see C<line>), clockwise from the top left corner
of the first piece.  For a range over several display lines that is
the shape a selection has: the first piece from its first character to
its right end, the middle lines whole, the last piece up to its last
character (8 corners; more when the middle lines differ in width).  The
pieces are taken as bands from the top down: a band reaches down to the
next one (the space between lines is inside), and pieces side by side
(the leaves of a block) make one band, their bounding box.
C<ornament coords> gives every corner.

=item B<mix> I<weight> I<point> ?I<weight> I<point> ...?

The weighted mean of the points (the weights must not add up to 0).

=item B<offset> I<point> I<dx> I<dy>

The point moved by I<dx> to the right and I<dy> down: screen distances
(such as C<3> or C<2p>), or numbers with the unit C<em> or C<ex> (such
as C<0.5em> or C<-1ex>), measured at every redisplay in the font of
I<point>: an I<em> is the width of C<M> in that font, an I<ex> half its
ascent.  The font of an C<at> point is that of the character at its
index (the one after the position; with a C<leftward> wrapper, the one
before it); that of a C<range> or C<line> point, the largest font in
it (the one with the largest em), or with the units C<emmin>,
C<emmid>, C<emmax>, C<exmin>, C<exmid>, C<exmax>, its smallest font,
the mean of its smallest and largest, or its largest; that of C<mix>,
C<min>, C<max>, C<xy>, C<yx> and C<offset>, the font of their first
point.  A position that is not displayed has the widget's font.

=item B<xy> I<point1> I<point2>

The x coordinate of I<point1> with the y coordinate of I<point2>.

=item B<yx> I<point1> I<point2>

The y coordinate of I<point1> with the x coordinate of I<point2> (its
font is that of I<point1>).

=item B<min> I<point> ?I<point> ...?, B<max> I<point> ?I<point> ...?

The smallest (largest) x and the smallest (largest) y of the points.

=item B<leaf> I<k> ?I<anchor>?, B<block> ?I<anchor>?

Only in the ornaments of a block type: see L<Ornaments of blocks>.

=back

The I<anchor> is one of C<nw>, C<n>, C<ne>, C<w>, C<center> (or C<c>),
C<e>, C<sw>, C<s>, C<se> (as in Tk), C<bw>, C<b>, C<be>: the left end,
the middle and the right end of the baseline, or C<mw>, C<m>, C<me>:
the same on the mid line, half an x-height above the baseline (the
x-height is half the ascent of the font of the point: that of its
character; for a range, of the largest font in it; the widget's font
for a stand-in).  It may also be a list of two numbers I<fx> I<fy>: the
place at the fraction I<fx> of the width from the left and I<fy> of the
height from the top (C<[0.5, 0.5]> is C<center>).  The default is
C<bw>.

An index that names no mark and no tag (such as C<2.5>, C<2.5+3c> or
C<2.0 lineend>) is resolved when the ornament is created (or its
points replaced), and the ornament keeps the position as a I<private
mark> of its own: the point stays on its character whatever is
inserted or deleted before it.  A private mark has right gravity (text
inserted at it goes before it), except the end of a range, which has
left gravity (text inserted at the end of a range stays outside it).
An index that names a mark or a tag (C<insert>, C<mymark+3c>,
C<sel.first>), C<end>, C<@x,y>, or the name of an embedded image or
window, is kept as it is written and computed again at every
redisplay.  An ornament whose index no longer exists (its mark was
unset, its tag removed) is not drawn.

Wherever an index goes, a I<wrapper> makes a private mark of a given
gravity, of any index (resolved now, even if it names a mark):

=over 5

=item B<leftward> I<index>

A private mark with left gravity (text inserted at it goes after it).

=item B<rightward> I<index>

A private mark with right gravity.

=back

In Perl a wrapper is an array reference too: C<< [at => [leftward =>
'insert']] >>.  The program never sees the private marks: they are not
in C<mark names>, C<mark next>, C<mark previous>, C<dump> or C<block
list>, cannot be named (the names of marks starting with the character
C<\001> are reserved: C<mark set> refuses them), and never have a
value.  Deleting an ornament, replacing its points or destroying the
widget removes them.  C<ornament points> gives the index of each
private mark as it is now (a wrapped one as the wrapper:
C<[leftward =E<gt> '2.7']>).  When a deletion moved a private mark, its
undo puts it back, as it does with the program's marks.

A position that is not displayed (above or below the window) gets a
stand-in place: where it would be if every text line between it and
the window took one line height (that of the top or bottom display
line), with no width.  Its x is the one the position had when it was
last displayed (each index of each point remembers it, as a place in
its display line: it follows horizontal scrolling); if it has not been
displayed since the point was given, the middle of the text area, or,
with the widget option C<-ornamentproportional>, the place proportional
to its offset in its text line (relative to the line's length) across
the text area.  No line is laid out for a stand-in.  A position hidden
by C<-elide> between displayed lines gets the place of the next
displayed character.  An ornament none of whose positions is displayed
is not drawn (even a shape whose ends are above and below the window).

When a deletion removes all the text an ornament refers to, the
ornament is deleted with it (unless its option C<-keep> is set).  Only
an ornament all of whose indices are private marks qualifies (one that
uses a mark of the program, a tag, C<end> or C<@x,y> is never deleted
this way); it is deleted if the character of each C<at> point (the
character after its mark, or before it for a mark of left gravity)
is deleted, and the range of each range point is inside the deleted
text.

Ornaments are not part of the text: they are temporary.  Undo does not
create or delete them (the undo of a deletion does not bring back an
ornament it deleted), and neither C<dump> nor C<block list> shows them.

In Perl a point is an array reference, nested ones for the points it
is made of:

  $text->markSet(from => '1.4');
  $text->markSet(to => '1.12');
  # A light box under a range, and an arched arrow between two words.
  $text->ornamentCreate('rectangle', [range => 'from', 'to', 'nw'],
      [range => 'from', 'to', 'se'], -fill => '#ffe9a8', -layer => 'under');
  $text->ornamentCreate('line', [at => 'from', 's'],
      [offset => [mix => 1, [at => 'from', 's'], 1, [at => 'to', 's']], 0, 20],
      [at => 'to', 's'], -smooth => 1, -arrow => 'last', -fill => 'red');

=head2 Ornaments of blocks

A block may have ornaments of its own, drawn with it: the layout
callback may return them among its lists (see L<Layout callback>),
with coordinates in pixels from the top left corner of the block.
They take no room and are not leaves; they are drawn every time the
block is drawn, under its text (C<-layer under>: before the text of
the leaves, and among the stolen lines in the order the callback
returned them) or over it (the default: after the leaves), and only
where the block's line is drawn (as the rest of what the block draws,
they are not clipped to the block, but to its display line).  The
options are those of C<ornament create> (C<-keep> has no effect;
C<-state hidden> hides it).  They are not listed by C<ornament names>,
have no id and cannot be configured: the callback gives them anew at
every layout of the block (their options are read then, once per
layout).

A block type may also have ornaments drawn for every block of the type
that is displayed: the option C<-ornaments> of C<block configure>, a
list of ornament specifications (I<templates>) such as

  $text->blockConfigure('Fraction', -ornaments => [
      ['line', [xy => [block => 'w'], [leaf => 0, 's']],
               [xy => [block => 'e'], [leaf => 0, 's']]],   # the bar
  ]);

each a type, its points and options, as the arguments of C<ornament
create>.  The points of a template are computed for each block when it
is laid out, from two forms of point that exist only there:

=over 5

=item B<leaf> I<k> ?I<anchor>?

A place on the box of the I<k>-th leaf of the block (from 0, in the
order of the arguments of the layout callback, which is the order of
the leaves in the block's tree, depth first): the smallest box that
holds its display lines as they are laid out in the block.  Its
baseline is that of the leaf's first display line, its font that of
the leaf's first character (for an empty leaf, the font of the
block).

=item B<block> ?I<anchor>?

A place on the box of the whole block: its width, and its height and
baseline (the ascent and descent the layout gave it).  Its font is
that of the text the block stands in (the tags at the block's
position).

=back

and from C<mix>, C<offset>, C<xy>, C<yx>, C<min> and C<max> of such
points (an offset in C<em> or C<ex> uses the font of its point, as
above).  Points with indices (C<at>, C<range>, C<line>, C<outline>) are
refused there, and C<leaf> and C<block> are refused everywhere else.
The anchors are those of L<Points> (the baseline, the mid line and
fractions included; the default is C<bw>).  A template that names a
leaf beyond the last one, or a leaf the layout callback does not show
(a C<{1}> list), is not drawn for that block.  Templates are drawn
before the ornaments the layout callback returned, in each layer, and
in their order; under the text they come before the stolen lines too.
C<block cget> gives the list as it was given.

=head2 Ornament subcommands

=over 5

=item B<ornament create> I<type> I<point> ?I<point> ...? ?I<option> I<value> ...?

Creates an ornament and returns its I<id> (a number).  I<type> is
C<line> (2 points or more), C<polygon> (3 or more), C<rectangle>,
C<oval> or C<arc> (2: opposite corners of the box), or C<text> (1).
Ornaments are drawn in the order they were created.

=item B<ornament delete> I<id> ?I<id> ...?

=item B<ornament names>

The ids of the ornaments.

=item B<ornament configure> I<id> ?I<option>? ?I<value> I<option> I<value> ...?

=item B<ornament cget> I<id> I<option>

=item B<ornament points> I<id> ?I<point> I<point> ...?

Returns the points of the ornament (as lists, with the indices of its
private marks as they are now), or replaces them.

=item B<ornament coords> I<id>

The points as they are now (x1 y1 x2 y2 ..., in pixels from the
top left corner of the window, before smoothing and arrowheads), or
an empty list if the ornament is not drawn.

=item B<ornament point> I<point>

Computes a point now: returns its x and y, and 1 if a position it uses
is displayed (0 if only stand-ins were used).

=back

The options (each type has those that apply to it):

=over 5

=item B<-fill> I<color>

The color of a line or a text; the inside of the other types (by
default none; black for a polygon, a line and a text).

=item B<-outline> I<color>

The outline of a polygon, rectangle, oval or arc (by default black,
for a polygon none).

=item B<-width> I<distance>

Of the line or outline (1).

=item B<-dash> I<list>

A dash pattern: lengths in pixels of the dashes and the gaps, such as
C<4 2> (by default a solid line).

=item B<-capstyle>, B<-joinstyle>

As for a canvas line (C<butt>, C<round>).

=item B<-smooth> I<boolean>

A line or polygon becomes a curve, as on a canvas: quadratic splines
through the midpoints of its segments, bent toward the points between
them (an open line still starts and ends at its end points).

=item B<-arrow> C<none>|C<first>|C<last>|C<both>, B<-arrowshape> I<{a b c}>

Arrowheads of a line, as on a canvas (C<8 10 3>).

=item B<-start> I<degrees>, B<-extent> I<degrees>, B<-style> C<pieslice>|C<chord>|C<arc>

Of an arc, as on a canvas: the part of the oval in the box from the
angle I<-start> (0 by default: from the right, counterclockwise) over
I<-extent> degrees (90 by default; at most 360 either way), drawn as a
pie slice (the default), a chord (the arc closed by a straight line),
or the arc alone (not filled).

=item B<-text> I<string>, B<-font> I<font>, B<-anchor> I<anchor>

Of a text: what it says (one line), its font (by default the widget's)
and the place of its box (a Tk anchor) at its point (C<center> by
default).

=item B<-keep> I<boolean>

Keep the ornament when its text is deleted (by default it is deleted
with it, see above).

=item B<-layer> C<over>|C<under>

Over the text (the default) or under it.

=item B<-state> C<normal>|C<hidden>

=back

=head1 Mark and tag subcommands

The C<mark> and C<tag> subcommands are those of the Tk text widget,
with one more each:

=over 7

=item B<mark data> I<markName ?value?>

Returns or sets the value kept with the mark I<markName>.  Returns the
value (an empty result, C<undef> in Perl, if the mark has none); with
I<value>, sets it and returns nothing, C<undef> removing the value.  A
mark that does not exist is an error (C<there is no mark named
"m">).  See L<Values>.

=item B<tag data> I<tagName index ?value?>

Returns or sets the value kept with the run of the tag I<tagName> that
contains the character at I<index>.  Returns the value (an empty
result, C<undef> in Perl, if the run has none); with I<value>, sets
it and returns nothing, C<undef> removing the value.  A character
without the tag is an error (C<no run of tag "b" at 1.6>), as is a
tag that does not exist.  See L<Values>.

=back

=head1 The dump subcommand

  .t dump ?-all -text -mark -tag -window -image -block -values? ?-command script? index ?index2?

C<dump> is Tk's, and looks into blocks: the text, marks, tag toggles,
windows and images inside a block are reported with their (external)
indices; with C<-block> (part of C<-all>) a C<block> entry (the block
type, at the block's head) and a C<blockend> entry (after its tail)
surround them.

With C<-values> (not part of C<-all>; alone it means C<-all
-values>), every entry gets a fourth field: for a C<mark> entry, the
value of the mark (C<mark data>), for a C<tagon> entry, the value of
the run the toggle starts (C<tag data>), a copy in either case; for
every other entry, and for marks and runs without a value, C<undef>
(an empty string in Tcl).  So the result stays a list of entries of
one length, four elements each instead of three.  A C<-command>
callback gets the fourth field as a fourth argument (without
C<-values> it gets three, as before).  The values of block nodes
(C<block nodedata>) and the instance data of blocks (C<block data>)
are not in the dump: a block carries a tree of them, which C<block
list> shows (the header of a C<Tk::Text::Block>); the C<block>,
C<blockend>, C<tagoff>, C<text>, C<window> and C<image> entries have
C<undef>.  Without C<-values> the dump is as before.

  .t dump -mark -values 1.0 end
  ;# mark m 1.2 mv  mark insert 3.0 {}  ...

=head1 Undo and redo of block and tag changes

With C<-undo> on, C<block insert>, C<block split>, C<block trim>,
C<block sprout>, C<block flatten>, C<block cut>, C<block paste>,
C<block level>, C<tag add> and C<tag remove> are
recorded for C<edit undo>, as
insertions and deletions are (Tk's text widget records neither tags
nor, of course, blocks).  The undo reverses each of them, the redo
does it again:

=over 5

=item *

C<block split>: the undo deletes the separator the split put in; the
deletion joins the two leaves, and the nodes the split cut, up to
their common ancestor (see L<Deletion of text in blocks>); levels the
split added above the root are taken away again (as C<block trim>
would).  Outside blocks the split put in a newline, which the undo
deletes.

=item *

C<block insert>: the undo dissolves the new block by deleting its head
(see L<Destruction of blocks>): its contents come back where they
were, with their tags, marks and nested blocks.  The values of the
leaves the block insert moved whole into the block go back to those
leaves, the joins and merges it made are undone (see L<Node values and
editing>), and its instance data (C<block data>) and the values of its
own nodes are kept in the undo step for the redo.  If the range of the
block insert crossed nodes of an enclosing block (see C<block insert>
in L<Block subcommands>), the undo also gives every separator of the
range, and the one after it, the level it had, so that the nodes of
the enclosing block are those before the block insert, and the values
of the nodes block insert emptied, or left on the end side, come back
to them; in a tree whose leaves are at different depths (see L<Ragged
trees>) the leaves of the range get back their depths too.  No text
moves for that, and the undo is one step, as always.

=item *

C<block trim>: the undo adds the root again, with the value it had.

=item *

C<block flatten>: the undo does the steps back in reverse order (each
separator deleted comes back with the nodes it joined, each node
pulled out gets its leaf and value back); the tree and the values are
exactly those before the flatten.  The redo flattens again.

=item *

C<block sprout> (either form): the undo takes the new node out again
(the middle leaf takes its value, if it has one), then deletes the separators the
sprout put in (the start piece keeps its value, those of the middle
and end pieces go into the undo step); the tree and the values are
exactly those before the sprout.  The redo sprouts again, and gives
back the values the undo took.

=item *

A deletion that joined two leaves of different depths (see L<Ragged
trees>): the undo puts the text back with its structure (every leaf
at its depth), gives the values back, and then takes out again, in
reverse order, the nodes the deletion gave the shallower leaf before
joining; the tree and the values are exactly those before the
deletion (C<C( a | B( y | z ) )> again in the example of L<Ragged
trees>).  A value set on such a node after the deletion goes into the
undo step meanwhile, and comes back with the redo, which joins as the
deletion did.

=item *

C<block level>: the undo gives the separator the depth it had, takes
away the levels a higher depth added below the root, and gives back
the values a lower depth dropped or moved; the redo changes the depth
again.

=item *

C<block cut>: undone and redone as a deletion; the redo joins by the
rule of C<block cut> again.  C<block paste>: the undo deletes the
range the paste filled, by the same rule, and then takes away the
levels the paste added below the root (and, in a block that was a
single leaf, makes the root padding again); the redo inserts what the
undo deleted, as for any insertion, with the values.  With
C<-autoseparators> each is a step of its own.

=item *

C<tag add> and C<tag remove> over a range: the undo gives the tag in
that range exactly the ranges it had there before, the run values
included (a run that tag add extended keeps its value on the part that
remains, the values of the runs it merged come back).  Changes of the
tag C<sel> (the selection) are not recorded, nor are those that change
nothing (adding a tag where it is all over the range, removing it
where it is nowhere).

=back

A redo checks again what the command checks: if the change cannot be
made again (the block type of a C<block insert> was deleted, or made
C<-empty> while the range is not empty; the block a C<block trim>
worked on is gone or cannot be trimmed), the redo does nothing, and
the values its undo step keeps are freed when the step is discarded.

What these changes drop goes into their undo step as for deletions
(see L<Undo and redo>): the losers of joins and merges, the nodes
block insert empties, a root block trim drops, the runs tag remove
removes; the undo gives them back, the redo takes them again.

Each of these changes is a kind of edit of its own for
C<-autoseparators>, as insertions and deletions are: following Tk's
rule, a separator goes into the undo history when a change is of
another kind than the last one, so that a run of changes of the same
kind (several C<tag add> in a row, as typing is a run of insertions)
is one undo step, and a change of another kind starts a new one
(C<tag add> and C<tag remove> are two kinds, as insertion and deletion
are; C<block sprout>, C<block flatten> and C<block level> are kinds of
their own).  To make one step of several changes of different kinds, use
an edit step (see L<Several changes as one undo step>).  A
program that uses tags for display only (highlighting found text, say)
can switch C<-undo> off around those calls: tags do not move text, so
the history stays valid.  These changes also count for C<edit
modified>, as insertions and deletions do, with C<-undo> off too
(but for those of C<sel> and those that change nothing); a program
that highlights can keep the flag with C<edit modified> around the
calls.

Not recorded (so not undone, and what they drop is freed when they
return): C<tag delete>, C<tag configure>, C<mark set>, C<mark unset>,
C<block delete>, C<block configure>, and, outside an edit step, the
setting of values (C<block data>, C<block nodedata>, C<mark data>,
C<tag data>).

=head2 Several changes as one undo step

One edit of the user is often several commands: a block is made with
C<block insert>, then gets its instance data, its separators and the
values of its nodes; a selection is replaced by a deletion and an
insertion; two pieces are exchanged by two cuts and two pastes.  With
C<-autoseparators> each change of another kind is an undo step, and a
value set is not recorded at all.

  .t edit step begin
  ...
  .t edit step end

makes one undo step of everything between the two: C<edit undo> takes
all of it back, C<edit redo> does all of it again.  Between them

=over 5

=item *

no separator goes into the undo history: C<-autoseparators> puts none,
and C<edit separator> does nothing;

=item *

the setting of a value (C<block nodedata>, C<tag data>, C<mark data>,
C<block data>) is recorded, with C<-undo> on: the value the place had
goes into the undo step instead of being freed, the undo gives it back
and takes the value that was set into the step, and the redo
exchanges them again.  A set that changes nothing (no value there and
none given) is not recorded.

=back

Steps nest: C<edit step begin> inside a step only counts, and the
C<edit step end> that matches the first C<begin> ends the undo step.
C<edit step begin> and C<edit step end> return the number of steps
open then, and so does C<edit step> alone; C<edit step end> with no
step open is an error.  The change after a step starts a step of its
own.  A program must not leave a step open: until its C<end> all
changes are one undo step.  In Perl the method C<editStep> takes care
of that:

  $text->editStep(sub {
    $text->blockInsert('Fraction', '2.1', '2.3');
    $text->blockSplit('2.3', 0);
    $text->blockData('2.2', $data);
    $text->blockNodedata('2.2', 1, $value);
  });

runs the code inside a step, ends the step also when the code dies
(the error is passed on), and returns what the code returns.

The C<-valuecommand> callback is told C<stash> for the value a
recorded set replaces (C<drop> for an unrecorded one), then C<stash>
and C<restore> as the undo and the redo exchange the two values, and
C<discard> for the one the step holds when the step is discarded.

=head1 Values

A Perl scalar can be kept with every node of the tree of a block (the
leaves included), with every mark and with every run of a tag:

  .t block nodedata index level ?value?
  .t mark data markName ?value?
  .t tag data tagName index ?value?

In Perl these are C<< $t->blockNodedata($index, $level, ?$value?) >>,
C<< $t->markData($name, ?$value?) >> and C<< $t->tagData($tag, $index,
?$value?) >>.  Without a value they return the value, or C<undef> if
there is none; with a value they set it, and setting C<undef> removes
the value.  The values are data only: the display does not depend on
them (setting a node value does not redisplay the block, and the
layout callback does not receive node values), and C<dump> reports
those of marks and runs only with C<-values> (see L<The dump
subcommand>).  They stay with their node, mark or run through edits,
come back with undo, and are freed at the moments listed in L<When
values are freed>.

=head2 Which node, which run

The position given to C<block nodedata> names a leaf of the innermost
block it is inside:

=over 5

=item *

a character of a leaf (or a block nested in it, or an I<empty> block,
which occupies one index unit of the leaf) names that leaf;

=item *

an interleaf separator, and the tail of the block, name the leaf
before them;

=item *

the head of a block belongs to the enclosing structure, as for
insertion (see L<Insertion in blocks>): it names a leaf of the
enclosing block, and is an error outside of blocks.

=back

An empty block has no leaves, hence no node values.  A position
outside of every block is an error (C<bad index "2.0": not inside a
block>).

The I<level> picks the leaf (0) or one of its ancestors: 1 is the
parent of the leaf, 2 the parent of that node, and so on.  A negative
level counts down from the root: -1 is the root, -2 the child of the
root on the way to the leaf, and so on.  A node is reached from every
position in it, the root from every position in the block.  A level
beyond the root, or a negative level below the leaf, is an error,
which gives the number of levels above that leaf.  The levels are
those of the leaf the position names: in a ragged tree (see L<Ragged
trees>) the same node can have different levels from different
leaves, and the padding the widget keeps is never counted.  In
C<R( x | S( 2 | 3 ) )> on line 2 (C<x> 2.1, C<2> 2.3, C<3> 2.5),
C<nodedata 2.1 1> and C<nodedata 2.3 2> both name the root, which is
C<nodedata 2.1 -1> and C<nodedata 2.5 -1> too, and C<nodedata 2.1 2>
is an error ("... has 1 level above this leaf").  In a block that is a
single leaf, level 0 and level -1 both name the leaf.
With a fraction C<{num|den}> on line 2 (head 2.0, C<num> 2.1-2.3, the
separator 2.4, C<den> 2.5-2.7, the tail 2.8):

  .t block nodedata 2.2 0 N	;# the leaf num
  .t block nodedata 2.4 0	;# N: the separator names num
  .t block nodedata 2.8 0	;# the tail names den: nothing
  .t block nodedata 2.6 -1 R	;# the root (level 1 here)
  .t block nodedata 2.2 -2	;# N: down from the root, the leaf
  .t block nodedata 2.0 0	;# bad index "2.0": not inside a block
  .t block nodedata 2.2 2	;# bad level "2": the block containing
				;#   2.2 has 1 level above this leaf

A I<run> of a tag is a maximal stretch of characters carrying it.  It
continues over line ends, interleaf separators, and heads and tails
of blocks: a run that covers a block contains it.  C<tag data> names
the run of the character at the position; every character of the run
names the same run.

=head2 Copies

The widget keeps a copy of the scalar it is given, as C<block data>
does, and reading returns a copy; the elements of C<block list> hold
copies too.  A reference is copied as a reference: an object given as
a value stays alive as long as the widget keeps the value.  So
I<freeing> a value below means that the widget drops its copy; an
object is destroyed (and its C<DESTROY> method runs) when its last
reference goes.

=head2 Node values and editing

The values live in the tree, so they move with the text.

=over 5

=item *

Insertion inside a leaf does not change values.  A newline inserted in
a leaf (or C<block split> at level 0) splits it: the first part keeps
the value, the new leaf starts without one.  C<block split> at a
higher level does the same on each level: the node before the cut
keeps its value, the new node after it starts without one (in a leaf
with padding, see L<Ragged trees>, the lowest levels cut only
padding, which holds no values).  Where the level reaches the root,
it first inserts a new node between the root and all its children
(one for each level missing): the root stays the root and keeps its
value, the new node starts without one and is then cut as any other
node.

=item *

A leaf whose text becomes empty keeps its value.

=item *

A deletion deletes a leaf, value and all, if the range holds all of
its text together with the separator before it (the separator or tail
after it need not be in the range), and a node if it holds all of its
leaves in this way.  Otherwise the leaf where the range starts and the
leaf where it ends are joined, and if they have different parents,
their ancestors are joined on each level up to the common ancestor
(see L<Deletion of text in blocks>); if one of the two is less deep
below the common ancestor than the other, it is first given new nodes
above it, without values, until both are equally deep (the new node
next to a node of the other side then takes that node's value by the
rule that follows).  On each level the joined node
keeps the value of the node on the start side if it has one, else it
takes the value of the node on the end side; the other value is freed.
The starting leaf always survives a join, even when all of its text is
in the range: in C<{num|mid|den}>, deleting C<mid|> keeps the value of
C<mid> on the joined leaf (the inverse of inserting C<mid> and a
newline at the start of C<den>), while deleting C<|mid> deletes the
leaf C<mid> with its value.  The last of a block's nodes directly
above the leaves also holds the block's tail, so a deletion never
removes it whole (nor its ancestors below the root, which hold the
tail too): when all its leaves are deleted, it is joined to the node
before it, and its value follows the rule for joined nodes: it moves
to that node if that node has no value, and is dropped otherwise.

=item *

C<block level> changes the depth of a separator without joining the
two leaves beside it: they keep their values.  A higher depth cuts
nodes as C<block split> does (the part before the cut keeps the
value); a lower depth joins nodes by the rule of a deletion (the
start side's value, else the end side's).

=item *

C<block cut> deletes in the same way, but a joined leaf or node never
takes the value of the end side: it keeps what the start side had,
and the end side's value leaves with the list C<block cut> returns
(see L<Cut and paste with structure>).  C<block paste> gives the
leaves and nodes it makes the values its list has for them.

=item *

A deletion that deletes a block deletes all of its node values; one
that dissolves it (it holds its head or tail, see L<Destruction of
blocks>) frees all of its node values too, the values of the leaves
whose contents join the enclosing structure included.  The values in
blocks nested in what is left stay with those blocks.

=item *

C<block trim> removes the root: the new root (its only child) keeps
the value of the old root if it had one, else its own; the other value
is freed.

=item *

C<block sprout> shares the value of the former leaf between the start
piece, the new node and the end piece (with one index, or a range from
delimiter to delimiter, the value moves to the new node); the middle
leaf has none.  C<block flatten> keeps, on each join, the start side's
value (else the end side's), and on each pull out the node's value
(else the leaf's); the others are freed (kept in the undo step).
I<(Temporary choices, see F<BUGS> 28.)>

=item *

C<block insert> inside a block moves leaves into the new block.  A
leaf moved whole keeps its value as a leaf of the new block (a first
leaf with nothing before I<index1>, and a last leaf with nothing after
I<index2> but its separator, move whole).  Where I<index1> or
I<index2> cuts a leaf, the part left in the enclosing block keeps the
value and the moved part starts without one; the two parts left on
both sides of the new block are one leaf, which keeps the value of the
first if it has one, else takes the value of the second, the other
being freed.  Nodes of the enclosing block left without leaves
disappear, with their values.

=back

The I<instance data> of a block (C<block data>) is freed with the
block, under the same rule as the values (L<When values are freed>).

=head2 Run values and editing

=over 5

=item *

When runs become one (C<tag add> over the gap between them, a deletion
of the gap, a deletion of the head of a block between them), the run
keeps the value of the leftmost of them that has one; the other values
are freed.  A run whose text is all deleted takes no part.

=item *

A run shortened at either end (by C<tag remove> or a deletion)
keeps its value.  A run cut in two (by C<tag remove> in its middle, or
by text inserted with a list of tags that lacks the tag) leaves the
value on the left part; the right part starts without one.  A run
extended by C<tag add> keeps its value.

=item *

Text inserted inside a run without a list of tags, a newline included,
is in the run (the inserted text takes the tags present on both sides,
as in Tk); text inserted at the start or the end of a run is not.
C<block split> and C<block insert> inside a run do not cut it;
C<block insert> at the start of a run puts the start of the run, value
and all, inside the new block.

=item *

A run whose text is all deleted, or which C<tag remove> covers
entirely, is gone with its value.  C<tag delete> frees the values of
all the runs of the tag.

=back

=head2 Mark values

The value stays with the mark when it moves: C<mark set> on an
existing mark, C<mark gravity>, edits (a deletion moves the marks of
its range to its start), undo putting the mark back.  Edits never
remove a mark, so they never free its value.  A mark set anew after
C<mark unset>, also one re-created by an undo, starts without a value.
The marks C<insert> and C<current> can have values too (C<mark unset>
ignores them, as before).  C<block list> shows a mark with a value as
C<[name, value]> (see L<What else is in the widget?>).

=head2 When values are freed

A node value is freed when it is replaced (or set to C<undef>), when
its node is deleted, when its block is deleted or dissolved, when it
loses a join (deletion, C<block insert>), when C<block trim> drops it,
when C<block insert> empties its node, and when the widget is
destroyed.  A mark value is freed when it is replaced (or set to
C<undef>), when C<mark unset> removes the mark, and when the widget is
destroyed.  A run value is freed when it is replaced (or set to
C<undef>), when all the text of the run is deleted, when C<tag remove>
covers the whole run, when C<tag delete> removes the tag, when it
loses a merge, and when the widget is destroyed.  With C<-undo> on,
the edits that can be undone (insertions, deletions, C<block insert>,
C<block split>, C<block trim>, C<tag add>, C<tag remove>) do not free
what they drop: it is kept by their undo step (L<Undo and redo>), and
freed when the step is discarded.  Nothing
else frees a value: in particular, setting other values, tag
configuration, moves of marks and unrelated edits do not.

Freeing a value can run Perl code (a C<DESTROY> method), so a value is
never freed in the middle of a change: the values that a widget
command drops are freed, in order, when that command returns (a Perl
method or a binding that makes several widget calls frees after each
of them).  A C<DESTROY> method may thus read the widget, and sees it
as it is after the change: when a deletion of line 2 frees a value,
the C<DESTROY> method sees the index C<end> one line up already.  It
may change the widget too (see below); to know where the value was
attached before it was detached, use C<-valuecommand> (see L<Telling
the program: -valuecommand>).  When the widget is destroyed,
its remaining values (those in the undo history included) are freed
after it is gone, and a C<DESTROY> method that calls it gets the
usual error for a destroyed widget.

B<Changes made from a C<DESTROY> method.>  While the values a command
dropped are being freed, a C<DESTROY> method may change the widget.
Such a change is an undo step of its own: it does not merge into the
step of the command that dropped the value, nor into the next change.
The values it drops join the values being freed and are freed in the
same pass, after those already waiting (so still before the Perl
method that made the first command returns).  The values are freed in
rounds: those the command dropped in round 1, those dropped by changes
made from their C<DESTROY> methods in round 2, and so on.  A chain of
such changes (a value freed by a change made from a C<DESTROY> method,
whose own C<DESTROY> method changes the widget, and so on) has a
limit, 10 to begin with: a change in the round of the limit is refused
with the error C<cannot modify .t while its values are being freed, 10
changes deep>, unless the object making it asks for more rounds (see
below).  So a chain of 9 changes, in rounds 1 to 9, is always made.
(2.04 refused every change while values were being freed, a stopgap
until the program could learn where a value was before it was
detached.)

B<More rounds: DESTROYmult.>  When a change from a C<DESTROY> method
is about to be made in the round of the limit, the widget asks the
object whose C<DESTROY> method is attempting it, calling, in scalar
context,

  $more = $object->DESTROYmult($n, $limit);

C<$n> is 1 for the first such request of this freeing pass, 2 for the
next, and so on; C<$limit> is the current limit.  If C<$more> is a
positive integer, the limit becomes C<$limit + $more> and the change
is made; the next time the chain reaches the new limit, the widget
calls C<DESTROYmult($n + 1, $limit + $more)>.  A method that always
answers 5 is thus called with (1, 10), (2, 15), (3, 20) and so on.
Other changes in a round below the raised limit are made without
asking.  The change is refused as above, with the error naming the
current limit (C<cannot modify .t while its values are being freed, 15
changes deep> once it was raised by 5), if

=over 5

=item *

the answer is 0, C<undef>, negative, not a number, or not an integer;

=item *

there is no object to ask (see below), or it is not a blessed object;

=item *

the object cannot C<DESTROYmult> (C<< !$object->can('DESTROYmult') >>;
an inherited method, or one that C<can> reports, will do);

=item *

C<DESTROYmult> (or C<can>) dies: its error is reported as a background
error (C<Tk::Error>), as those of the C<-valuecommand> callback are,
and the answer counts as 0.

=back

A change that C<DESTROYmult> itself attempts is refused, without
asking again.  The limit and the count of requests belong to one
freeing pass, that is to one outermost widget command (a command made
by Perl code that the freeing runs is part of the pass): the next
command starts again with the limit 10 and request 1.  The call leaves
C<$@> as it was; C<DESTROYmult> should not keep a reference to its
object (it is being destroyed).

B<Which object is asked.>  The object whose C<DESTROY> method is the
innermost one running when the change is attempted, that is the
C<DESTROY> method that makes the change, itself or through the
subroutines it calls.  When a value is an object whose own C<DESTROY>
makes the change, that is the value.  When the change is made by the
C<DESTROY> method of an object held inside the value being freed (in
an unblessed array or hash that is the value, or in a field of an
object that is the value), that inner object is asked, not the value:
its method is the one that knows what its change needs, and an
unblessed value could not be asked at all.  Perl calls an object's
C<DESTROY> method before it frees what the object holds, so an object
held by the value is usually destroyed after the value's C<DESTROY>
has returned; if the value's C<DESTROY> frees it itself (C<< delete
$self->{child} >>), both are running, and the inner one is asked.  The
object is found as C<caller> finds the arguments of a call (in
C<@DB::args>): the first argument of the innermost C<DESTROY> method
written in Perl, also when the method has shifted it.  A C<DESTROY>
method that has replaced its C<@_> leaves nothing to ask.

B<Commands refused while the -valuecommand runs.>  While the callback
of C<-valuecommand> runs, the widget refuses the commands that would
modify it, with the error C<cannot modify .t while its -valuecommand
runs>: the command that called it has not made its change yet.
Reading commands, and those that only change the view, work as usual.
The rule: a command that would change something, or create a tag or a
block type, is refused; a query of an existing one is not.  The
commands refused are:

=over 5

=item *

C<insert>, C<delete>, and C<configure> with options to set;

=item *

C<tag add>, C<tag remove>, C<tag delete>, C<tag raise>, C<tag
lower>, C<tag data> when it sets something, and C<tag configure> and
C<tag bind> when they set something or name a tag that does not exist
(a query would create it);

=item *

C<mark set>, C<mark unset>, and C<mark gravity> and C<mark data> when
they set something;

=item *

C<block insert>, C<block split>, C<block trim>, C<block delete>,
C<block configure> when it sets something or names a block type that
does not exist (a query would create it),
C<block addline>, C<block deletelines>, and C<block data> and C<block
nodedata> when they set something;

=item *

C<image create>, C<window create>, and C<image configure> and C<window
configure> with options to set;

=item *

C<edit undo>, C<edit redo>, C<edit reset>, C<edit separator>, and
C<edit modified> with a value.

=back

Everything else works: C<get>, C<index>, C<compare>, C<dump>,
C<search>, C<bbox>, C<dlineinfo>, the queries of C<tag>, C<mark>,
C<block>, C<image>, C<window>, C<edit> and C<configure>, C<cget>,
C<see>, C<xview>, C<yview>, C<scan> and C<debug>.

=head2 Undo and redo

With C<-undo> on, a deletion does not free the values it drops (of
deleted nodes and runs, of the blocks it deletes or dissolves, their
instance data included, the losers of joins and merges): they go into
its undo step, each with an address that is valid again once the
deletion is undone (where the node's first leaf or the run starts,
the node's level, the tag's name; where a block's head is, for its
instance data).  C<edit undo> re-creates the text (the blocks with
their depth, and the runs as separate runs again), then gives every
value back to the node, run or block at its address, and moves back
the values a join moved.  C<edit redo> takes them into the step again.  The undo of
an insertion and its redo do the same.  A value the undo finds on the
node or run it gives a value back to (one set after the edit, or of a
run made since and merged with the restored one) is not freed either:
it waits in the step, and the redo gives it back.  So does a value
set after a deletion on a leaf made of what was left of a block the
deletion dissolved, also when that block was nested in another one:
the undo re-creates the block, and the value waits in the step with
the place the leaf has in the text without the deleted range, where
the redo gives it back (eText/BUGS 26, 31).  If the undo finds no node
at an address otherwise, the value is freed.

The values in an undo step are freed when the step is discarded: by
C<edit reset>, when the history grows beyond C<-maxundo> steps, when
a new edit after an undo drops the steps that could have been redone,
and when the widget is destroyed.

Marks need no records: the undo moves an existing mark back with its
value.  C<block insert>, C<block split>, C<block trim>, C<tag add> and
C<tag remove> keep what they drop in their undo steps in the same way
(see L<Undo and redo of block and tag changes>).  C<tag delete>,
C<mark unset> and the setting of values are not undoable, so the
values they drop are freed when they return; but a value set inside
an edit step is recorded, and the value it replaces waits in the undo
step (see L<Several changes as one undo step>).

The redo of an insertion re-inserts it exactly: when the insertion is
undone, the inserted range is recorded in block-list form, as a
deletion records what it deletes (at that moment the range is as the
insertion left it, the later recorded changes having been undone),
and the redo inserts that list (Tk 8.4 re-inserts the plain string).
So the text comes back with the tags it was inserted with (not those
of the text around it), with the separators it made in a block, and
with the marks that were in it when it was undone; then the values
come back to its runs and nodes.  If the recorded indices have become
stale (changes made with C<-undo> off) and the range cuts blocks, the
redo inserts the plain string.

The undo keeps its own records of the values; its own block list of
the deleted text leaves them out (the instance data of blocks
included, and those of marks, which the undo never needs: it moves an
existing mark back with its value), so that it holds no extra
reference to them.  A program re-creating text from the elements of C<block
list> sets no values unless it does so itself; C<block paste> sets
those its list has (see L<Cut and paste with structure>).

=head2 Telling the program: -valuecommand

With the option C<-valuecommand>, the widget tells the program, before
a change is made, which values the change will detach and where they
are, while the widget is not changed yet (and, provisionally, which
nodes it will create without a value, C<new>); and afterwards which values
an undo or a redo gave back and which a discarded undo step frees.
For most commands this is before the command changes anything; the
commands that make several changes in a row tell before each of them
(see the note "Postponed" below).  The callback is called as

  $cb->($widget, $event, $kind, $where, $value, $cause)

with C<$value> the value (as C<block nodedata> and the others return
it), and:

=over 5

=item C<$kind> and C<$where>

The owner of the value and its place, an array reference:

  node    [index, level]       blockNodedata(@$where) returns the value
  run     [tag, start, end]    tagData(tag, start) returns it
  mark    [name, index]        markData(name) returns it
  block   [index]              the head of the block (block data)

A node (the leaves included) is named by the position where its first
leaf starts and its level counted from that leaf (0 for a leaf), as
in L<Undo and redo>: C<blockNodedata(@$where)> returns the value
whatever the depths of the other leaves (see L<Ragged trees>).  A block is named by its head; C<block data> at
the head returns the value for an I<empty> block, and for another
block at a position inside it that is not inside a block nested in it
(its tail, for one).

=item C<$event>

=over 5

=item C<drop>

before the change: the value is detached and freed when the command
ends;

=item C<stash>

before the change: the value goes into the undo step of the change
(C<-undo> on), or, for a value that an undo or a redo finds where it
gives another back, into the step it applies;

=item C<move>

before the change: a merge (of two leaves, nodes or runs that become
one) gives the value to another owner.  The last element of C<$where>
is an array reference naming the new owner, in the same form, as it
is before the change: C<[index, level]> or C<[tag, start, end]>;

=item C<restore>

an undo or a redo gave the value back: called once it is back (before
the rest of the command), with its place then;

=item C<discard>

an undo step that held the value was thrown away (C<edit reset>,
C<-maxundo>, a new change dropping the steps that could be redone), or
an undo or a redo found no place for it: called at the end of the
command, just before the value is freed, with the place the step
recorded, which may not exist any more (a run's is C<[tag, start]>, a
position on a line that is gone is given as recorded);

=item C<copy>

I<(Temporary.)> before C<block sprout> puts the value of a leaf on
another owner too (the new node, the end piece): the value is shared,
nothing is detached.  C<$where> is the place of the value, and its
last element names the receiving owner as it is I<after> the change.

=item C<new>

I<(Provisional, decision O5.)> before the change: the change will
create a node or a leaf without a value; C<$where> is the place it
will have I<after> the change, C<[index, level]> (the level counted
from the node's first leaf, as for the other events), and C<$value>
is C<undef>.  Told once for each such node or leaf: the new leaf of a
newline typed in a block (or of C<block split>), the second halves of
the nodes C<block split> cuts and the nodes it adds (see below), the
root and the leaves of a new block (C<block insert>) and the leaf of
the enclosing block left when a whole leaf moves into the new block,
the leaves that the separators of a block a deletion dissolves make
in the block around it, the new node and the pieces of C<block
sprout> that do not receive a copy of the former leaf's value (its
middle leaf always), the nodes a deletion gives the shallower of two
leaves before joining them, and the root of a block that was a single
leaf and gets a second one.  Nodes and leaves that an undo or a redo
re-creates are not told (they get back the values they had,
C<restore>), nor is the disappearance of a node without a value: a
program that wants to follow every node can set a value on each node
it is told about.  With C<{num|den}> on line 2, the value C<R> on the
root and C<N> on C<num>:

  .t block split 2.2 1    ;# R( X( n ) | Y( um | den ) )

The split reaches the root, so it first inserts a new node C<R1>
between the root C<R> and all its children; C<R> stays the root and
keeps its value, but its address grows by one level, since a node was
inserted below it (as for a wrap, see C<block sprout>); then C<R1> is
split into C<X( n )> and C<Y( um | den )>.  This tells C<new> three
times, before the change: C<R1> (that is, C<X>) at C<[2.1 1]>, C<Y> at
C<[2.3 1]> and the leaf C<um> at C<[2.3 0]>; then the value C<R> is
told C<move> from C<[2.1 1]> to C<[2.1 2]> as C<R1> is inserted below
it.  C<blockNodedata(@$where)> after the
change names the node, unless a later step of the same command gives
it a value (a deletion's join, telling C<move> to that place).  The
ready-made C<DETACH> callback passes C<new> on to no value (there is
none).

=item C<late>

a value was detached that the widget did not foresee: called at the
end of the command, after the change, with the place the value had
before it if the widget knows it, else C<$where> is C<undef>.  This
should not happen.  With C<debug> on, the command fails then (as when
a detach was foreseen but did not happen as told), so that tests catch
it.

=back

=item C<$cause>

The command: C<delete>, C<insert>, C<tag add>, C<tag remove>, C<tag
delete>, C<block insert>, C<block trim>, C<block split>, C<block sprout>,
C<block flatten>, C<block cut>, C<block paste>, C<block level>, C<undo>,
C<redo>, C<reset> (C<edit reset>), C<separator> (C<edit separator>),
C<configure> (C<-maxundo>); C<set> for the commands that set a value
(C<block nodedata>, C<tag data>, C<mark data>, C<block data>, undef
included) and C<unset> for C<mark unset>.

=back

The calls before a change are made once the command has checked its
arguments, before it changes anything, for a command that makes one
change.

I<(Temporary.)> In a tree whose leaves are at different depths, the
steps of C<block sprout>, and of a deletion that joins leaves of
different depths, are told each just before it is made: giving a leaf
a node above it changes the address of the nodes above the leaf of
which it is the first leaf (their level grows by one), told as
C<move> with the new place as it is I<after> the change; taking such a
node out again (the undo of C<block sprout>, or of such a deletion,
after the values have come back) the same way back; the
value of a leaf that moves to the node made above it is a C<move>;
the copies are told C<copy>; the separators C<block sprout> puts in
are told nothing, as for C<block split>.  C<block flatten> tells each
of its steps just before it is made: a join as a deletion's join
(C<move>, C<drop> or C<stash>), a pull out as C<move> of the node's
value to the leaf, C<drop> or C<stash> of the leaf's own if both have
one, and C<move> of the nodes above whose address changes (their
level shrinks by one).  The nodes these steps create without a value
are told C<new> (see above): C<block sprout> tells them all before its
first step, with their places after the command; a deletion tells the
nodes it gives the start leaf before giving them, with their places
once all are made (the join then keeps them; those it gives the end
leaf are merged into the start side's at once and are not told).
Nothing is told when a root becomes padding again (the undo of these
commands, C<block flatten> at the root).

B<Postponed: telling everything before a command that makes several
changes starts; today these commands tell before each of their
changes.>  The approved design said that the program is told before
the command changes anything.  For the commands that make several
changes in a row, the widget tells before I<each> change instead, the
widget being as the previous change left it (so a C<$where> names the
place at that moment, not before the command).  These commands are:

=over 5

=item *

C<edit undo> and C<edit redo>, which apply the recorded changes of a
step one by one: each is told just before it is applied;

=item *

C<insert> with lists of tags (C<insert index chars tagList ?chars
tagList ...?>): each piece is inserted, then the tags it got from the
text around it are taken off and those of its list put on, one tag
after the other, and each of these is told just before it is made;

=item *

C<tag add> and C<tag remove> with several ranges: each range is told
before it is tagged or untagged;

=item *

a deletion through the end of the text, which first takes the tags
off the final newline (told then), and then deletes (told then);

=item *

C<block flatten>, C<block sprout>, and a deletion that joins leaves of
different depths (see above): each step is told just before it is
made.

=back

Also, a value that an undo or a redo displaces (one it finds where it
gives another back, L<Undo and redo>) is told (C<stash>) just before
it moves, and C<restore> comes as soon as a value is back, not at the
end of the command.  The owner postponed the question whether to tell
everything at the start of such commands (which would need the
look-ahead of all their changes from the widget as it is before the
first); see F<BUGS> 27.

While the callback runs, the widget can be read but not changed: the
commands listed in L<When values are freed> are refused, with the
error C<cannot modify .t while its -valuecommand runs>.  (A
C<DESTROY> method, which runs once the change is made, may change the
widget.)  The callback
cannot refuse the change.  An error in the callback is reported as a
background error (C<Tk::Error>) and the command goes on (see L<When
Perl code called by the widget dies>).  The callback should not
destroy the widget.

Nothing is told when the widget is destroyed (its values are freed
then, see L<When values are freed>), nor about values that have no
Perl part (in a widget built with representation B, a container that
holds only other slots).  Without the option nothing of this runs: no
look-ahead, no table.

B<The ready-made callback.>  With

  $t->configure(-valuecommand => 'DETACH');

the widget calls its method C<DETACH> (a callback given as a string is
a method of the widget), which passes the notification on to values
that are objects with a C<DETACH> method of their own:

  $value->DETACH($widget, $event, $kind, $where, $cause)

at the same moments as above; other values (plain scalars, objects
without such a method) are skipped.  A subclass of Tk::eText may
define its own C<DETACH> (and call C<< $w->SUPER::DETACH(...) >> to
pass the values on).  As with any C<-valuecommand>, the commands then
do the look-ahead; an error in a C<DETACH> method is a background
error.

=head2 When Perl code called by the widget dies

The widget runs Perl code at three places that may die: the
C<DESTROY> methods of the values it frees, the C<-valuecommand>
callback (or, with C<< -valuecommand => 'DETACH' >>, the C<DETACH>
methods of the values) and C<DESTROYmult>.  None of these errors
stops the widget command that ran the code, and none of them makes a
value freed twice or kept for ever:

=over 5

=item A C<DESTROY> method dies

Perl does not let an error leave a C<DESTROY> method: it makes it the
warning C<(in cleanup)> I<message>, with a tab before it (category
C<misc>), given only if warnings are on where the error is raised
(C<use warnings> there, or C<perl -w>); otherwise the error is lost.
The value is freed all the
same, the other values waiting are freed after it, and the widget
command that dropped them returns normally, with its usual result.  A
change the method made before it died stays made, as an undo step of
its own.

=item A change refused inside a C<DESTROY> method

The refusal (C<cannot modify .t while its values are being freed, 10
changes deep>, see L<When values are freed>) is an error raised inside
the C<DESTROY> method, so it is the case above: unless it is caught,
it becomes an "(in cleanup)" warning, and the values and the command
go on.  It is raised by the widget method, which Perl/Tk compiles in
F<Tk.pm> without C<use warnings>: if it leaves C<DESTROY> as it is,
the warning is given only under C<perl -w> (C<$^W>), and is lost
otherwise.  To know, catch it with C<eval> inside C<DESTROY>:

  sub DESTROY {
    my $self = shift;
    eval { $self->{widget}->insert('end', "gone\n"); 1 }
      or warn "not made: $@";
  }

=item The C<-valuecommand> callback dies, or a C<DETACH> method

The error is reported as a background error (C<Tk::Error>, called
when Tk is next idle), and the command goes on as if the callback had
returned: the change is made, and the values are freed, kept or given
back as usual, each once; nothing the callback was given is kept.
Each call that dies is one background error.  (Perl/Tk itself keeps
about half a kilobyte for each background error, whatever reported
it, a binding included; that memory is not the widget's.)

=item C<DESTROYmult> dies

A background error, and the answer counts as 0: the change is refused
(L<When values are freed>), and that refusal, raised inside a
C<DESTROY> method, is the case above.

=back

=head1 Additional text widget options

=over 10

=item C<-valuecommand>

A callback told before a command detaches values (or creates nodes
without values), see L<Telling the program: -valuecommand>; C<'DETACH'> passes the notification on to
values that are objects with a C<DETACH> method.  Empty (or undef) by
default.

=item C<-getFlags>

The value is an integer, binary bits of this integer denote current
I<text representation> options. If no bits are set, the operations
that consider text contents as a string behave like the standard Tk
text widget.

If bit C<1> is set, the string representation of a text range
I<always> gives a string of the same length as the length of the
interval in the index space. If some text annotation results in an
empty string in the standard representation, it is represented as an
appropriate number of C<*>s if this bit is set. Currently this
concerns embedded windows only, which are represented as C<*>.

All undocumented bits are reserved and should be 0; since 2.06 the
widget ignores them (before, some of them changed what the widget's
own extractions, C<block list> and the undo's records, contained).

=item C<-ornamentproportional>

A boolean (0 by default; new in 2.08, provisional).  The x of the
stand-in of a position of an ornament that is not displayed, and was
never displayed since the ornament got it: when set, proportional to
the position's offset in its text line (relative to the line's length)
across the width of the text area; else the middle of the text area.
See L<Ornaments>.

=back

=head1 Minitutorial

=head2 Example of a simple "pedestal" block

Suppose you are satisfied with the standard layout procedure, but want
to extend the resulting group of lines 10 points to the right (so when
part of block is selected, selection extends 10 points to the
right of the rightmost element in leaves), and want to add a blue
3D background of width 5 with "height" 2 around the resulting guy,
and draw the block on gray 3D background of width 2.

Note that it is not enough to use a tag even for gray background,
since the border of the tag is inside the rectangle that contains the
letter, and to get a correct pedestal look we want the border to
surround the letter, not to be drawn outside of them.

In what follows we use TCL as the language for callback. Of course,
the resulting code will be much simpler in some other languages.

First, we create the 2 new additional elements to display:

  .t tag configure backgr1 -background blue -border 2 -relief raised
  .t tag configure backgr2 -background gray90 -border 2 -relief raised
  .t insert 1.0 \n backgr1
  set backgrId1 [.t block addline 1.0]
  .t delete 1.0 1.0+1c
  .t insert 1.0 \n backgr2
  set backgrId2 [.t block addline 1.0]
  .t delete 1.0 1.0+1c

(or we could use existing ones, if possible). The third row creates a
row in the text widget that is empty, and has tag "backgr1". This row
will show the background only, and we will use it to show the raised
background behind the block. The fourth row memorizes the I<id> of this
additional line, and the fifth one returns the text in the widget to
its initial state. The line is not shown anymore, but the way to show
it is preserved in a safe place. The second element is created in the
same way.

Next, since we are satisfied with the way the leaves of the tree are
places on the screen (i.e., one under another), we do not want to be
concerned with internal structure of the block tree, so we ask the
widget to lie about internal structure of the tree:

  .t block config myBlock -layoutdepth 1 \
	-layoutwidths 1 -layoutcmd myLayoutCmd

Now the data given to C<myLayoutCmd> will be always the same, as if
the block consisted of one leaf only that is the direct child of the
root. So the arguments the C<myLayoutCmd> receives are the following
ones:

  proc myLayoutCmd {block x row} {
    global backgrId1 backgrId2
    set c [lindex $row 0]
    set w [lindex $row 2]
    set tw [lindex $row 3]
    set h [lindex $row 4]
    set b [lindex $row 5]

Now C<$c>, C<$w>, C<$tw>, C<$h>, C<$b> contain the count, width,
I<total width>, height and baseline of the contents of the block.
Next we extend the I<total width> of the row.

    set tw [expr $tw+10]
    set tw2 [expr $tw+4]
    set tw1 [expr $tw+10]

We will not replace the width of the row, so mouse events could be
directed to outside of the block if clicked in the extended area. (In
fact they won't, since we will extend the size of the ambient block.)
Next we calculated widths of additonal rows,

    set h2 [expr $h+4]
    set h1 [expr $h+10]
    set b2 [expr $b+2]
    set b1 [expr $b+5]

and their height and baselines. All is prepared now to layout the rows:

    set addrow1 [list $backgrId1 0 0 $tw1 $tw1 $h1 $b1]
    set addrow2 [list $backgrId2 3 3 $tw2 $tw2 $h2 $b2]

Note that the same list $addrow1 is good for specifying the size of the
total block, since the first element of the list (that is $backgrId)
is ignored in the information for the whole block. Now we need to
move the real contents of the block 5 points to the right and down
with  respect to the rectangle occupied by the
block, and return the calculated information:

    set row [list $c 5 5 $w $tw $h $b]
    return [list $addrow1 $row $addrow1 $addrow2]
  }

Note that it is vital to put addrow2 after addrow1, since it should be
drawn after the addrow1 for it to appear to be on top of addrow1.

That's all! Now you can create a binding for insertion of empty block
into the widget (this binding supposes that C<bindtags> are reverted):

  bind .text <Control-Meta-m> {
    %W block insert myBlock insert
    %W mark set index index-1c
    break
  }

This binding moves the insertion point inside the block, so you are
ready to fill block with whatever information you need.

Sample code in the distribution of extended text widget
provides other examples of blocks: superSub, Fraction, and so on.

=head2 Example of a simple "tabulation" block

Here we describe how to code blocks that contain no editable
information, but provide geometry management. Consider an example of
tabulation: if we implement tabulation as a block, the size of this
block should change depending on the position of the start, but the
only editing operation should be the deletion of the block as a whole.

While it is possible to implement this kind of block using the same
types of blocks as in the previous section, we will need a lot of code
change in the bindings if we use this approach: a usual block takes at
least 2 positions in the index space, so it is possible to make an
insertion inside this block. Thus we either need correction of
keybindings that move the insertion point, or should correct the the
insertion code to check whether the insertion happens inside a block
of this type. If we do not do this, we need additional decision how to
handle blocks of this type that have not-empty contents.

The solution is to use "empty" blocks that take only 1 position in the
index space, so it is impossible to insert text inside them. We make
block type empty by using configuration option C<-empty>:

  .t block configure Tab -empty on -layoutcmd {layoutTab 5 35}

Note the spaces in the name of layoutcmd: No quoting is performed
during the call, so C<5> and C<35> become first two arguments of
C<layoutTab> procedure. This procedure can be as simple as follows:

  proc layoutTab {min mult block x} {
    global backgrId2
    set w [expr $min + $mult - ($x + $min - 1) % $mult - 1]
    set totblock [list $backgrId2 0 0 $w $w 5 3]
    return [list $totblock $totblock]
  }

The only "working" row is the C<set w> one. It calculates the width
of the block using the following rule: 

=over 5

=item

the width is at least $min, and the right end is on the position that
is proportional to $mult counting from the left of the line.

=back

The last row returns a list of length 2. The first element is the
description of the block as a whole, the next one is necesssarily the
description of an additional element (since there are no "regular"
leaves in the tree). This additional element is the same size as the
block itself, and is used only to provide some visual feedback. We use
I<id> $backgrId2 created elsewhere (say, by the code in the previous
example), and ask for the rectangle to be 3 points above the baseline,
and 2 points below.

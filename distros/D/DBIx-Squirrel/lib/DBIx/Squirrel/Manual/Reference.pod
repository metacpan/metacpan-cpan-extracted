=head1 NAME

DBIx::Squirrel::Manual::Reference - DBIx::Squirrel reference

=head1 DESCRIPTION

You write the SQL; DBIx::Squirrel takes away the DBI machinery around
it, with placeholders in any common style, a list into C<IN (...)> from
one placeholder, and results read through an iterator, and every
handle is still a DBI handle. Rows can also be changed as they're
read, by small functions written beside the query.

This reference describes every method, attribute, function and
message, and the protocols other code can rely on. It comes in two
parts, as the L<user guide|DBIx::Squirrel::Manual::HowTo> does. Part 1 is DBIx::Squirrel:
the round trip to the database, a query sent and its rows read back,
complete in itself. Part 2 is data crossing the database's edge, done
with a distribution of its own, which Part 2 introduces. The chapters
follow the guide's, and each links to its chapter there: the guide is
the tour, this is the map. Each module's own POD says the same things
more briefly. Where the two differ, the POD is the authority. Every
example runs, against the database below, imports what it uses, and
its comments say what it prints.

This is version 4. L<Upgrading from 3.x|/"Upgrading from 3.x">,
L<Upgrading from 2.x|/"Upgrading from 2.x"> and
L<Upgrading from 1.x|/"Upgrading from 1.x"> list what changes for code
written for earlier versions.

=head1 The examples' database

The examples run against this SQLite database, the user guide's, a
file called C<music.db>. They follow on from each other, so C<$dbh> is
this handle wherever it appears. Each example after it imports what
it uses, from the module that makes it, so it works when copied, with
a handle of your own as C<$dbh>.

    use v5.36;
    use DBIx::Squirrel;

    my $dbh = DBIx::Squirrel->connect('dbi:SQLite:dbname=music.db', {RaiseError => 1, PrintError => 0});

    $dbh->do("DROP TABLE IF EXISTS $_") for qw(track album artist);
    $dbh->do('CREATE TABLE artist (id INTEGER PRIMARY KEY, name TEXT)');
    $dbh->do('CREATE TABLE album  (id INTEGER PRIMARY KEY, artist_id INTEGER, title TEXT, year INTEGER)');
    $dbh->do('CREATE TABLE track  (id INTEGER PRIMARY KEY, album_id INTEGER, name TEXT, plays INTEGER)');

    $dbh->do('INSERT INTO artist (name) VALUES (?)', $_) for 'Abba', 'Blur', 'Cream';
    $dbh->do('INSERT INTO album (artist_id, title, year) VALUES (?, ?, ?)', @$_)
        for [1, 'Arrival', 1976], [2, 'Parklife', 1994], [2, 'The Great Escape', 1995],
            [3, 'Disraeli Gears', 1967];
    $dbh->do('INSERT INTO track (album_id, name, plays) VALUES (?, ?, ?)', @$_)
        for [1, 'Dancing Queen', 9100], [1, 'Knowing Me, Knowing You', 4200],
            [2, 'Girls & Boys', 6100], [2, 'Parklife', 5800],
            [3, 'Country House', 3900], [4, 'Sunshine of Your Love', 7700];

=head1 At a glance

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(drop_if take);

    # Placeholders in the style you like: ?, ?1, :1, $1, :name or $name
    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id');
    $sth->execute(id => 2);
    say $sth->fetchrow_arrayref->[0];    # Blur

    # A placeholder with ... takes a list: a ? for each of its values
    my $names = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...:ids) ORDER BY id', ids => [1, 3]);
    say "@$names";    # Abba Cream

    # An iterator over the rows, read as they're wanted
    my $it = $dbh->iterate('SELECT name FROM artist ORDER BY id');
    while (my($row) = $it->next) {
        say $row->[0];
    }
    # Abba
    # Blur
    # Cream

    # Stages beside the query, for what SQL can't do: the two most played
    # tracks not yet on a phone
    my %on_my_phone = map { $_ => 1 } 'Dancing Queen', 'Parklife', 'Sunshine of Your Love';
    my @next = $dbh->iterate(
        'SELECT name FROM track ORDER BY plays DESC',
        pluck('name'),
        drop_if { $on_my_phone{$_} },
        take(2),
    )->all;
    say join ', ', @next;    # Girls & Boys, Knowing Me, Knowing You

    # Each row as an object, with a method for each column
    say $dbh->results('SELECT * FROM album WHERE id = ?', 2)->first->title;    # Parklife

=head1 Part 1: DBIx::Squirrel

Everything in this part is DBIx::Squirrel's own: the DBI's handles,
extended, with placeholders, the iterator and stages. It's the whole
library, and nothing in it needs Part 2.

=head1 1. Connecting

The user guide's L<chapter 1|DBIx::Squirrel::Manual::HowTo/"1. Still the DBI">.

=head2 Importing

C<use DBIx::Squirrel> takes the names the DBI exports, as C<use DBI>
does, and the DBI exports them:

    use DBIx::Squirrel qw(:sql_types neat);

    say SQL_INTEGER;    # 4
    say neat('Abba');   # 'Abba'

=head2 connect

A program connects with C<< DBIx::Squirrel->connect >> where it would call
C<< DBI->connect >>, and everything after works as it did: the handles are
subclasses of the DBI's, C<DBIx::Squirrel::db> and C<DBIx::Squirrel::st>,
so they do everything the DBI's handles do. For SQLite, or any data
source without a username or password, the attributes can follow the
data source straight away, as in L<the examples'
database|/"The examples' database">.

Unlike the DBI's C<connect>, it B<always croaks> if the connection
fails, whatever C<RaiseError> is set to. The message is the one the DBI
raises under C<RaiseError>, such as
C<DBIx::Squirrel connect('dbname=music.db','',...) failed: ...>, and
it's reported at the line that called C<connect>. The DBI returns
C<undef> without C<RaiseError>.

    eval { DBIx::Squirrel->connect('dbi:NoSuchDriver:x', {RaiseError => 0, PrintError => 0}) };
    say $@ ? 'croaked' : 'returned';    # croaked

=head2 Connecting with an existing handle

Given a database handle in place of a data source, C<connect> makes a
new connection with the same parameters, using the DBI's C<clone>. Any
attributes passed are applied to the new connection. The handle can
come from DBIx::Squirrel, from the DBI itself, or from code that made
its own connection. So a plain DBI handle can be turned into
DBIx::Squirrel's:

    use DBI;

    my $plain    = DBI->connect('dbi:SQLite:dbname=music.db', '', '', {RaiseError => 1});
    my $squirrel = DBIx::Squirrel->connect($plain);
    say ref $squirrel;    # DBIx::Squirrel::db

The new handle keeps the first one's C<ekorn_> defaults. Any passed
take their place. It's a separate connection, not a second name for
the first. It doesn't share the first one's transaction, temporary
tables or session settings. An in-memory SQLite database, for example,
gives a new, empty database.

=head2 DBIx::Squirrel's own attributes

Attributes whose names start C<ekorn_> are DBIx::Squirrel's own. They
aren't passed on to the DBI. Passed to C<connect>, they're the defaults
for every statement the handle prepares. Passed to C<prepare> (or
C<prepare_cached>, C<do>, C<iterate>, C<results> and the select methods),
they override those defaults for one statement.

=over 4

=item C<ekorn_dialect>

The database whose rules statements are read by, such as C<mysql> or C<Pg>. C<connect> works it out when it isn't given. See L<The dialect|/"The dialect">.

=item C<ekorn_finish_active>

When true, a statement still active from an earlier C<execute> is finished before it's executed again. See L<execute|/"execute">.

=item C<ekorn_slice>

The shape an iterator fetches rows in: an array reference for arrays, the default, or a hash reference for hashes. See L<Rows as arrays or hashes|/"Rows as arrays or hashes">.

=item C<ekorn_result_class>

The base class of a result set's row objects, a subclass of C<DBIx::Squirrel::Result>. See L<Methods of your own|/"Methods of your own">.

=back

    my $hashes = DBIx::Squirrel->connect('dbi:SQLite:dbname=music.db', {
        RaiseError  => 1,
        ekorn_slice => {},    # iterators fetch hashes, by default
    });
    say $hashes->iterate('SELECT name FROM artist WHERE id = 1')->first->{name};                        # Abba
    say $hashes->iterate('SELECT name FROM artist WHERE id = 1', {ekorn_slice => []})->first->[0];    # Abba

=head2 The dialect

Statements are read by the rules of the database they're for: where
strings start and end, and what's a comment (see
L<Placeholders|/"2. Placeholders">). The dialect is given in the
C<ekorn_dialect> attribute. When it isn't, C<connect> works it out:

=over 4

=item *

It's the driver's own name, such as C<SQLite>, C<mysql> or C<Pg>.

=item *

A driver that passes the connection on to another database
(DBD::ADO, DBD::Gofer, DBD::JDBC, DBD::ODBC or DBD::Proxy) is asked,
through the DBI's C<get_info>, what the database is. MariaDB, MySQL,
PostgreSQL and SQLite are recognised.

=item *

Any other database, or one that doesn't say, is read by the standard
rules.

=back

Name the dialect when C<connect> can't tell:

    $dbh = DBIx::Squirrel->connect($odbc_data_source, $username, $password, {ekorn_dialect => 'mysql'});

=head2 Subclassing

Called on a subclass of DBIx::Squirrel, C<connect> uses that subclass's
database and statement handle classes. The DBI requires the subclass
to have both, and each must be a subclass of DBIx::Squirrel's:

    package My::Squirrel     { our @ISA = 'DBIx::Squirrel' }
    package My::Squirrel::db { our @ISA = 'DBIx::Squirrel::db' }
    package My::Squirrel::st { our @ISA = 'DBIx::Squirrel::st' }

    my $mine = My::Squirrel->connect('dbi:SQLite:dbname=music.db', {RaiseError => 1});
    say ref $mine;    # My::Squirrel::db

Without them, the DBI warns that the subclass isn't set up, and
returns its own handles.

=head1 2. Placeholders

The user guide's L<chapter 2|DBIx::Squirrel::Manual::HowTo/"2. Writing statements">.

=head2 The styles

A statement can use placeholders in any of these styles. Each is
rewritten as C<?> before the DBI sees it:

=over 4

=item C<?>

B<Example:> C<WHERE id = ?>

B<How values are bound:> In order, as with the DBI.

=item C<?1>

B<Example:> C<WHERE id = ?1>

B<How values are bound:> By number, from 1.

=item C<:1>

B<Example:> C<WHERE id = :1>

B<How values are bound:> By number, from 1.

=item C<$1>

B<Example:> C<WHERE id = $1>

B<How values are bound:> By number, from 1.

=item C<:name>

B<Example:> C<WHERE id = :id>

B<How values are bound:> By name.

=item C<$name>

B<Example:> C<WHERE id = $id>

B<How values are bound:> By name.

=back

A statement uses B<one style> throughout. C<prepare> croaks if it
finds more than one, listing each as an example:
C<Expected one placeholder style, not several (?, :name)>.

The same placeholder can appear more than once:

=over 4

=item *

A B<numbered> placeholder is bound once, wherever it appears. In
C<SELECT $2 + $1, $1>, the values C<(10, 20)> give
C<SELECT 20 + 10, 10>. There must be as many values as the highest
number, and numbers start from 1.

=item *

A B<named> placeholder is bound by name, wherever it appears.
Values are given as pairs or in a hash reference, with or without
the sigil. There must be a value for each name, and no other.

=back

    say join ' ', $dbh->selectrow_array('SELECT $2 + $1, $1', 10, 20);    # 30 10

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id OR id = :id + 10');
    $sth->execute(id => 2);
    say $sth->fetchrow_arrayref->[0];    # Blur
    $sth->execute({':id' => 3});
    say $sth->fetchrow_arrayref->[0];    # Cream

=head2 Lists

A placeholder with C<...> before it takes a list. It's written as a C<?>
for each of its values, separated by commas. Use it for C<IN>, and
anywhere else SQL takes a list of values:

    my $names = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...:ids) ORDER BY id', ids => [1, 2]);
    say "@$names";    # Abba Blur

Any style can take a list: C<...?>, C<...?1>, C<...:1>, C<...$1>,
C<...:name> or C<...$name>. The list is a reference to an array of at
least one plain value. It's given as any other value is: by name, or
in order. Given to a statement whose one value is a list, a single
array reference is the list, not the values in it:

    my $one = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN (...?) ORDER BY id', [1, 3]);
    say "@$one";    # Abba Cream

    my $two = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE name = ? OR id IN (...?) ORDER BY id', 'Abba', [2]);
    say "@$two";    # Abba Blur

=over 4

=item *

B<It's prepared with its values.> How many values a list has
decides the statement the DBI prepares. So a statement taking a list
is prepared by a method given its values: C<do>, the select methods,
C<iterate>, C<results>, and the Sugar's functions. C<prepare> and
C<prepare_cached> croak:
C<Expected bind values with a statement taking a list (...:ids)>.

=item *

B<A list has at least one plain value.> An empty list croaks, as
C<IN ()> isn't SQL, so the empty case is left to you:
C<Expected at least one value in a list (...:ids)>. So does a plain
value or C<undef> in place of a list. So does a list holding an
unblessed reference, such as C<[[1, 2, 3]]> to a statement whose one
value is a list. An object in a list is a value.

=item *

B<A placeholder takes a list everywhere it's used, or nowhere.>
Used twice, it takes its list in both places.

=item *

B<Its handle is for lists of the lengths it was prepared for.> The
statement handle of a statement taking a list, such as an iterator's
C<sth>, can be executed again with lists of the same lengths. Given
another length, it croaks. An iterator's L<C<reset>|/"reset"> prepares
the statement again, on a new handle, when a list has a different
number of values. A Sugar statement taking a list isn't cached, as
each length makes a different statement.

=item *

B<Databases limit the values in a statement.> A very long list can
fail to prepare, as the same statement would with plain DBI.

=back

With DBD::Pg, C<= ANY(?)> given an array reference, as a PostgreSQL
array, is one statement whatever the array's length. The two don't mix
up. A list placeholder's array is its list, and any other
placeholder's is a PostgreSQL array. C<pg_placeholder_dollaronly>
leaves the statement to DBD::Pg, so under it no placeholder can take a
list.

=head2 What isn't a placeholder

Placeholders are looked for only in the SQL itself. These are left
unchanged:

=over 4

=item *

anything inside a quoted string or identifier: C<'10:30'>, C<"a:b">,
C<> C<c?> C<>;

=item *

comments: C<-- :x>, C</* $1 */>;

=item *

PostgreSQL's dollar-quoted bodies: C<$$ ... $$>, C<$tag$ ... $tag$>;

=item *

a cast, such as C<x::int>;

=item *

an identifier containing C<$>, such as C<v$session>.

=back

    my $row = $dbh->selectrow_arrayref(q{SELECT '10:30', :name -- not :a placeholder}, undef, name => 'Abba');
    say "@$row";    # 10:30 Abba

To use a C<?>, C<:> or C<$> that isn't a placeholder, put a backslash
before it, as DBD::Pg allows. PostgreSQL's C<?>, C<?|> and C<?&>
operators are examples. The backslash and the character after it are
passed on unchanged, and DBD::Pg removes the backslash:

    $pg->prepare(q{SELECT * FROM doc WHERE data \? 'key' AND id = :id});

=head2 Strings, by dialect

Strings are read by the rules of the handle's L<dialect|/"The dialect">:

=over 4

=item *

With C<mysql> and C<MariaDB>, a backslash escapes a character in a
string (C<'it\'s'>), C<"..."> is a string, and C<#> starts a comment.
MySQL's C<NO_BACKSLASH_ESCAPES> mode isn't noticed.

=item *

With other dialects, a backslash is an ordinary character in a
string (C<'C:\'>), except in PostgreSQL's C<E'...'> strings.

=back

To read one statement as another dialect, give it C<ekorn_dialect>:

    $dbh->prepare($statement, {ekorn_dialect => 'mysql'});

=head2 DBD::Pg's own options

DBD::Pg's placeholder options are followed, whether set on the
database handle or passed to C<prepare>:

=over 4

=item *

With C<pg_placeholder_dollaronly>, only C<$1>-style placeholders are
recognised. The statement is passed on as written, for DBD::Pg to
read and bind.

=item *

With C<pg_placeholder_nocolons>, the C<:1> and C<:name> styles aren't
placeholders, so array slices such as C<data[:2]> are left alone.

=back

=head1 3. Preparing, binding and running

The user guide's L<chapter
3|DBIx::Squirrel::Manual::HowTo/"3. Binding values and running statements">.

=head2 prepare

A statement, with placeholders in any of the L<styles|/"The styles">,
can be written in whichever of four ways suits where it comes from:

=over 4

=item *

a string;

=item *

an array reference of lines, which are joined with spaces;

=item *

a code reference returning either;

=item *

a statement handle, whose statement is prepared again.

=back

    my $sth = $dbh->prepare(['SELECT title', 'FROM album', 'WHERE id = ?']);
    $sth->execute(1);
    say $sth->fetchrow_arrayref->[0];    # Arrival

    my $again = $dbh->prepare(sub { 'SELECT name FROM artist WHERE id = ?' });
    $again->execute(3);
    say $again->fetchrow_arrayref->[0];    # Cream

Blank space around the statement is removed. Comments are passed on to
the database.

Unlike the DBI's C<prepare>, it B<always croaks> if the statement
can't be prepared, whatever C<RaiseError> is set to. The message is the
one the DBI raises under C<RaiseError>, such as
C<DBD::SQLite::db prepare failed: near "SELEC": syntax error>.

Most statements are strings given without attributes. Such a statement
is read for placeholders once for each database handle, which keeps
what it found. The handle keeps up to 1000 statements, and starts
again when it has that many.

A statement taking a L<list|/"Lists"> can't be prepared without its
values, so C<prepare> croaks given one.

=head2 execute

A statement with numbered or named placeholders, executed without
values, croaks unless each placeholder already has a value bound. The
value can come from L<C<bind>|/"bind">, L<C<bind_param>|/"bind_param"> or an
earlier C<execute>, as the DBI keeps them. The DBI would leave the
placeholder unbound, which most drivers read as C<NULL>. C<do>,
iterators and the select methods check the same way:

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = :id');
    eval { $sth->execute };
    print $@;    # Expected a value for each placeholder (none for id) at ... line ...

    $sth->bind_param(id => 1);
    $sth->execute;
    say $sth->fetchrow_arrayref->[0];    # Abba

The DBI doesn't finish a statement still active from an earlier
C<execute> before executing it again. Nor does C<execute>, unless the
C<ekorn_finish_active> attribute is true, on the database handle or the
statement.

=head2 bind

Binding values apart from executing suits a statement run more than
once, or values gathered before it runs. As C<bind> returns the
statement handle, C<execute> can follow it in the same line:

    my $sth = $dbh->prepare('SELECT name FROM track WHERE plays > :plays ORDER BY plays DESC');
    $sth->bind(plays => 8000)->execute;
    say $sth->fetchrow_arrayref->[0];    # Dancing Queen

If the values don't match the placeholders, it croaks at the caller's
line:

=over 4

=item numbered

There aren't as many values as the highest number: C<Expected 2 bind values, not 1>.

=item named

There's an odd number of values: C<Expected names and values in pairs>.

=item named

A name isn't one of the statement's: C<Expected a placeholder of the statement (x)>.

=item named

A name has no value: C<Expected a value for each placeholder (none for id)>.

=item named

A name is given twice, as C<:id> and C<id>: C<Expected one value for each placeholder (two for id)>.

=back

=head2 An array reference of values

A single array reference stands for the values in it, so
C<< $sth->bind([1, 2]) >> is C<< $sth->bind(1, 2) >>. The same goes for
C<execute>, C<do> and the select methods.

An object is a value, as it is to the DBI, whatever it's made of: a
blessed array isn't unwrapped, and a blessed hash isn't taken for
the attributes.

There are two exceptions, each for a statement taking one value:

=over 4

=item *

To a statement whose one value is a L<list|/"Lists">, the array
reference is the list.

=item *

DBD::Pg binds an array reference as a PostgreSQL array. So, with
DBD::Pg, an array reference given to a statement taking one value,
such as C<SELECT * FROM artist WHERE id = ANY(?)>, is that value, as
it would be with the DBI. Through another driver, such as DBD::ODBC,
it's unwrapped as usual, as the driver can't bind arrays.

=back

=head2 bind_param

C<bind_param> binds one value, with the DBI's attributes or type, which
C<bind> and C<execute> can't give. Its placeholder can be named in
whichever way suits its style:

=over 4

=item *

by position, for C<?> placeholders, as with the DBI;

=item *

by number, for numbered placeholders, with or without the sigil: C<1>
or C<'$1'>;

=item *

by name, for named placeholders, with or without the sigil: C<'id'>
or C<':id'>;

=item *

by position, for named placeholders too, as with the DBI.

=back

The value is bound to every use of the placeholder in the statement.
The value for a L<list|/"Lists"> is the list. Each value in it is bound
to a position of its own.

    my $sth = $dbh->prepare('SELECT :a + :a, :b');
    $sth->bind_param(a => 2);
    $sth->bind_param(':b', 3);
    $sth->execute;
    say join ' ', @{ $sth->fetchrow_arrayref };    # 4 3

=head2 execute_array

C<execute_array> and C<execute_for_fetch> execute a statement once for
each row of values, as the DBI's do, and C<bind_param_array> binds an
array of values to a placeholder, a value for each row. They're how
the DBI loads many rows at once. Plain DBI's work for C<?>, and for
other styles only as far as the driver reads them; here they work for
every style:

=over 4

=item *

A row's values come in the order of its placeholders: by number, or,
for names, in the order each first appears. C<:id, :name, :id> takes
two values a row, not three.

=item *

For named placeholders, a row can be a hash, keyed by name, with or
without the sigil: rows shaped by L<as_hash|/"as_hash">, or records
from anywhere, load as they are.

=item *

C<bind_param_array> names its placeholder as
L<C<bind_param>|/"bind_param"> does: by number or by name, with or
without the sigil. A plain value, not an array, is the value for
every row.

=back

    $dbh->do('CREATE TEMP TABLE gig (artist TEXT, city TEXT, year INTEGER)');
    my $sth = $dbh->prepare('INSERT INTO gig (artist, city, year) VALUES (:artist, :city, :year)');

    # An array for each name, in the order each first appears
    say scalar $sth->execute_array({}, ['Abba', 'Blur'], ['Brighton', 'Colchester'], [1974, 1990]);    # 2

    # Rows as hashes, from anything that gives them
    my @rows = ({artist => 'Cream', city => 'Windsor', year => 1966});
    say scalar $sth->execute_for_fetch(sub { shift @rows });    # 1

    # Arrays bound by name, and a value for every row
    $sth->bind_param_array(':artist', ['Abba', 'Cream']);
    $sth->bind_param_array(city => ['London', 'London']);
    $sth->bind_param_array(year => 1977);
    my @status;
    say scalar $sth->execute_array({ArrayTupleStatus => \@status});    # 2
    say "@status";                                                     # 1 1

    say $dbh->selectrow_array('SELECT COUNT(*) FROM gig');    # 5
    $dbh->do('DROP TABLE gig');

C<ArrayTupleFetch> and C<ArrayTupleStatus> work as the DBI's do, and so
does context: in a list, C<execute_array> gives the rows executed and the
rows changed. The counts the DBI checks are of the placeholders, not
their uses, and its errors are its own, raised as its attributes say. A
row of the wrong shape croaks at the caller's line, as C<execute> would:
one with too few or too many values, C<Expected 2 bind values, not 1>, or
one that's neither an array nor, for named placeholders, a hash,
C<Expected a row of values: an array, or a hash for named placeholders>.
The rows before it have been executed, so load in a transaction to keep
all or none. For C<?>, the DBI's way holds instead: the row's error goes
in its status, and the rows after it are executed. A statement with a
L<list|/"Lists"> can't take rows, as its handle is prepared for lists of
one length: each of the three croaks, C<Expected no list placeholder in a
statement for rows of values (...:ids)>. Arrays bound with
C<bind_param_array> are kept with the statement, not in the DBI's
C<ParamArrays>, for any style but C<?>.

=head2 do

Unlike the DBI's, the attributes may be left out. The first argument
after the statement is taken as the attributes only if it's an
unblessed hash reference or C<undef>. An array reference there stands
for the L<values in it|/"An array reference of values">. Any other
unblessed reference croaks: C<Expected a reference to a HASH or ARRAY>.
An object there is a bind value, as it is to the DBI.

    $dbh->begin_work;
    say $dbh->do('UPDATE artist SET name = :name WHERE id = :id', name => 'BLUR', id => 2);    # 1
    say $dbh->do('UPDATE artist SET name = ? WHERE id = ?', ['Blur', 2]);                       # 1
    $dbh->rollback;

A statement with C<?> placeholders, or none, goes to the driver's own
C<do>, as with plain DBI. So the driver's row counts and options apply,
such as running several statements with DBD::SQLite's
C<sqlite_allow_multiple_statements>. A statement with numbered or named
placeholders is prepared and executed. Some drivers, such as
DBD::SQLite, then count the rows of an C<UPDATE ... RETURNING> only as
they're fetched, giving C<0E0>.

Like the DBI's, C<do> returns no rows, even from a C<SELECT> or a
C<RETURNING> clause. Use C<prepare> and C<execute>, an
L<iterator|/"4. Iterators">, or the select methods, for those.

=head2 The select methods

Each select method works as the DBI's does, given no stages. It
prepares the statement as C<prepare> does, unless it's already a
statement handle, and binds the values as L<C<bind>|/"bind"> binds them,
so placeholders can be in any style. C<selectall_hashref>'s key field
can be an array reference of fields, for nested keys, and
C<selectcol_arrayref> takes the DBI's C<Columns> attribute, as the DBI's
do:

    my @row = $dbh->selectrow_array('SELECT id, name FROM artist WHERE id = ?', 2);
    say "@row";    # 2 Blur

    say $dbh->selectrow_hashref('SELECT * FROM artist WHERE id = :id', id => 1)->{name};    # Abba

    my $col = $dbh->selectcol_arrayref('SELECT name FROM artist WHERE id IN ($1, $2) ORDER BY id', 1, 2);
    say "@$col";    # Abba Blur

    my $by_id = $dbh->selectall_hashref('SELECT id, name FROM artist', 'id');
    say $by_id->{3}{name};    # Cream

As with L<C<do>|/"do">, the attributes may be left out. The first
argument after the statement, or after C<selectall_hashref>'s key
field, is taken as the attributes only if it's an unblessed hash
reference or C<undef>. So named values given in a hash reference, or a
first value that's C<undef>, need the attributes, or C<undef>, in front.

B<Given stages after the bind values,> each pushes what the DBI's
method returns through them, as a pipeline called with values does. It
returns every value that comes out of the last. Where one value is
asked for, it returns a sink's result, if a sink is last, or else how
many values came out. As a pushed run has no statement as its source,
the stages can't use C<pluck> by a name for an array row, or C<as_hash>;
C<pluck> with no column, or by position, works.

What goes through the stages is what the method returns.
C<selectall_array> returns the rows, so each row goes through on its
own, and C<selectrow_array> each of the row's values. The others return
one reference, so a stage gets all of it at once: every row, for
C<selectall_arrayref>.

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my @slugs = $dbh->selectall_array('SELECT title FROM album ORDER BY year', pluck, sub { lc s( \W+ )(-)xgr });
    say "@slugs";    # disraeli-gears arrival parklife the-great-escape

    say scalar $dbh->selectall_array('SELECT name FROM track', sub { split ' ', $_->[0] });    # 16

    say join ',', $dbh->selectrow_array('SELECT id, name FROM artist WHERE id = :id', id => 2, sub {"<$_>"});    # <2>,<Blur>

    say $dbh->selectall_arrayref('SELECT name FROM artist ORDER BY id', sub { join ' ', map { $_->[0] } @$_ });    # Abba Blur Cream

C<selectall_array> with stages is the select method most like
L<C<iterate>|/"iterate">, but every row is fetched before the first goes
through the stages. An iterator fetches rows as they're wanted, and
stops fetching when a stage stops the run.

Unlike C<prepare>, they don't croak if the statement can't be prepared.
Without C<RaiseError>, each returns what the DBI's returns, C<undef> or
nothing.

=head1 4. Iterators

The user guide's L<chapter
4|DBIx::Squirrel::Manual::HowTo/"4. A statement as a source of rows">.

An iterator treats a statement as a source of rows, read only as
they're wanted. Each row is run through the iterator's
L<stages|/"5. Stages and Context">, if any, and what comes out is a
result. With no stages, the result is the row.

=head2 iterate

An iterator is the usual way to read a statement's results here: it
fetches rows as they're wanted, and hands out each after it has run
through the stages. The bind values are in any form C<execute> takes,
and, as with C<do>, the attributes may be left out. The B<stages> are
at the end of the arguments: code references, or stages made by
DBIx::Squirrel's modules. Each row is run through them, in order. See
L<Stages|/"Stages">.

B<A sink given last says what comes back,> in place of an iterator,
as L<chapter 14|/"14. Sinks">, in Part 2, describes.

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $it = $dbh->iterate('SELECT name FROM artist WHERE name LIKE :pattern ORDER BY id', pattern => '%r%', pluck);
    while (my($name) = $it->next) {
        say $name;
    }
    # Blur
    # Cream

The statement isn't executed until the first result is asked for. It's
finished when the results run out, when the run is ended early, by a
L<stop|/"6. Stopping early">, or by C<first> or C<single>, and when
the iterator is let go.

=head2 How rows are fetched

Rows are fetched with the DBI's C<fetchall_arrayref>, 2 at first, the
least that tells whether there's a second, then twice as many each
time a fetch fills its batch, up to 64. Past 64, each fetch's cost is
spread so thin that a batch of 1,024 read narrow rows at most 7%
faster, and would hold more of a wide row's data. So reading one row fetches no more than
two, and DBIx::Squirrel holds no more than 64 rows of a result.

The driver may hold more. DBD::SQLite reads rows as they're fetched,
but DBD::Pg and DBD::mysql receive the whole result when the
statement is executed. With MySQL, the C<mysql_use_result> attribute
makes the driver read rows as they're fetched. With PostgreSQL, a
cursor does, declared and fetched from in your SQL.

Without stages, C<all> takes what's left of the batch and fetches the
rest at once. That's nearly as quick as the DBI's own
C<selectall_arrayref>. With stages, each row goes through them in turn,
which costs a little for each row. So to change every row of a large
result, when nothing needs to stop early, C<map> over C<all> is quicker
than a stage:

    my @names = map { $_->[0] } $dbh->iterate('SELECT name FROM artist ORDER BY id')->all;
    say "@names";    # Abba Blur Cream

=head2 The iterator's methods

An iterator is read a result at a time with C<next>, in a C<while> loop,
or for what's left of the run, with C<all>, or for one result, with
C<first> or C<single>. C<all>, C<first> and C<single> take what's left of
the run, so after C<next> they start from the next result, and each
finishes the statement, so the rest of its rows aren't fetched:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $it = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck);
    my($abba) = $it->next;
    say $abba;                   # Abba
    say join ' ', $it->all;      # Blur Cream

    my $names = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck)->all;
    say scalar @$names;          # 3

    say $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck)->first;                # Abba
    say $dbh->iterate('SELECT name FROM artist WHERE id > 9', pluck)->first // 'none';    # none
    say $dbh->iterate('SELECT COUNT(*) FROM track', pluck)->single;                        # 6

C<all> gives an array reference only where one value is asked for. In
a hash constructor, an argument list or a sub's return, it gives a
list, flattened into what's around it, unless you write C<scalar>.
C<all_arrayref> gives one reference, whatever the context, reading the
run to its end as C<all> does:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my %artists = (
        names => $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck)->all_arrayref,
        table => 'artist',
    );
    say "@{$artists{names}}";    # Abba Blur Cream

C<single> is for a statement meant to give one result: if there's
another, it warns, and returns the first, which finds a statement that
lost its C<LIMIT 1>, or its C<WHERE>.

A stage can return C<undef> as a result. So read C<next> in list
context, as below, rather than testing whether what it returns is
defined. Once a stage dies, the iterator has ended: C<next> returns an
empty list on every call after, and the statement is finished, until
L<reset|/"reset"> runs it again.

    my $it = $dbh->iterate('SELECT id, name FROM artist ORDER BY id', sub { $_->[0] == 2 ? undef : $_->[1] });
    my @seen;
    while (my($name) = $it->next) {
        push @seen, $name // '(none)';
    }
    say "@seen";    # Abba (none) Cream

C<ended> tells how the last run ended: C<done> when the rows ran out,
C<stopped> when it was cut short, by C<first>, by C<single> finding a
second result, or by a stage that stopped, and C<died> when a stage
died. It returns nothing while a run is going, or after C<reset> starts
a new one. A run read with C<|> or C<@{}> is the iterator's last run too
(see L<16. Operators|/"16. Operators: E<verbar> and @{}">).

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $it = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck);
    $it->all;
    say $it->ended;                   # done
    $it->reset->first;
    say $it->ended;                   # stopped
    say $it->reset->ended // 'none';  # none

The iterator reaches its statement too. C<column_names> gives the
statement's columns, as C<fetchrow_hashref> would key them, executing
it first if it hasn't been. They're read when it's executed, as some
drivers, such as DBD::mysql, give none once the last row is fetched;
a stage asks for them through L<iterator|/"Context">. C<sth> gives the
statement handle, which changes when C<reset> prepares a statement
taking a L<list|/"Lists"> again, for a list of another length.

    say join ', ', $dbh->iterate('SELECT id, title AS Album FROM album')->column_names;    # id, Album

    my $it = $dbh->iterate('SELECT name FROM artist');
    say $it->sth->{Statement};    # SELECT name FROM artist

C<iterate> makes an iterator by calling C<< DBIx::Squirrel::Iterator->new >>
with a statement handle, its bind values and stages. To iterate over a
handle you already have, call C<iterate> on it, or C<new> directly; a
handle that isn't DBIx::Squirrel's croaks, C<Expected a DBIx::Squirrel
statement handle>.

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = ?');
    say DBIx::Squirrel::Iterator->new($sth, 3, pluck)->first;    # Cream

=head2 reset

One iterator can be read again, rather than made again: with other
bind values, which replace the ones before, or more stages, which join
its own, each kept until others are given. A run still going is
finished first, and whatever it held goes with it:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $it = $dbh->iterate('SELECT name FROM artist WHERE id > ? ORDER BY id', 0, pluck);
    say join ' ', $it->all;                      # Abba Blur Cream
    say join ' ', $it->reset(1)->all;            # Blur Cream
    say join ' ', $it->reset(sub {lc})->all;     # blur cream

A statement taking a L<list|/"Lists"> is prepared again, on a new
statement handle, if a list given has a different number of values
from the one before. C<sth> then returns the new handle.

=head2 Rows as arrays or hashes

Rows are fetched as arrays, unless the C<ekorn_slice> attribute says
otherwise. It's a slice as the DBI's C<fetchall_arrayref> takes it: an
array reference for arrays, or a hash reference for hashes. Given to
C<connect>, it's the default for each statement the handle prepares.
Given to C<prepare> or C<iterate>, it's for that statement.

    my $it = $dbh->iterate('SELECT id, name FROM artist ORDER BY id', {ekorn_slice => {}}, sub { "$_->{id}: $_->{name}" });
    say join ', ', $it->all;    # 1: Abba, 2: Blur, 3: Cream

=head2 One iterator to a statement handle

A statement handle can have only one iterator going through its
results at a time. While the first has results left, executing another
over the same handle croaks:
C<Expected the statement handle's other iterator to be finished>. Read
the first to the end, or let it go out of scope, first. An iterator
that's let go ends its run, and finishes its statement.

=head1 5. Stages and Context

The user guide's L<chapter
5|DBIx::Squirrel::Manual::HowTo/"5. Stages: shaping rows on the way out">.

=head2 Stages

A stage is given one value, as its argument and in C<$_>, and returns a
list. Write it whichever way reads best: name the value with a
signature, or leave the signature out and use C<$_>:

    sub ($row) { $row->[1] }    # the value, named
    sub { $_->[1] }             # the same, in $_

C<$_> is localised for each call, so your own C<$_> is unchanged.

=over 4

=item nothing

B<It's a:> filter

B<The value:> is dropped.

=item one value

B<It's a:> map

B<The value:> is replaced by that value, which goes on.

=item several values

B<It's a:> flatMap

B<The value:> is replaced by each, which goes through the rest of the stages on its own.

=back

Each value goes through every stage before the next one starts. So the
values come out in order. A stage returns whatever its last statement
gives, so a stage run for its side effects should still return what
the next stage needs.

    my %little = map { $_ => 1 } qw(a of the);

    my @words = $dbh->iterate(
        'SELECT title FROM album ORDER BY year',
        sub { split ' ', $_->[0] },       # flatMap
        sub {lc},                         # map
        sub { $little{$_} ? () : $_ },    # filter
    )->all;
    say "@words";    # disraeli gears arrival parklife great escape

The filter here tests words a stage made, which no C<WHERE> can see. A
row the database could leave out, it should: a C<WHERE> is quicker,
and fewer rows cross the wire.

A stage can be a code reference, or a stage made by one of
DBIx::Squirrel's modules, such as the canned stages below, and
C<gather>'s. Part 2's L<pipelines|/"15. Pipelines"> go wherever a stage
goes, too.

=head2 Context

DBIx::Squirrel::Context's functions tell a stage what it can't work
out from its value: where in the results it is, the row its value came
from, and the iterator reading them. None is exported by default.

    use DBIx::Squirrel::Context qw(iterator result_number result_original);

C<result_number> works in any run of stages, each counting its own: an
iterator's or result set's own stages, and those given to a select
method. C<result_original> gives the row a result is being made from,
as the statement gave it, whatever the stages before have done to it.
C<iterator> works only in an iterator's or result set's own stages, run
by its C<next>, C<all>, C<first> or C<single>. Elsewhere it returns
C<undef>, and outside a run all three do. Part 2's L<The run's
context|/"The run's context"> says how each works in its runs.

    use DBIx::Squirrel::Context qw(result_number result_original);

    my @chart = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        sub { $_->[0] },
        sub { result_number() . ". $_ (" . result_original()->[1] . ')' },
    )->all;
    say $chart[0];    # 1. Dancing Queen (9100)

C<result_number> counts results, not rows. While a stage drops rows,
the number stays the same, and each value a stage returns in place of
one row is a result of its own. So numbering after a filter numbers
what's left:

    use DBIx::Squirrel::Stages::Flow qw(drop_if);
    use DBIx::Squirrel::Context qw(result_number);

    my %on_my_phone = map { $_ => 1 } 'Dancing Queen', 'Parklife', 'Sunshine of Your Love';

    my @to_copy = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        drop_if { $on_my_phone{ $_->[0] } },
        sub { result_number() . ". $_->[0]" },
    )->all;
    say for @to_copy;
    # 1. Knowing Me, Knowing You
    # 2. Girls & Boys
    # 3. Country House

C<result_original> keeps the row as it was fetched, so a stage after
others that reshaped it can still read any of its columns. For a
result set, it's the row object. In a flush of a stage made with
L<gather|/"gather">, and the stages after it, it's C<undef>, as what a
flush gives comes from every row, not one.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Context qw(result_original);

    my @plays = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC LIMIT 2',
        pluck('name'),
        sub { "$_: " . result_original()->[1] },
    )->all;
    say for @plays;
    # Dancing Queen: 9100
    # Sunshine of Your Love: 7700

C<iterator> reaches the rest: its C<sth> is the statement handle, the
statement handle's C<Database> is the database handle, and its
C<column_names> are the statement's columns.

    use DBIx::Squirrel::Context qw(iterator);

    my($columns) = $dbh->iterate(
        'SELECT id, name FROM artist WHERE id = 1',
        sub { join ',', iterator()->column_names },
    )->all;
    say $columns;                 # id,name
    say iterator() // 'none';     # none

=head2 Canned stages

Four modules of ready-made stages ship with DBIx::Squirrel, each for
one kind of job: Flow takes or drops values, Rows reshapes rows, Batch
gathers values together, and Taps looks at them as they go by. Each
exports the stages it's usually used for, and the rest upon request, as
the L<index|/"Index"> says. C<:all> gives them all, and C<()> none. Naming
a stage in the import list replaces the defaults. To have the defaults
and one more, name C<:DEFAULT> too:

    use DBIx::Squirrel::Stages::Flow qw(:DEFAULT take_while);

Flow's are discussed in L<Taking and dropping|/"Taking and dropping">,
and Batch's in L<Batching and collecting|/"Batching and collecting">.
Each is a function that makes a stage, checking what it's given when
it's called, not on each value.

=head3 Reshaping rows

A row comes as an array, a hash (with the C<ekorn_slice> attribute), or
a row object (from C<results>), and C<pluck> takes one column from any
of them: by name, in any case, or by position, from 0. Given no
column, it takes a row's only column, so a one-column query gives
plain values:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my @names = $dbh->iterate('SELECT id, name FROM artist ORDER BY id', pluck('name'))->all;
    say "@names";    # Abba Blur Cream

    say join ' ', $dbh->results('SELECT id, name FROM artist ORDER BY id', pluck(0))->all;    # 1 2 3
    say join ' ', $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck)->all;           # Abba Blur Cream

C<pluck> with no column counts each row's own columns, and croaks at a
row of more than one, rather than give the first, which would go wrong
silently when a query gains a column. C<pluck(0)> takes the first.

A name for an array row, or a position for a hash row, is found from
the statement's column names, in the L<run's
context|/"The run's context">, once on each run: an iterator's or result
set's own stages, a chain made with C<|>, or a pipeline of yours,
reading one. So it needs a statement to be what the run reads. A name
for a hash row reads the hash's own keys, so it works anywhere.

C<as_hash> makes each row a hash, as C<fetchrow_hashref> would, for code
written for the DBI's hashes:

    use DBIx::Squirrel::Stages::Rows qw(as_hash);

    my $album = $dbh->iterate('SELECT title, year FROM album WHERE id = 2', as_hash)->first;
    say "$album->{title} ($album->{year})";    # Parklife (1994)

Given column names, C<as_hash> keeps only those, so a stage after it,
or code given its hashes, gets the columns it needs, whatever the
C<SELECT> gave. The names are found in any case, and the hash is keyed
as it would be without them. A name the row hasn't got croaks, so a
query that lost a column shows at once:

    use DBIx::Squirrel::Stages::Rows qw(as_hash);

    my @artists = $dbh->iterate('SELECT * FROM artist ORDER BY id LIMIT 2', as_hash('NAME'))->all;
    say join ' ', keys %{ $artists[0] };              # name
    say join ' ', map { $_->{name} } @artists;       # Abba Blur

The run's context still names every column the statement has, so a
stage reading it sees them all.

**C<pluck> reads the statement's columns, not the row's.** After a
stage that reshapes rows, a name or position for an array row picks
the wrong field, and says nothing. Make the rows hashes first, with
C<as_hash>. Then C<pluck> by name reads each hash's own keys:

    use DBIx::Squirrel::Stages::Rows qw(pluck as_hash);

    my $sql = 'SELECT id, name FROM artist ORDER BY id';

    my @wrong = $dbh->iterate(
        $sql,
        sub { [reverse @$_] },
        pluck('id'),
    )->all;
    say "@wrong";    # Abba Blur Cream

    my @ids = $dbh->iterate(
        $sql,
        as_hash,
        sub { +{%$_, name => uc $_->{name}} },
        pluck('id'),
    )->all;
    say "@ids";    # 1 2 3

=head3 Taps

A tap looks at each value as it goes by and passes it on unchanged,
so a pipeline can be logged, counted or debugged without changing what
it gives. C<peek> calls a block with each value; C<count_into> counts
them into a variable, from 0 on each run:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Taps qw(peek count_into);

    my @seen;
    my @names = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck,
        peek { push @seen, length },
    )->all;
    say "@names: @seen";    # Abba Blur Cream: 4 4 5

    my $read  = 0;
    my @named = $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        count_into(\$read),
        pluck('name'),
    )->all;
    say "@named, from $read rows";    # Abba Blur Cream, from 3 rows

C<dump_to> is for debugging: it writes each value with Data::Dumper, to
a filehandle or STDERR. Where Text::Redact::Secrets v1.x is installed,
it writes each secret that module's rules find as C<*REDACTED*>, in the
text it writes only: the value passed on is as it came. The rules find
a long, random password, token or key, such as the password in a DSN,
but not a short or ordinary password, so a dump can still hold
secrets. Without the module, or while
C<local $DBIx::Squirrel::Stages::Taps::DumpSecrets = 1> is set, it
writes each value in full; with the module there but broken, it
croaks rather than write a dump. It doesn't escape control characters in strings, so
a value from outside can send escape sequences to a terminal.

    use DBIx::Squirrel::Stages::Rows qw(as_hash);
    use DBIx::Squirrel::Stages::Taps qw(dump_to);

    open my $fh, '>', \my $dump or die $!;
    $dbh->iterate('SELECT id, name FROM artist WHERE id = 1', as_hash, dump_to($fh))->all;
    close $fh;
    print $dump;
    # {
    #   'id' => 1,
    #   'name' => 'Abba'
    # }

Where a tap needs more than one thing done, C<tee> runs each value
through a branch of stages of its own. The branch is a run beside the
main run: its stages keep their state across the values, a stop in it
ends only the branch, and a death in it kills the run. It shares the
main run's context, so C<pluck> and C<as_hash> work in it on a
statement's rows. Each value costs a push into the branch, several
times what C<peek> costs, so it's for side jobs and debugging, not a
hot loop. A stop after the tee, such as C<take>'s or C<first>'s, closes
the branch, so its flushes run, and what it holds, such as a
part-filled C<batch>, is handed on, as when the input runs out.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(take_if);
    use DBIx::Squirrel::Stages::Taps qw(tee);

    my @hits;
    my @names = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY id',
        tee(take_if { $_->[1] > 6000 }, pluck('name'), sub { push @hits, $_; () }),
        pluck('name'),
    )->all;
    say scalar(@names), ' tracks; hits: ', join ', ', @hits;    # 6 tracks; hits: Dancing Queen, Girls & Boys, Sunshine of Your Love

=head1 6. Stopping early

The user guide's L<chapter 6|DBIx::Squirrel::Manual::HowTo/"6. Stopping early">.

=head2 Stop

A stage that knows no more results are wanted calls C<Stop>, rather
than drop every row after, so no more rows are fetched. The run ends
early and quietly:

=over 4

=item *

The rest of that stage doesn't run.

=item *

The values already out of the pipeline are kept.

=item *

Any values the stop carries go on through the stages after it.

=item *

Nothing else is processed, and no more rows are fetched.

=back

An iterator that's stopped finishes its statement. Stages after the
one that stopped, made with
L<C<gather>|/"7. Gathering: stages made for each run">, still have their
flushes called.

    use DBIx::Squirrel::Stop qw(Stop);

    my @upto = $dbh->iterate(
        'SELECT title, year FROM album ORDER BY year',
        sub { $_->[1] >= 1990 ? Stop($_) : $_ },    # this one, then no more
        sub { $_->[0] },
    )->all;
    say "@upto";    # Disraeli Gears Arrival Parklife

C<Stop> is exported by default. To keep it out of your namespace,
C<use DBIx::Squirrel::Stop ()>, and call it by its full name,
C<DBIx::Squirrel::Stop::Stop()>.

=head2 Catch errors, but let a stop through

A stop is an exception, an object, which the run catches. So a stage
that catches errors itself, with C<eval> or C<try>, should throw a stop
on again. C<is_stop>, exported on request, is true of every stop,
whether thrown with C<Stop>, with C<throw>, or as a subclass of your
own, and false of any other error. Part 2's L<What a stop is|/"What a stop is"> gives
its class:

    use DBIx::Squirrel::Stop qw(Stop is_stop);
    use experimental qw(try);

    my @safe = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        sub ($row) {
            try {
                Stop() if $row->[0] eq 'Cream';
                return uc $row->[0];
            }
            catch ($e) {
                die $e if is_stop($e);    # a stop goes on
                return 'unknown';
            }
        },
    )->all;
    say "@safe";    # ABBA BLUR

=head2 Taking and dropping

DBIx::Squirrel::Stages::Flow's stages decide which values go on, by
their place or by a test. In SQL, C<LIMIT>, C<OFFSET> and C<WHERE> do
that in the database, which is quicker; these are for when Perl
decides: a test on data the database doesn't have, a test on what
came before, or a limit on what's left after one. A stage that stops
the run stops the fetching too, so no more rows are read than are
wanted. Some examples use a hash of the tracks already on a phone,
which the database knows nothing of.

B<By place.> C<take> and C<drop> give a page: C<drop(20), take(10)>
passes on values 21 to 30. C<take> stops the run at its last
value, so the statement is finished then:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(drop_if drop take);

    my %on_my_phone = map { $_ => 1 } 'Dancing Queen', 'Parklife', 'Sunshine of Your Love';

    my @page = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        pluck,
        drop_if { $on_my_phone{$_} },
        drop(1),
        take(2),
    )->all;
    say join ', ', @page;    # Girls & Boys, Country House

C<take_first>, C<take_last> and C<take_single> each pass on one value, so
the stages after them go on working with it. C<take_last> reads every
value to find the last. C<take_single> is for a statement meant to give
one row: at a second, it warns and stops, so a forgotten limit is
found.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(take_first take_last take_single);

    say $dbh->iterate('SELECT title FROM album ORDER BY year', pluck, take_first)->all;    # Disraeli Gears

    my @newest = $dbh->iterate(
        'SELECT title FROM album ORDER BY year',
        take_last,
        pluck,
    )->all;
    say "@newest";    # The Great Escape

    say $dbh->iterate('SELECT name FROM artist WHERE id = 2', pluck, take_single)->all;    # Blur

B<By a test.> C<take_if> and C<drop_if> test every value, as C<grep>
does, and never stop the run. A plain stage ending in a test passes on
what the test returns, true or false; C<take_if> passes on the value:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(take_if drop_if);

    my %on_my_phone = map { $_ => 1 } 'Dancing Queen', 'Parklife', 'Sunshine of Your Love';

    my @copied = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        take_if { $on_my_phone{ $_->[0] } },
        pluck(0),
    )->all;
    say join ', ', @copied;    # Dancing Queen, Parklife, Sunshine of Your Love

    my @to_copy = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        drop_if { $on_my_phone{ $_->[0] } },
        pluck(0),
    )->all;
    say join ', ', @to_copy;    # Knowing Me, Knowing You, Girls & Boys, Country House

A test the database could do, such as C<< plays > 6000 >>, belongs in the
C<WHERE>. In a stage, it's for debugging: trying a condition on a
query's rows without touching the query, before it goes in the SQL:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(take_if);

    my @would_keep = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY id',
        take_if { $_->[1] > 6000 },    # trying it out, before it goes in a WHERE
        pluck(0),
    )->all;
    say join ', ', @would_keep;    # Dancing Queen, Girls & Boys, Sunshine of Your Love

C<take_while> and C<drop_while> test values only until the first that
fails, so they suit rows in the order the test reads. C<take_while>
stops the run there, and reads no further, where C<take_if> would read
every row; C<drop_while> passes on everything from there, without
testing again:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Flow qw(take_while drop_while drop);

    my $half   = $dbh->selectrow_array('SELECT SUM(plays) FROM track') / 2;
    my $so_far = 0;

    my @hits = $dbh->iterate(
        'SELECT name, plays FROM track ORDER BY plays DESC',
        take_while { $so_far < $half },    # the hits making half the plays
        sub { $so_far += $_->[1]; $_->[0] },
    )->all;
    say join ', ', @hits;    # Dancing Queen, Sunshine of Your Love, Girls & Boys

    my $stopped_at = 'Arrival';    # where the last run stopped

    my @still_to_do = $dbh->iterate(
        'SELECT title FROM album ORDER BY year',
        pluck,
        drop_while { $_ ne $stopped_at },
        drop(1),
    )->all;
    say join ', ', @still_to_do;    # Parklife, The Great Escape

=head1 7. Gathering: stages made for each run

The user guide's L<chapter 7|DBIx::Squirrel::Manual::HowTo/"7. Parts made for each run">.

=head2 gather

A stage that keeps state, or holds values to give them together, is
made with C<gather>, so its state starts afresh on each run: each
execution of an iterator or result set, including after C<reset>, each
call of a Sugar statement, and each call of a pipeline. C<gather> calls
its block at the start of each run, so whatever the block declares is
fresh each time. The block returns:

=over 4

=item *

B<the step:> a code reference, called with each value as any stage
is, or a pipeline, whose stages are made for the run in its place;

=item *

B<optionally, the flush:> called with no arguments once the values
run out, even if there were none. What it returns goes through the
rest of the stages, as what a stage returns does. After a
L<stop|/"6. Stopping early">, only the flushes of the stages after
the one that stopped are called;

=item *

B<optionally, the end:> called once the run has ended, however it
ended, and told how: C<done>, C<stopped> or C<died>. An iterator's run
is C<done> once its rows run out, and C<stopped> when C<first> or
C<single> finishes it. What the end returns is dropped.

=back

The parts can be given as a list, in that order, with C<undef> for a
flush left out before an end. Or they can be given by name, in one
hash reference with the keys C<step>, C<flush> and C<end>, giving only
those the stage has.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Gather qw(gather);

    # Each value, then, once they run out, how many there were
    sub and_count () {
        return gather {
            my $count = 0;    # this run's
            return (sub ($value) { $count++; $value }, sub () {"($count)"});
        };
    }

    my $it = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck,
        and_count,
    );
    say join ' ', $it->all;           # Abba Blur Cream (3)
    say join ' ', $it->reset->all;    # Abba Blur Cream (3)

    my @how;
    my $watched = gather { +{step => sub { $_->[0] }, end => sub ($how) { push @how, $how }} };
    $dbh->iterate('SELECT name FROM artist', $watched)->first;
    say "@how";    # stopped

A block that returns anything else croaks as the run starts:
C<Expected stage #%s, made with gather, to return a code reference or a pipeline, and optionally a flush and an end>.
C<gather> given something other than a block or code reference croaks
C<Expected a code reference>.

A stage made with C<gather> is an object that can go wherever a stage
can. C<gather> is exported by default; to keep it out of your
namespace, C<use DBIx::Squirrel::Gather ()>.

=head2 Batching and collecting

DBIx::Squirrel::Stages::Batch's stages hold values and pass them on
together. They're made with C<gather>, so each run starts afresh, and
both pass on what they still hold once the values run out.

C<batch> suits loading or sending rows in groups, as it holds no more
than one batch at a time; the last batch, given when the values run
out, may be shorter, and with no values there's no batch at all:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Batch qw(batch);

    my @batches = $dbh->iterate(
        'SELECT name FROM track ORDER BY id',
        pluck('name'),
        batch(4),
    )->all;
    say scalar(@$_), ': ', join ', ', @$_ for @batches;
    # 4: Dancing Queen, Knowing Me, Knowing You, Girls & Boys, Parklife
    # 2: Country House, Sunshine of Your Love

C<collect> holds every value until the end, so the whole result is in
memory at once. Given a block, it passes on what the block makes of
them all, which can be nothing, one value, or several; the block is
called even with no values, so C<collect> always gives a result:

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Stages::Batch qw(collect);

    my($ids) = $dbh->iterate('SELECT id FROM artist ORDER BY id', pluck, collect)->all;
    say "@$ids";    # 1 2 3

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        collect { join '+', @_ },
    )->first;
    # Abba+Blur+Cream

=head1 8. Result sets and row objects

The user guide's L<chapter 8|DBIx::Squirrel::Manual::HowTo/"8. Rows as objects">.

=head2 results

Where code reads a row's columns by name, a result set makes each row
an object, with a method for each column, named in lower case, so
C<< $artist->name >> reads as it would in a class of your own. It's read
as any iterator is, and its stages see the objects:

    my $results = $dbh->results('SELECT id, Name FROM artist WHERE id <= ? ORDER BY id', 2);
    while (my($artist) = $results->next) {
        say $artist->id, ' ', $artist->name;
    }
    # 1 Abba
    # 2 Blur

Rows are always fetched as arrays for a result set. The C<ekorn_slice>
attribute doesn't apply.

=head2 Row objects

Each row is an array, blessed into a class with a method for each
column. There's one class for each base class and list of column
names. It's made the first time a result set fetches rows with those
columns, and kept for the life of the program. A row needs nothing
from its result set, and can be kept after the result set has gone.

A column gets no method:

=over 4

=item *

if its name can't be a method's, such as C<COUNT(*)>;

=item *

if the base class already has a method of that name, such as C<can>,
C<isa>, C<get_column>, or one of your own.

=back

When two columns have one name, as in C<SELECT a.id, b.id>, the method
is the first's. To give such a column a method, give it another name
in the statement, with C<AS>:

    my $row = $dbh->results('SELECT COUNT(*), COUNT(*) AS albums FROM album')->first;
    say $row->albums;    # 4
    say $row->[0];       # 4

=head2 get_column

A column whose name can't be a method's, such as C<COUNT(*)>, or one a
method of the class already has, is read with C<get_column>, by its
name, in any case, or its position:

    my $row = $dbh->results('SELECT COUNT(*) FROM album')->first;
    say $row->get_column('count(*)');    # 4
    say $row->get_column(0);             # 4

=head2 Methods of your own

Row classes are subclasses of C<DBIx::Squirrel::Result>, or of the
class given in the C<ekorn_result_class> attribute, which must itself
be a subclass of C<DBIx::Squirrel::Result>. So rows can have methods of
your own:

    package My::Artist {
        our @ISA = 'DBIx::Squirrel::Result';
        sub shout ($self) { return uc $self->name }
    }

    my $artist = $dbh->results('SELECT * FROM artist WHERE id = 2', {ekorn_result_class => 'My::Artist'})->first;
    say $artist->shout;    # BLUR

A class that isn't a subclass of C<DBIx::Squirrel::Result> croaks:
C<Expected ekorn_result_class to be a subclass of DBIx::Squirrel::Result (My::Other)>.

=head1 9. Sugar: a function for each database and statement

The user guide's L<chapter
9|DBIx::Squirrel::Manual::HowTo/"9. A function for each database and statement">.

C<DBIx::Squirrel::Sugar> gives each database a name. The package that
names it gets a function of that name, which returns the database
handle or runs a statement on it. A statement gets a function too,
which runs it with the bind values and any stages given.

=head2 Defining them on use

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Sugar database => {
        music => [$data_source, $username, $password, \%attr],
    };
    use DBIx::Squirrel::Sugar statement => {
        artist_names => [music => 'SELECT name FROM artist', pluck],
        artist       => [music => 'SELECT * FROM artist WHERE id = :id'],
    };
    use DBIx::Squirrel::Sugar pipeline => {loud => [sub {uc}]};
    use DBIx::Squirrel::Sugar qw(database statement);

Given a hash reference after C<database> or C<statement>, C<use> defines
each database or statement named in it, with its arguments in an array
reference. Part 2's L<The Sugar's pipelines|/"The Sugar's pipelines">
adds a third key, for naming pipelines. It gives the package each
function while the package is compiled, so the function can be called
without parentheses. The arguments are worked out then too: the
environment, literals, and what a C<BEGIN> block has set are there, but
a variable the program sets as it runs is not yet. C<use> also gives
the package the C<database> and C<statement> functions, and, given just
their names, only those.

=head2 Defining them as the program runs

C<use> defines databases and statements as the program compiles, from
what's known then. Where the arguments aren't known until the program
runs, such as a data source read from a configuration file, C<database>
and C<statement> define them then, and give the package the same
functions. A function defined so isn't known as the program compiles,
so it's called with parentheses. Given just a name, C<database> is the
handle, from anywhere in the program:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    database(archive => 'dbi:SQLite:dbname=music.db', {RaiseError => 1});
    statement(albums_of => archive => 'SELECT title FROM album WHERE artist_id = ? ORDER BY year', pluck);

    say join ', ', albums_of(2)->all;    # Parklife, The Great Escape
    say ref database('archive');           # DBIx::Squirrel::db

A statement's database is found when its function runs, so it can be
defined after the statement. Each database is defined once in a
program, by a name a function can have, which the package can't have
a function of already.

=head2 The function a database is given

    $dbh     = music();
    $sth     = music($statement, @bind_values);
    $sth     = music($statement, \%attr, @bind_values);
    $it      = music($statement, @bind_values, @stages);

=over 4

=item nothing

returns the database handle.

=item a statement and bind values

prepares the statement, executes it, and returns the statement handle, or nothing if it couldn't be executed.

=item those, and stages at the end

returns what C<iterate> does: an iterator over the results.

=back

An unblessed hash reference or C<undef> straight after the statement is
the attributes to prepare it with. The statement can be a statement
handle, which is itself executed, or iterated over.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Sugar database => {music => ['dbi:SQLite:dbname=music.db', '', '', {RaiseError => 1}]};

    say music('SELECT name FROM artist WHERE id = ?', 1)->fetchrow_arrayref->[0];    # Abba
    say ref music('SELECT name FROM artist', pluck);                                 # DBIx::Squirrel::Iterator
    say join ' ', music('SELECT name FROM artist ORDER BY id', pluck)->all;    # Abba Blur Cream

=head2 The function a statement is given

    $sth     = artist(@bind_values);
    $it      = artist(@bind_values, @stages);

It executes the statement with the bind values, and returns the
statement handle, or nothing if it couldn't be executed. With stages,
its own or those given after the bind values, it returns an iterator
over the results, as C<iterate> does. The results go through its own stages, then those
given. Stages given are for that call only. A string given is always a
bind value, never a pipeline's name.

    use DBIx::Squirrel::Stages::Rows qw(pluck);
    use DBIx::Squirrel::Sugar
        statement => {
            artist_names => [music => 'SELECT name FROM artist ORDER BY id', pluck],
            artist       => [music => 'SELECT * FROM artist WHERE id = :id'],
        };

    say ref artist_names;                              # DBIx::Squirrel::Iterator
    say join ' ', artist_names->all;                  # Abba Blur Cream
    say join ' ', artist_names(sub {lc})->all;        # abba blur cream
    say artist_names->first;                           # Abba
    say artist(id => 3)->fetchrow_hashref->{name};     # Cream

A stage imported is a function of your package, so a statement can't
be given its name: C<Expected no function of the name in main already
(pluck)>. Import only the names you call, or call a stage by its full
name, as C<DBIx::Squirrel::Stages::Rows::pluck(...)>.

The statement is prepared once for each database handle, with
C<prepare_cached>. Its handle may be in use: by a statement handle not
read to the end, or by an iterator of an earlier call still reading. A
call then prepares one of its own. A statement taking a L<list|/"Lists">
is prepared for each call's values instead, and isn't cached.

=head1 10. Caching and connections

The user guide's L<chapter 10|DBIx::Squirrel::Manual::HowTo/"10. Caching and connections">.

=head2 prepare_cached

The DBI's cache of statement handles works as it does with the DBI,
but for two things: how a statement's placeholders, and an iterator
reading a handle, bear on which handle is handed out.

Two statements can be rewritten the same: C<SELECT :a, :b> and
C<SELECT :b, :a> both become C<SELECT ?, ?>. Each still has a handle of
its own, as the statement as written is part of the cache's key.
DBIx::Squirrel's own attributes are part of the key too. So a
statement prepared with C<< {ekorn_slice => {}} >> and one prepared without
have different handles.

The DBI finishes a cached handle that's still active before handing it
out. If an iterator is part way through the handle, that would cut its
results short. So such a handle isn't handed out or finished. A new
handle is made instead, and cached in its place. The exception is
C<$if_active> of 2, which asks for the cached handle, unchanged.
Otherwise, C<$if_active> means what it does to the DBI. A cached handle
that's active, with no iterator, is finished, after a warning, unless
C<$if_active> says otherwise.

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    my $sql   = 'SELECT name FROM artist ORDER BY id';
    my $first = $dbh->prepare_cached($sql)->iterate(pluck);
    $first->next;
    my $second = $dbh->prepare_cached($sql)->iterate(pluck);
    say $first->sth == $second->sth ? 'shared' : 'a handle each';    # a handle each
    say join ' ', $second->all;    # Abba Blur Cream
    say join ' ', $first->all;     # Blur Cream

=head2 connect_cached

Code that connects in several places, such as a function for each
request, shares one connection by connecting with C<connect_cached>.
It takes its arguments as C<connect> does, and calls C<connect> when it
needs a new connection, so it croaks on failure too. DBIx::Squirrel's
own attributes are part of its key, so a handle made to fetch rows as
hashes isn't handed to code expecting arrays:

    my $one   = DBIx::Squirrel->connect_cached('dbi:SQLite:dbname=music.db', {RaiseError => 1});
    my $two   = DBIx::Squirrel->connect_cached('dbi:SQLite:dbname=music.db', {RaiseError => 1});
    my $hashy = DBIx::Squirrel->connect_cached('dbi:SQLite:dbname=music.db', {RaiseError => 1, ekorn_slice => {}});
    say $one == $two   ? 'shared' : 'apart';    # shared
    say $one == $hashy ? 'shared' : 'apart';    # apart

=head2 The Sugar's connections

A Sugar database is connected to when it's first used, not when it's
defined, with C<connect_cached>. So two databases defined with the same
arguments share a handle. The handle is kept, and each use has the
same one, without a ping to the database each time. It's pinged only
while its last call has failed, which leaves the error to be read.
It's made again if the connection has gone, or if the handle has been
disconnected. So the call after a connection drops fails, as it would
with plain DBI, and the call after that has a new connection.

=head1 11. Writing stages, and functions that take them

The user guide's L<chapter
11|DBIx::Squirrel::Manual::HowTo/"11. Functions that take stages, and stages for others">.

=head2 A function that takes stages

A function can take stages from its caller, at the end of its
arguments, and hand them to C<iterate> after its values. Its caller
then gets an iterator. A function taking a fixed number of values
takes the rest as stages, as here; Part 2's L<What a call takes as
stages|/"What a call takes as stages"> says how to find the stages at
the end of any list:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    sub albums_since ($year, @stages) {
        return $dbh->iterate('SELECT title FROM album WHERE year >= ? ORDER BY year', $year, @stages);
    }

    say join ', ', albums_since(1990, pluck)->all;    # Parklife, The Great Escape

=head2 Stages for others

A stage of your own is a code reference, or a function that makes
one, as the canned stages are. Part 2's L<Making each kind of
part|/"Making each kind of part"> shows more ways. To work alongside
the canned stages, it should:

=over 4

=item *

a function that makes it, checking its options once;

=item *

state in a C<gather> block, so it starts afresh on each run;

=item *

a flush, for a stage that holds values, and an end, for one that
holds something to release;

=item *

C<Stop>, for one that knows no more are wanted;

=item *

a tap that returns the value it was given;

=item *

names, exports and tests.

=back

What follows is what's particular to stages for rows.

B<The shapes of a row.> A row can be an array, a hash (with the
C<ekorn_slice> attribute), or a row object (from C<results>). A stage
for others should say which it takes, or take all three, as C<pluck>
does. A stage that needs the statement's column names reads them from
the L<run's context|/"The run's context">.

B<Errors.> A function that makes a stage croaks when it's given the
wrong things, so the message names the line that called it. A module
of stages sets its C<@CARP_NOT> to DBIx::Squirrel's internal packages,
which take in the DBI's and those of the modules underneath. Then what
it croaks while a row goes through its stage is reported at the line
that asked for the result, not inside DBIx::Squirrel:

    use DBIx::Squirrel::Stages::Rows qw(pluck);

    package My::Stages {
        use DBIx::Squirrel::Errors qw(croakf);

        our @CARP_NOT = @DBIx::Squirrel::Errors::INTERNAL;

        sub prefixed ($prefix) {
            croakf 'Expected a prefix' unless defined $prefix && length $prefix;
            return sub ($value) {"$prefix$value"};
        }
    }

    say join ' ', $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck,
        My::Stages::prefixed('#'),
    )->all;
    # #Abba #Blur #Cream

    eval { My::Stages::prefixed('') };
    print $@;    # Expected a prefix at ... line ...

C<croakf> makes its message with C<sprintf>. The format is a literal,
written in the code; values go in as arguments, through C<%s> and the
like, never as the format. A format made from data does whatever its
C<%> directives say: C<%999999999s> makes a string of a gigabyte. A
literal C<%> is C<%%>.

    package My::Columns {
        use DBIx::Squirrel::Errors qw(croakf);

        sub exactly ($n) {
            croakf 'Expected %d %s, not %d%%', 3, 'columns', $n unless $n == 3;
            return $n;
        }
    }

    eval { My::Columns::exactly(50) };
    print $@;    # Expected 3 columns, not 50% at ... line ...

B<Where they go.> A stage goes where what it needs to know is. One
that needs a database, a statement, a row's column names, or the row a
result came from goes under C<DBIx::Squirrel::Stages::>. One that would
work on values from anywhere belongs with the pipeline itself, as
Part 2's L<Making each kind of part|/"Making each kind of part"> says.
The user guide's L<Decide where a stage
belongs|DBIx::Squirrel::Manual::HowTo/"Decide where a stage belongs"> says how to choose.

B<Testing.> A pipeline called with values tests a stage without a
database. Run it twice, to show it starts afresh. Then run it on rows
from an in-memory SQLite database, in each shape it takes.

B<Publishing.> Name a module of stages for its job, as
C<DBIx::Squirrel::Stages::CSV>, in a distribution named
C<DBIx-Squirrel-Stages-CSV>. Have it require the DBIx::Squirrel it was
tested with: v3.0.0 is the first with sinks, C<|> and the run's context
described in L<17. Protocols|/"17. Protocols">.

=head1 12. Errors and diagnostics

The user guide's L<chapter 12|DBIx::Squirrel::Manual::HowTo/"12. When things go wrong">.

=head2 Errors

Errors are reported at the line of your code that called
DBIx::Squirrel, never at a line inside it or the DBI. That includes
the DBI's own errors under C<RaiseError>, such as
C<DBD::SQLite::db prepare failed: near "SELEC": syntax error>, which
keep the DBI's message.

DBIx::Squirrel croaks where the DBI would return C<undef> in C<connect>,
C<prepare> and C<prepare_cached>. The error then has the message the DBI
raises under C<RaiseError>, so it reads the same whatever C<RaiseError>
is set to.

Each error names the method you called, as plain DBI does: C<do> and
the select methods, not the C<prepare> or C<execute> they call;
C<selectall_array>'s errors name C<selectall_arrayref>, as the DBI's do.

An error from a C<HandleError> callback, or one that isn't a string, is
passed on unchanged. The DBI's warnings, under C<PrintError>, its
default, are reported the same way plain DBI reports them: at your
line, naming the method you called.

    eval { $dbh->prepare('SELEC name FROM artist') };
    print $@;    # DBD::SQLite::db prepare failed: near "SELEC": syntax error at ... line ...

=head2 Diagnostics

These are the messages a user of Part 1 meets, from DBIx::Squirrel and
the stages it exports. Each is reported at the caller's line. Those
starting "Expected" say what was expected. Part 2's L<Messages of the
pipeline|/"Messages of the pipeline"> has those of what it adds.

=head3 Connecting, preparing and binding

=over 4

=item C<Expected a statement>

The statement was blank, or a reference other than those C<prepare> takes.

=item C<Expected one placeholder style, not several (%s)>

The statement mixed styles, such as C<?> and C<:name>. Each is listed as an example.

=item C<Expected placeholders numbered from 1 (%s)>

A numbered placeholder such as C<$0>.

=item C<Expected ekorn_slice to be a reference to an ARRAY or HASH>

C<ekorn_slice> was something else.

=item C<Expected a reference to a HASH or ARRAY>

The first argument after the statement in C<do>, C<iterate>, C<results> or a select method was an unblessed reference, but not to a hash or an array. An object there is a bind value.

=item C<Expected %d bind values, not %d>

A statement with numbered placeholders was given more or fewer values than its highest number; or a row given to C<execute_for_fetch> had more or fewer values than the statement has placeholders.

=item C<Expected names and values in pairs>

A statement with named placeholders was given an odd number of values.

=item C<Expected a placeholder of the statement (%s)>

A value was given for a placeholder the statement doesn't have.

=item C<Expected no list placeholder in a statement for rows of values (%s)>

C<execute_array>, C<execute_for_fetch> or C<bind_param_array> was called on a statement with a list placeholder, whose handle is prepared for lists of one length.

=item C<Expected a row of values: an array, or a hash for named placeholders>

A row given to C<execute_for_fetch>, or by C<ArrayTupleFetch>, was neither an array, nor, for named placeholders, a hash.

=item C<Expected a value for each placeholder (none for %s)>

A statement with named placeholders wasn't given a value for each name, or a statement with numbered or named placeholders was executed without values when some had none bound.

=item C<Expected one value for each placeholder (two for %s)>

A statement with named placeholders was given a value for a name twice, written with and without its sigil, as C<:id> and C<id>.

=item C<Expected bind values with a statement taking a list (%s)>

C<prepare> or C<prepare_cached> was given a statement taking a L<list|/"Lists">. Each list placeholder is named, and a C<?> is named by its position: C<...? at 2>.

=item C<Expected a placeholder to take a list everywhere or nowhere (%s)>

A placeholder was used with C<...> in one place and without it in another.

=item C<Expected no list placeholder with pg_placeholder_dollaronly (%s)>

A C<$1> placeholder took a list under DBD::Pg's C<pg_placeholder_dollaronly>.

=item C<Expected a reference to an ARRAY for a list (%s)>

A list placeholder was given a plain value, C<undef>, or a reference to something other than an array.

=item C<Expected at least one value in a list (%s)>

A list placeholder was given an empty list.

=item C<Expected plain values in a list (%s)>

A list held an unblessed reference, as C<[[1, 2]]> does to a statement whose one value is a list.

=item C<Expected %d values in a list, as prepared, not %d (%s)>

The handle of a statement taking a list was executed or bound with a list of another length.

=back

=head3 Iterators and result sets

=over 4

=item C<Expected a DBIx::Squirrel statement handle>

C<< DBIx::Squirrel::Iterator->new >> wasn't given a C<DBIx::Squirrel::st>.

=item C<Expected only one item, but there were more>

A warning: C<single> or C<take_single> found a second result, and gave the first.

=item C<Expected the statement handle's other iterator to be finished>

Another iterator over the same statement handle has results left.

=item C<Expected ekorn_result_class to be a subclass of DBIx::Squirrel::Result (%s)>

C<ekorn_result_class> named a class that isn't one.

=item C<Expected a column of the row (%s)>

C<get_column>, C<pluck> or C<as_hash> was given a name or position the row doesn't have.

=back

=head3 Pipelines

=over 4

=item C<Expected a code reference>

The block given to C<gather>, C<take_while>, C<drop_while>, C<take_if>, C<drop_if>, C<collect> or C<peek> wasn't a code reference.

=item C<Expected stage #%s, made with gather, to return a code reference or a pipeline, and optionally a flush and an end>

The block given to C<gather> for that stage returned something else.

=item C<Pipeline stage #%s failed at %s line %d:>

A stage, or its flush, died. The message it died with follows, indented. See L<When a stage dies|/"When a stage dies">.

=item C<Pipeline end of %s failed at %s line %d:>

An end died, in a run that hadn't died already: the source's, as C<the source>, or a stage's, as C<stage #2>.

=item C<The end of %s died while the run was already dying: %s>

A warning: an end died in a run that had died already. The run's own error is the one thrown.

=item C<Stop used outside a pipeline>

C<Stop> was called where no pipeline was running to catch it.

=back

=head3 Canned stages and sinks

=over 4

=item C<Expected a count of 0 or more>

C<take> or C<drop> was given something other than a whole number.

=item C<Expected a batch size of 1 or more>

C<batch> was given something other than a whole number above 0.

=item C<Expected a column, by name or position>

C<pluck> was given an undefined column, or an empty name.

=item C<Expected a column name>

C<as_hash> was given an undefined or empty column name.

=item C<Expected one column to pluck, not %d>

C<pluck>, given no column, had a row of more than one column, or of none.

=item C<Expected a statement to read, for the column names>

C<as_hash>, or C<pluck> with a name for an array row or a position for a hash row, ran where no statement was being read, such as in a pipeline called with values.

=item C<Expected a row: an array, a hash or a row object>

C<pluck> or C<as_hash> was given a value that isn't a row.

=item C<Expected a reference to a scalar>

C<count_into> was given something else.

=item C<Expected an open filehandle>

C<dump_to> was given something else.

=back

=head3 Sugar

=over 4

=item C<Expected the arguments to connect to %s in an ARRAY>

A database's definition, given to C<use>, wasn't an array reference.

=item C<Expected the statement %s in an ARRAY>

A statement's definition, given to C<use>, wasn't an array reference.

=item C<Expected a name for a database (%s)>

The name can't be a function's.

=item C<Expected a name for a statement (%s)>

The name can't be a function's.

=item C<Expected a database defined once (%s)>

The name was given to another database already.

=item C<Expected a database named %s>

C<database> was given a name no database has.

=item C<Expected a database and a statement for %s>

A statement's definition didn't name its database, or have its SQL.

=item C<Expected only stages after the statement for %s: code references, pipelines or their names, or objects offering a stage's role method>

A statement's definition had something after the statement and its attributes that's neither a stage nor a pipeline's name.

=item C<Expected no function of the name in %s already (%s)>

The package has a function of that name already, such as a stage it imported.

=back

=head1 Differences from plain DBI

Where DBIx::Squirrel and plain DBI do the same thing, they give the
same result. These are the places they differ.

=over 4

=item Placeholders

B<Plain DBI:> C<?>, and whatever the driver adds.

B<DBIx::Squirrel:> C<?>, C<?1>, C<:1>, C<$1>, C<:name> and C<$name>, rewritten as C<?> for the DBI.

=item Numbered and named placeholders

B<Plain DBI:> Bound by position.

B<DBIx::Squirrel:> Bound once, by number or name, wherever they appear.

=item Lists, as for C<IN>

B<Plain DBI:> A C<?> for each value, written out.

B<DBIx::Squirrel:> C<...?>, C<...$1> or C<...:name>, written as a C<?> for each value of the list given.

=item C<connect> failing

B<Plain DBI:> Returns C<undef>, unless C<RaiseError>.

B<DBIx::Squirrel:> Always croaks, with the DBI's C<RaiseError> message.

=item C<prepare> failing

B<Plain DBI:> Returns C<undef>, unless C<RaiseError>.

B<DBIx::Squirrel:> Always croaks, with the DBI's C<RaiseError> message.

=item Attributes in C<do> and the select methods

B<Plain DBI:> Required, or C<undef>, before the bind values.

B<DBIx::Squirrel:> May be left out.

=item A lone array reference of bind values

B<Plain DBI:> A value.

B<DBIx::Squirrel:> The values in it, except for a statement taking one value that's a list, or with DBD::Pg.

=item Where errors and warnings are reported

B<Plain DBI:> The line inside the module that called the DBI.

B<DBIx::Squirrel:> The line of your code that called DBIx::Squirrel.

=item Statements

B<Plain DBI:> A string.

B<DBIx::Squirrel:> A string, lines in an array reference, a code reference returning either, or a statement handle.

=item Executing an active statement

B<Plain DBI:> Left to the driver.

B<DBIx::Squirrel:> The same, or finished first with C<ekorn_finish_active>.

=item Executing with placeholders unbound

B<Plain DBI:> Left to the driver, which most read as C<NULL>.

B<DBIx::Squirrel:> Croaks, for numbered and named placeholders: C<Expected a value for each placeholder (none for id)>.

=item C<execute_array>, C<execute_for_fetch> and C<bind_param_array>

B<Plain DBI:> For C<?>, and other styles as far as the driver reads them.

B<DBIx::Squirrel:> For every style: a row's values in placeholder order, or a hash by name; C<bind_param_array> by name.

=item Stages after the select methods' values

B<Plain DBI:> None.

B<DBIx::Squirrel:> What the DBI gives is pushed through them.

=item Iterators, result sets, pipelines

B<Plain DBI:> None.

B<DBIx::Squirrel:> C<iterate>, C<results>, sinks, C<|> and C<@{}>, C<pipe>, C<tap> and the Sugar.

=back

=head1 Where you can stop

That's DBIx::Squirrel: placeholders in any style, values checked
before they reach the database, the iterator, and stages beside the
query, on handles that are still the DBI's. If that does what you
need, nothing in Part 2 is needed.

=head1 Part 2: With Ekorn::Pipeline

Part 1 is the round trip to the database. Part 2 is data crossing the
database's edge: query results written to files, JSON and CSV, loaded
from them in batches, or sent to several places in one run. That's
done with L<Ekorn::Pipeline|Ekorn::Pipeline>,
the pipeline behind DBIx::Squirrel's stages, which moved into a
distribution of its own in 2026, as L<the guide's Part
2|DBIx::Squirrel::Manual::HowTo/"Part 2: With Ekorn::Pipeline"> tells. This part describes what
the two do together: importing both from one module, sinks, pipelines,
operators, and the protocols between them.

=head1 13. Import everything from one place

    use DBIx::Squirrel::Tooling qw(:all);               # everything below
    use DBIx::Squirrel::Tooling qw(:stages :sinks);     # or some tags
    use DBIx::Squirrel::Tooling qw(pluck keep_all);     # or some names

What a caller uses to do work is made in several modules, each
described below. DBIx::Squirrel::Tooling exports all of it, from one
place, by tags named as Ekorn::Pipeline::Tooling's are, with
DBIx::Squirrel's own C<:rows> and C<:context> besides:

=over 4

=item C<:core>

B<Holds:> C<Stop>, C<is_stop>, C<gather>, C<is_stage>

B<Made in:> L<Stop|/"6. Stopping early">, L<Gather|/"7. Gathering: stages made for each run">, Ekorn::Pipeline

=item C<:flow>

B<Holds:> C<take>, C<take_first>, C<take_last>, C<take_single>, C<take_if>, C<take_while>, C<drop>, C<drop_if>, C<drop_while>

B<Made in:> L<Stages::Flow|/"Taking and dropping">

=item C<:batch>

B<Holds:> C<batch>, C<collect>

B<Made in:> L<Stages::Batch|/"Batching and collecting">

=item C<:taps>

B<Holds:> C<peek>, C<count_into>, C<dump_to>, C<tee>

B<Made in:> L<Stages::Taps|/"Canned stages">

=item C<:rows>

B<Holds:> C<pluck>, C<as_hash>

B<Made in:> L<Stages::Rows|/"Canned stages">

=item C<:stages>

B<Holds:> C<:flow>, C<:batch>, C<:taps> and C<:rows>

=item C<:context>

B<Holds:> C<iterator>, C<result_number>, C<result_original>

B<Made in:> L<Context|/"Context">

=item C<:sources>

B<Holds:> C<from_array>, C<from_fh>, C<from_file>, C<counter>

B<Made in:> Ekorn::Pipeline::Sources

=item C<:sinks>

B<Holds:> C<count_items>, C<keep>, C<keep_all>, C<keep_first>, C<keep_last>, C<keep_single>, C<to_fh>, C<to_file>

B<Made in:> L<Sinks|/"14. Sinks">

=item C<:json>

B<Holds:> C<from_json>, C<from_jsonl>, C<to_json>, C<to_jsonl>

B<Made in:> Ekorn::Pipeline::JSON

=item C<:csv>

B<Holds:> C<from_csv>, C<to_csv>

B<Made in:> Ekorn::Pipeline::CSV

=item C<:words>

B<Holds:> C<pipeline>, C<stage>, C<gather>, C<source>, C<generator>, C<yield>, C<sink_one>, C<sink_many>

B<Made in:> Ekorn::Pipeline::Factories

=item C<:all>

B<Holds:> all of the above

=back

=over 4

=item *

B<Nothing by default.> Ask for tags, names, or both. An unknown tag
or name is Exporter's error: it warns C<"%s" is not defined in
%DBIx::Squirrel::Tooling::EXPORT_TAGS>, or C<"%s" is not exported by
the DBIx::Squirrel::Tooling module>, and dies C<Can't continue after
import errors>.

=item *

B<The same subs.> Each name is the sub its own module exports,
prototype and all, so C<take_if { ... }> and C<stage { ... }> parse as
they do imported from there, and importing a name from both does no
harm.

=item *

B<DBIx::Squirrel's, where both export a name.> Each name comes from
DBIx::Squirrel's own module where it has one, and from
Ekorn::Pipeline's only where it has none. Today each name both
export is the same sub, so importing Ekorn::Pipeline::Tooling too,
in either order, gives the same subs. A test fails if that changes.

=item *

B<What's left out.> What's for extending DBIx::Squirrel rather than
using it, such as C<croakf>, from DBIx::Squirrel::Errors, and
C<is_sink>, from Ekorn::Pipeline; L<the
Sugar|/"9. Sugar: a function for each database and statement">, whose
C<use> makes functions; and L<C<E<verbar>>|/"16. Operators: E<verbar> and @{}">, which only
C<use Ekorn::Pipeline::Operators> puts in force, in its own scope.

=item *

B<JSON.pm's names.> JSON exports a C<from_json> and a C<to_json> of
its own, by default, so a module using both imports C<:all> or C<:json>
from only one of them, or calls the other's by its full name.

=item *

B<Text::CSV.> C<:csv>'s names need it, but load it only when one
is first called, so C<:csv> and C<:all> import without it.

=item *

B<Its own lists.> What each tag holds is the list here, not
whatever Ekorn::Pipeline::Tooling's tag of the same name holds. A
name Ekorn::Pipeline adds comes into a tag only in a release of
DBIx::Squirrel that adds it, so a newer Ekorn::Pipeline changes
nothing a caller imports.

=item *

B<What a tag holds is public.> A name may be added to one in a
release that only adds, but is dropped or renamed only in a major
release.

=back

=head1 14. Sinks

The user guide's L<chapter
15|DBIx::Squirrel::Manual::HowTo/"15. Sinks: saying what you want back">.

A sink is a last stage that says what a run gives. Given last to
C<iterate>, C<results>, a Sugar function, or a select method, it makes
the call read the run through and give the sink's result, not an
iterator. The sinks are Ekorn::Pipeline's, from
Ekorn::Pipeline::Sinks, which exports none by default, and
DBIx::Squirrel::Tooling's C<:sinks> exports them all:

    use Ekorn::Pipeline::Sinks qw(keep_all keep_first keep_last keep_single keep count_items to_file to_fh);

=over 4

=item C<keep_all>

B<Gives:> every result, as a list; or, where one value is asked for, an array reference of them

B<Stops the run early?:> no

=item C<keep_first>

B<Gives:> the first result, or C<undef> if none

B<Stops the run early?:> yes

=item C<keep_last>

B<Gives:> the last result, reading every one to find it, or C<undef> if none

B<Stops the run early?:> no

=item C<keep_single>

B<Gives:> the one result, or C<undef> if none; at a second, a warning, C<Expected only one item, but there were more>, and the first

B<Stops the run early?:> at a second

=item C<keep($n)>

B<Gives:> the first C<$n> results, as a list, or an array reference where one value is asked for

B<Stops the run early?:> yes, at C<$n>

=item C<count_items>

B<Gives:> how many results there were

B<Stops the run early?:> no

=item C<to_file($path)>

B<Gives:> writes each result to the file, a line each, and gives how many; it closes the file however the run ends

B<Stops the run early?:> no

=item C<to_fh($fh)>

B<Gives:> prints each result to your filehandle, a line each, and gives how many; you close it

B<Stops the run early?:> no

=back

A sink of many, C<keep_all> or C<keep>, never gives a count: for that,
use C<count_items>. An empty result is an empty array reference, which
is true, so test it with C<@$rows>.

Ekorn::Pipeline::JSON's C<to_json> and C<to_jsonl>, from Tooling's
L<C<:json>|/"13. Import everything from one place">, are sinks too, given a
C<file> or an C<fh>: they write each result as JSON, and give how many.

    use DBIx::Squirrel::Tooling qw(pluck keep_all keep_last keep_single keep count_items);

    my @names = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        keep_all,
    );
    my $names = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        keep_all,
    );
    say "@names";            # Abba Blur Cream
    say scalar @$names;      # 3

    say $dbh->iterate(
        'SELECT name FROM track ORDER BY plays',
        pluck('name'),
        keep_last,
    );
    # Dancing Queen

    say $dbh->iterate(
        'SELECT name FROM artist WHERE id = ?', 2,
        pluck('name'),
        keep_single,
    );
    # Blur

    say join ', ', $dbh->iterate(
        'SELECT name FROM track ORDER BY plays DESC',
        pluck('name'),
        keep(2),
    );
    # Dancing Queen, Sunshine of Your Love

    say $dbh->iterate('SELECT title FROM album', sub { split ' ', $_->[0] }, count_items);    # 7

The iterator's methods and the sinks overlap: C<all> and C<keep_all>,
C<first> and C<keep_first>, C<single> and C<keep_single>. A method takes
what's left of an iterator you have; a sink says, in the call, what it
gives, and is the only way to have a count, the last, the first few,
or a file. C<all> without stages is quicker than C<keep_all>, as it
fetches every row in one go.

Ekorn's reference has the sinks in full, and how to write one, in
L<Sinks|Ekorn::Pipeline::Manual::Reference/"Sinks: Ekorn::Pipeline::Sinks">.

C<keep_first>, C<keep_last> and C<keep_single> are the sinks of the
stages C<take_first>, C<take_last> and C<take_single>, so the stages are
for a pipeline that goes on after them. After C<as_hash> with names,
give C<to_csv> the same names as its header, C<< header => [qw(name
plays)] >>, as the run's context still names every column the statement
has, so C<< header => 1 >> writes a column for each, empty for those left
out.

=head1 15. Pipelines

The user guide's L<chapter
17|DBIx::Squirrel::Manual::HowTo/"17. Building pipelines from pipelines">.

The pipeline is
L<Ekorn::Pipeline|Ekorn::Pipeline>'s. It
began here, and is now a distribution of its own, so that any function
can take stages from its caller. DBIx::Squirrel uses it as it is: a
pipeline is made with C<< Ekorn::Pipeline->new >>, and the handles' C<pipe>
and C<tap> are Ekorn::Pipeline::Pipes'. Loading it doesn't load the
DBI, so a pipeline works in code that has nothing to do with a
database.

DBIx::Squirrel keeps its own names for the modules of functions:
C<DBIx::Squirrel::Stop>, C<DBIx::Squirrel::Gather>, and the stages in
C<DBIx::Squirrel::Stages::Flow>, C<Batch> and C<Taps>. Each exports
Ekorn's functions from a list of DBIx::Squirrel's own, so a function
added to Ekorn::Pipeline reaches DBIx::Squirrel's modules only once
it's added to that list, and documented here. The objects are Ekorn's:
a stop is an C<Ekorn::Pipeline::Stop>, and a stage made with C<gather>
an C<Ekorn::Pipeline::Gather>. DBIx::Squirrel subclasses none of
Ekorn's classes.

Ekorn::Pipeline's
L<reference|Ekorn::Pipeline::Manual::Reference>
describes the pipeline in full, and its L<user
guide|Ekorn::Pipeline::Manual::HowTo>
has recipes for any values. This chapter keeps to what DBIx::Squirrel
does with it.

=head2 Making and running a pipeline

    use Ekorn::Pipeline;

    my $p       = Ekorn::Pipeline->new(@stages);
    my @results = $p->(@values);              # push: values in, a list out
    my $next    = $p->iterator($source);      # pull: one value per call
    my @stages  = $p->stages;

A pipeline is an object that can be called as a code reference. Called
with values, it returns what comes out of the last stage: every value
in list context; in scalar context, a sink's result, if a sink is
last, or how many values came out. C<iterator> returns an iterator, an
object called as a code reference, handing out those values one per
call, from a source; a DBIx::Squirrel iterator is a source (L<15.
Protocols|/"The iterator as a source">). C<stages> returns the
pipeline's stages, in order, a pipeline given as a stage appearing as
the stages it was made of.

    use DBIx::Squirrel::Tooling qw(pluck);
    use Ekorn::Pipeline;

    my $shout = Ekorn::Pipeline->new(
        sub {uc},
        sub {"$_!"},
    );
    say join ' ', $shout->('hello', 'world');    # HELLO! WORLD!

    my $next  = Ekorn::Pipeline->new(pluck)->iterator($dbh->iterate('SELECT name FROM artist ORDER BY id'));
    my @names;
    while (my($name) = $next->next) { push @names, $name }
    say "@names";    # Abba Blur Cream

=head2 A pipeline as a stage

A pipeline can go wherever a stage goes: in another pipeline, or given
to C<iterate>, C<results>, an iterator's C<reset>, C<pipe>, C<tap>, a
select method, or a Sugar function, for a database or a statement. Its
stages run in its place, as if written out there, so a C<take> inside
it limits the whole run:

    use DBIx::Squirrel::Tooling qw(drop_if pluck take);
    use Ekorn::Pipeline;

    my %on_my_phone = map { $_ => 1 } 'Dancing Queen', 'Parklife', 'Sunshine of Your Love';
    my $to_copy = Ekorn::Pipeline->new(
        drop_if { $on_my_phone{ $_->[0] } },
        pluck('name'),
    );
    my $sql = 'SELECT name, plays FROM track ORDER BY plays DESC';
    say join ', ', $dbh->iterate($sql, $to_copy)->all;
    # Girls & Boys, Knowing Me, Knowing You, Country House
    say join ', ', $dbh->iterate(
        $sql,
        $to_copy,
        take(1),
    )->all;
    # Girls & Boys

Make a stage that counts or remembers with
L<C<gather>|/"7. Gathering: stages made for each run">. A plain closure is
the same code reference wherever it goes, so its state is shared by
every run it's in.

=head2 Named pipelines

    Ekorn::Pipeline->named($name => @stages);
    use Ekorn::Pipeline::Factories qw(pipeline);
    my $p = pipeline($name, @more_stages);

C<< Ekorn::Pipeline->named >> names a pipeline for the rest of the program,
in the package that names it, unless the name is qualified, as
C<My::Module::clean>. C<pipeline>, from Ekorn::Pipeline::Factories,
makes a pipeline of stages and names, looked up in its caller's
package as it's made. A name given alone gives the pipeline named, so
its stages are numbered where it stands. The L<Sugar's
definitions|/"Defining them as the program runs"> take names too, and
the Sugar's L<C<pipeline>|/"Defining them on use"> names pipelines as
well. Ekorn's reference has the rules, in L<Named
pipelines|Ekorn::Pipeline::Manual::Reference/"Named pipelines">.

    use DBIx::Squirrel::Tooling qw(pipeline take);
    use Ekorn::Pipeline;

    Ekorn::Pipeline->named(first_column => sub { $_->[0] });
    say join ' ', $dbh->iterate('SELECT name FROM artist ORDER BY id', pipeline('first_column', take(2)))->all;    # Abba Blur

=head2 pipe and tap

Database and statement handles both have these methods, from
Ekorn::Pipeline::Pipes. Each runs the handle itself through stages:
the first stage is called with the handle, and the rest with what
comes out of the stage before. On a statement handle, the statement
handle goes through the stages instead.
L<pipe and
tap|Ekorn::Pipeline::Manual::Reference/"pipe and tap: Ekorn::Pipeline::Pipes">,
in Ekorn's reference, says how to give a class of your own the same.

C<pipe> is for work that starts from the handle and ends in values: it
returns what a pipeline of the same stages gives: in list context, what
comes out of the last stage; in scalar context, how many results came
out, or a sink's result. For one value, read it in list context, or
end with C<keep_first>. Until v4.0.0, in scalar context, C<pipe> gave the
first result instead, unlike a pipeline. A stage that dies makes it
croak, naming the stage (see L<When a stage dies|/"When a stage dies">).

    my @names = $dbh->pipe(
        sub ($dbh) { @{ $dbh->selectcol_arrayref('SELECT name FROM artist ORDER BY id') } },
        sub {uc},
    );
    say "@names";    # ABBA BLUR CREAM

    my $sth = $dbh->prepare('SELECT name FROM artist WHERE id = ?');
    my ($name) = $sth->pipe(sub ($sth) { $sth->execute(2); $sth->fetchrow_arrayref->[0] });
    say $name;    # Blur

C<tap> is for a side job in the middle of a chain of method calls: it
drops what comes out, and returns the handle, however the stages end,
so the chain carries on after it.

    my $n = $dbh->tap(sub ($dbh) { say 'tapped ', ref $dbh })->selectrow_array('SELECT COUNT(*) FROM artist');
    say $n;
    # tapped DBIx::Squirrel::db
    # 3

=head2 When a stage dies

If a stage dies, the call that asked for the result croaks, at your
line. The message names the stage by its place, from C<#1>, and indents
the stage's own message below. A stage inside a pipeline given as a
stage is named by its place in each: C<#2.3> is the third stage of the
pipeline given as stage #2. A stage of a named pipeline gives the name
and its place there too: C<#2.2 (main::fussy#2)>. An exception object
is passed on unchanged.

    my $it = $dbh->iterate(
        'SELECT name FROM artist',
        sub {$_},
        sub { die "no names today\n" },
    );
    eval { $it->next };
    print $@;
    # Pipeline stage #2 failed at ... line ...:
    #     no names today

    say $it->ended;    # died
    say scalar(() = $it->next);    # 0

Once a stage dies, its run has ended. An iterator then returns nothing
more: C<next> returns an empty list on every call after, and C<all>
returns nothing. No more rows are fetched, no flush is called, and the
statement is finished. An end is still called, told C<died>. C<reset>
runs the statement again, from the start. To pass over a value a stage
can't handle, the stage catches its own error and returns nothing for
it, as L<What a stop is|/"What a stop is"> shows.

=head2 The Sugar's pipelines

    use DBIx::Squirrel::Tooling qw(pipeline);

    @results = shouted(@values);
    @results = shouted(@values, $pipeline);
    $it      = music($statement, @bind_values, pipeline('shouted'));
    $it      = artist_names(@bind_values, pipeline('shouted'));

Each pipeline after C<pipeline>, on C<use>, is named in the package, and
the package gets a function of its name. The function runs the values
it's given through the pipeline, and returns what comes out: a list in
list context, and in scalar context a sink's result, or how many values
came out. A pipeline given last adds its stages to that call.

A string given to a database's or a statement's function is a bind
value, so to use a named pipeline for one call, give the pipeline
itself: C<pipeline>, given a name alone, returns the pipeline of that
name.

    use DBIx::Squirrel::Tooling qw(pipeline keep_all pluck);
    use DBIx::Squirrel::Sugar
        statement => {
            loud_names => [music => 'SELECT name FROM artist ORDER BY id', pluck, 'shouted'],
        },
        pipeline => {shouted => [sub {uc}]};

    say join ' ', loud_names keep_all;                           # ABBA BLUR CREAM
    say join ' ', shouted('abba', 'blur');                       # ABBA BLUR
    say join ' ', artist_names pipeline('shouted'), keep_all;    # ABBA BLUR CREAM

    my @loud = music 'SELECT name FROM artist ORDER BY id',
        pluck('name'), pipeline('shouted'), keep_all;
    say "@loud";    # ABBA BLUR CREAM

A stage in a Sugar statement's definition can be a pipeline's
B<name>, as Ekorn::Pipeline names them with C<named>: words joined by
C<::>. A name is looked up as the statement is defined, in the package
defining it, unless it's qualified, as C<My::Module::clean>, and stands
in its place among the stages. So it must be defined first, and one
that isn't croaks then: C<No pipeline named main::clean>. On C<use>, the
definition is made as the program compiles, so give the pipeline after
C<pipeline>, in the same C<use> or one before it, or name it in a
C<BEGIN> block above it.

=head1 16. Operators: | and @{}

The user guide's L<chapter 20|DBIx::Squirrel::Manual::HowTo/"20. Chaining with E<verbar> and @{}">.

    use Ekorn::Pipeline::Operators;

    $result = $it | @stages... | $sink;
    $chain  = $it | $stage;
    @values = @$it;

An iterator, and so a result set, overloads C<|> and C<@{}> with
Ekorn::Pipeline::Operators' C<chain> and C<drain>, as Ekorn's own
sources do. They're in force only where
C<use Ekorn::Pipeline::Operators> is in scope. Elsewhere, both croak:
C<Expected use Ekorn::Pipeline::Operators in scope, for |>.
DBIx::Squirrel loads Operators with an empty import list, so it's
there, but in force only where you say.

=over 4

=item *

C<$it | $stage> gives a chain: the iterator's results through the
stage, which C<|> can extend, and which is a source.

=item *

C<$it | ... | $sink> gives the sink's result.

=item *

C<@$it>, or C<@{ $chain }>, gives every result.

=back

**C<|> always gives one value.** Perl calls an operator for one value,
so a chain ending in C<keep_all> gives an array reference, even
assigned to an array: C<my @rows = $it | keep_all> has one element. Use
C<@{ $it | keep_all }>, or give the stages and sink to C<iterate> as
arguments.

B<Each use is a run of its own,> from the first row, through the
iterator's stages. So C<< $it->[0] >>, C<scalar @$it> and C<$#$it> read every
row to give one row, a count or an index; two uses run the statement
twice; and C<for (@$it)> reads every row before the loop starts.

B<The run it starts is the iterator's.> It ends a run the iterator
had going, so C<next> returns nothing after, and C<ended> says how the
C<|> or C<@{}> run ended, until C<reset>.

    use DBIx::Squirrel::Tooling qw(pluck keep_all count_items);
    use Ekorn::Pipeline::Operators;

    my $it    = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck('name'));
    my $names = $it | keep_all;
    say "@$names";                  # Abba Blur Cream
    say $it | count_items;          # 3
    say "@$it";                     # Abba Blur Cream
    say "@{ $it | sub {lc} }";      # abba blur cream

    my @one = $it | keep_all;
    say scalar @one;                # 1

A chain run only for its sink's effect, written as a statement of its
own, runs, but Perl warns "Useless use of numeric bitwise or (|) in
void context" as it compiles the line, before any operator is called.
Keep the result: C<my $n = $it | to_file($path)>.

=head1 17. Protocols

What other code can rely on: the contracts between DBIx::Squirrel and
Ekorn::Pipeline, and between a statement's run and the stages reading
it. They're Ekorn::Pipeline's protocols, as DBIx::Squirrel keeps them;
Ekorn's reference describes the protocols themselves, in L<Delivering
parts for
Ekorn|Ekorn::Pipeline::Manual::Reference/"Delivering parts for Ekorn">.

=head2 The iterator as a source

A C<DBIx::Squirrel::Iterator>, and so a result set, is a source, as
Ekorn::Pipeline takes one, by offering C<EKORN_SOURCE>, so a pipeline's
C<iterator>, a chain made with C<|>, and C<@{}> can read it. Each run
reading it starts a fresh run of the statement, from its first row:

=over 4

=item *

the statement is executed again, finishing it first if it's active,
as C<reset> does, with the iterator's bind values;

=item *

the rows go through the iterator's own stages before they leave it,
so a pipeline reading it gets its results, not its rows;

=item *

the run's context is the statement's (see below);

=item *

the run is the iterator's: one it had going ends, and C<ended> says
how this one ended;

=item *

if another iterator over the same statement handle has results left,
it croaks, C<Expected the statement handle's other iterator to be
finished>, rather than take the handle from under it.

=back

A run reading the iterator reads on even if the iterator itself is let
go first, and finishes the statement when it ends.

    use DBIx::Squirrel::Tooling qw(pluck);
    use Ekorn::Pipeline;

    my $it   = $dbh->iterate('SELECT name FROM artist ORDER BY id', pluck);
    my $next = Ekorn::Pipeline->new(sub {uc})->iterator($it);
    undef $it;
    my @names;
    while (my($name) = $next->next) { push @names, $name }
    say "@names";    # ABBA BLUR CREAM

=head2 The run's context

A run reading a statement, whether the iterator's own or a pipeline's
reading it, has the statement's context, which a stage asks for with
C<Ekorn::Pipeline::run_context()>. It's a hash reference:

=over 4

=item C<statement>

The statement handle, a C<DBIx::Squirrel::st>.

=item C<columns>

A reference to an array of the statement's column names, as C<fetchrow_hashref> keys them, following C<FetchHashKeyName>, read when the statement was executed.

=item C<row>

The row the statement gave last, as fetched, or as a row object for a result set: the row the value a stage is working on came from. C<undef> once the run has ended.

=back

A run whose context has a C<statement> that's a C<DBIx::Squirrel::st> is
reading a statement; any other run, such as a pipeline called with
values, has some other context, or none. C<pluck> and C<as_hash> read
it, and so can a stage of yours; C<result_original> gives the same
row, which the source also gives Ekorn as its original. While a flush
gives its values, which come from every row, not one,
C<Ekorn::Pipeline::ending()> is true, and the row is no value's;
C<result_original> gives C<undef> then.

    my $columns = sub ($row) {
        my $names = Ekorn::Pipeline::run_context()->{columns};
        return join ', ', map {"$names->[$_]=$row->[$_]"} keys @$names;
    };
    say join '; ', $dbh->iterate('SELECT id, name FROM artist ORDER BY id', $columns)->all;    # id=1, name=Abba; id=2, name=Blur; id=3, name=Cream

The context is the run's: a pipeline called inside a stage has its
own, which has no row unless it too reads a statement.

In Part 2's runs, C<result_number> counts every run's results: a chain
made with C<|>, and a pipeline of yours, each counting its own.
C<result_original> gives a statement's row in any run reading one,
chains included: it's Ekorn::Pipeline::Context's, and the statement's
source gives Ekorn the row as its original, which Ekorn passes through
chains. In a run reading no statement, it's the value the run's source
gave, or that was pushed. C<iterator> works in a sink given last to the
call that made the iterator, too.

=head2 What a call takes as stages

C<iterate>, C<results>, an iterator's C<reset>, the select methods,
C<pipe>, C<tap> and the Sugar's functions take stages at the end of
their arguments. A stage is whatever Ekorn::Pipeline's C<is_stage> is
true of: a code reference, a pipeline, or one of Ekorn's stage
objects. Those include stages made with C<gather>, Ekorn's words and
the canned stages, and its sinks. Anything else is a bind value, so an
object of your own given as a value stays one. A sink, if one is last,
says what the call gives (see L<14. Sinks|/"14. Sinks">). Only a Sugar
statement's definition takes pipelines' names, as strings.

=head2 What a gather's block returns

A C<gather> block, Ekorn's protocol for a part made for each run,
returns its step, flush and end, as a list or by name in a hash
reference (see L<gather|/"gather">). DBIx::Squirrel adds nothing to it;
Ekorn's reference has it in full, in
L<gather|Ekorn::Pipeline::Manual::Reference/"gather">.

=head2 Finding the stages at the end of a list

To find the stages at the end of a list of arguments, test each from
the end with C<is_stage>, Ekorn::Pipeline's, which Tooling's C<:core>
holds. It's true of code references, pipelines and Ekorn's stage
objects, and false of strings and other values. A sink given last is
a stage too, so a caller can end with one:

    use DBIx::Squirrel::Tooling qw(count_items is_stage);

    say albums_since(1990, count_items);              # 2
    say is_stage(sub {1}) ? 'a stage' : 'a value';    # a stage
    say is_stage('name') ? 'a stage' : 'a value';     # a value

=head2 What a stop is

A stop is an exception, an C<Ekorn::Pipeline::Stop>, which the pipeline
catches. DBIx::Squirrel::Stop isn't a class: it exports Ekorn's
C<Stop>. C<< Ekorn::Pipeline::Stop->throw(@values) >> does what C<Stop> does,
without importing it. A subclass of your own is a subclass of
C<Ekorn::Pipeline::Stop>, and stops a pipeline as C<Stop> does. Ekorn's
reference says what a stop holds, in L<The stop
object|Ekorn::Pipeline::Manual::Reference/"The stop object">.
A stage made with C<gather> is an C<Ekorn::Pipeline::Gather>.

So C<is_stop> is the same test as this one, which names the class:

    use experimental qw(try);
    use DBIx::Squirrel::Tooling qw(Stop);

    my @safe = $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        sub ($row) {
            try {
                Stop() if $row->[0] eq 'Cream';
                return uc $row->[0];
            }
            catch ($e) {
                die $e if $e isa 'Ekorn::Pipeline::Stop';
                return 'unknown';
            }
        },
    )->all;
    say "@safe";    # ABBA BLUR

=head2 Settings of the pipeline

C<$DBIx::Squirrel::Stages::Taps::DumpSecrets>, which has C<dump_to>
write each value in full, is Ekorn::Pipeline's
C<$Ekorn::Pipeline::Stages::Taps::DumpSecrets> under DBIx::Squirrel's
name, tied to it, so setting either, with C<local> or without, sets
both. Ekorn's message, when Text::Redact::Secrets is installed but
can't be used, names Ekorn's.

=head2 Messages of the pipeline

These are the messages of what Part 2 adds, from DBIx::Squirrel and
Ekorn::Pipeline, as its users meet them. Each is reported at the
caller's line.

=over 4

=item C<Expected use Ekorn::Pipeline::Operators in scope, for %s>

C<|> or C<@{}> was used on an iterator where the operators aren't in force.

=item C<Expected stage #%d to be a stage: a code reference, a pipeline, or an object offering a stage's role method>

Something passed as a stage to a pipeline, C<pipe> or C<tap> wasn't one. No stage runs.

=item C<Expected stage #%d to be a stage: a code reference, a pipeline or its name, or an object offering a stage's role method>

Something given to C<pipeline>, or to C<named>, wasn't a stage or a pipeline's name.

=item C<Expected a source: a code reference, or an object offering EKORN_SOURCE>

A pipeline's C<iterator> was given something it can't read.

=item C<No pipeline named %s>

A name, in a Sugar statement's definition or given to C<pipeline>, has no pipeline.

=item C<Expected database, pipeline or statement, not %s>

C<use DBIx::Squirrel::Sugar> was given something else.

=item C<Expected the pipelines after pipeline in a HASH or an ARRAY of pairs>

What came after C<pipeline> was something else. It, and the next, are Ekorn::Pipeline::Sugar's.

=item C<Expected the pipelines after pipeline in pairs of a name and an ARRAY>

The array reference after C<pipeline> had an odd number of items.

=item C<Expected a count of 0 or more>

C<keep> was given something other than a whole number.

=item C<Expected an open filehandle>

C<to_fh> was given something else.

=item C<Expected only one item, but there were more>

A warning: C<keep_single> found a second result, and gave the first.

=back

=head1 Making each kind of part

This section is for developers making parts for DBIx::Squirrel's
users. It says what a statement's run gives each piece of a part. Then
it works through an example of each kind DBIx::Squirrel adds to, made
with a word and as a class of your own. The protocol itself, what each
piece is called with, what it returns, and the rules every part keeps,
is Ekorn::Pipeline's, and its reference has it in full, in L<Making each
kind of part|Ekorn::Pipeline::Manual::Reference/"Making each kind of part">.
Each example runs against the examples' database, and its comments say
what it prints.

=head2 What a statement's run gives each piece

A part reading a statement, through C<iterate>, C<results>, a Sugar
function, C<|>, or a pipeline of yours reading an iterator, finds the
statement in the L<run's context|/"The run's context">. What each piece
finds there, and what L<Context|/"Context">'s functions give it:

=over 4

=item B<set-up>

**C<Ekorn::Pipeline::run_context()>:** nothing: the run hasn't read the statement yet

**C<result_original>:** C<undef>

**C<result_number>:** C<undef>

=item a stage's B<step>

**C<Ekorn::Pipeline::run_context()>:** C<statement>, C<columns>, and the C<row> this value came from

**C<result_original>:** the row

**C<result_number>:** the number of the result being made

=item a stage's B<flush>

**C<Ekorn::Pipeline::run_context()>:** C<statement> and C<columns>; C<ending()> is true, and the row is no value's

**C<result_original>:** C<undef>

**C<result_number>:** the number of the first value it gives

=item a sink's B<step>

**C<Ekorn::Pipeline::run_context()>:** C<statement>, C<columns> and C<row>, as for a stage

**C<result_original>:** the row

**C<result_number>:** the number of the value it's given

=item a sink's B<flush>

**C<Ekorn::Pipeline::run_context()>:** as for a stage's flush

**C<result_original>:** C<undef>

**C<result_number>:** the results so far, plus one

=item an B<end>

**C<Ekorn::Pipeline::run_context()>:** C<statement> and C<columns>; the C<row> is C<undef>

**C<result_original>:** C<undef>

**C<result_number>:** C<undef>

=back

So a stage that needs the statement's columns reads them in its step,
the first time it's called in the run, and keeps them in a variable of
the set-up, as C<pluck> and C<as_hash> do. It can't read them in the
set-up, which runs before the statement does.

=head2 A stage for rows, with the word C<gather>

A stage that gives each row, an array, as its columns and values, and
says how many rows there were once they run out. It croaks if what it
reads isn't a statement, in a module of stages, as L<Stages for
others|/"Stages for others"> says, so the message names the caller's
line:

    use DBIx::Squirrel::Tooling qw(take);

    package My::Stages {
        use DBIx::Squirrel::Errors qw(croakf);
        use DBIx::Squirrel::Tooling qw(gather);

        our @CARP_NOT = @DBIx::Squirrel::Errors::INTERNAL;

        sub labelled () {
            return gather {
                my($columns, $n) = (undef, 0);    # this run's
                return {
                    step => sub ($row) {
                        $columns //= do {
                            my $context = Ekorn::Pipeline::run_context();
                            croakf 'Expected a statement to read, for its columns'
                                unless ref $context eq 'HASH'
                                && $context->{statement} isa 'DBIx::Squirrel::st';
                            $context->{columns};
                        };
                        $n++;
                        return join ', ', map {"$columns->[$_]=$row->[$_]"} 0 .. $#$columns;
                    },
                    flush => sub () {"($n rows)"},
                };
            };
        }
    }

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Stages::labelled,
    )->all;
    # id=1, name=Abba
    # id=2, name=Blur
    # id=3, name=Cream
    # (3 rows)

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Stages::labelled,
        take(1),
    )->all;
    # id=1, name=Abba

    eval { Ekorn::Pipeline->new(My::Stages::labelled)->([1, 'Abba']) };
    print $@;
    # Pipeline stage #1 failed at ... line ...:
    #     Expected a statement to read, for its columns at ... line ...

In the second run, C<take(1)>, after it, stopped the run while rows
were still to come, so its flush wasn't called, as Ekorn's rules say.
Called with values, the pipeline reads no statement, so the stage
croaks.

=head2 The same stage, as a class

A class of your own can be the same stage, by offering C<EKORN_STAGE>,
called at the start of each run with the object, and returning the
pieces, as the set-up did. The object keeps its settings, and each run
its own columns:

    package My::Labelled {
        sub new ($class, %options) { bless {between => $options{between} // ', '}, $class }

        sub EKORN_STAGE ($self) {
            my $columns;    # this run's
            return {
                step => sub ($row) {
                    $columns //= Ekorn::Pipeline::run_context()->{columns};
                    return join $self->{between}, map {"$columns->[$_]=$row->[$_]"} 0 .. $#$columns;
                },
            };
        }
    }

    say for $dbh->iterate(
        'SELECT id, name FROM artist ORDER BY id',
        My::Labelled->new(between => ' '),
    )->all;
    # id=1 name=Abba
    # id=2 name=Blur
    # id=3 name=Cream

=head2 A sink into a table, with the word C<sink_one>

A sink that inserts each value into a table, and gives how many it
inserted. Its set-up begins a transaction, and its end commits it only
if the run ended C<done>, so a run that dies, or is stopped, leaves the
table as it was:

    use DBIx::Squirrel::Tooling qw(sink_one pluck);

    sub into ($dbh, $table) {
        return sink_one {
            my $n = 0;
            $dbh->begin_work;
            my $sth = $dbh->prepare("INSERT INTO $table (name) VALUES (?)");
            return {
                step  => sub ($name) { $sth->execute($name); $n++ },
                flush => sub ()      {$n},
                end   => sub ($how)  { $how eq 'done' ? $dbh->commit : $dbh->rollback },
            };
        };
    }

    $dbh->do('CREATE TEMP TABLE copy (name TEXT)');

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        into($dbh, 'copy'),
    );
    # 3

    eval {
        $dbh->iterate(
            'SELECT name FROM artist ORDER BY id',
            pluck('name'),
            sub { die "no Cream\n" if $_ eq 'Cream'; $_ },
            into($dbh, 'copy'),
        );
    };
    print $@;
    # Pipeline stage #2 failed at ... line ...:
    #     no Cream

    say $dbh->selectrow_array('SELECT COUNT(*) FROM copy');    # 3

The second run inserted Abba and Blur, then died at Cream, so the sink's
end was told C<died>, and rolled them back: the table has the first
run's three rows.

=head2 The same sink, as a class

A class offers C<EKORN_SINK_ONE> for a sink of one result, or
C<EKORN_SINK_MANY> for a sink of many, returning the same pieces:

    use DBIx::Squirrel::Tooling qw(pluck take);

    package My::Into {
        sub new ($class, $dbh, $table) { bless {dbh => $dbh, table => $table}, $class }

        sub EKORN_SINK_ONE ($self) {
            my($dbh, $n) = ($self->{dbh}, 0);
            $dbh->begin_work;
            my $sth = $dbh->prepare("INSERT INTO $self->{table} (name) VALUES (?)");
            return {
                step  => sub ($name) { $sth->execute($name); $n++ },
                flush => sub ()      {$n},
                end   => sub ($how)  { $how eq 'done' ? $dbh->commit : $dbh->rollback },
            };
        }
    }

    say $dbh->iterate(
        'SELECT name FROM artist ORDER BY id',
        pluck('name'),
        take(2),
        My::Into->new($dbh, 'copy'),
    );
    # 2

    say $dbh->selectrow_array('SELECT COUNT(*) FROM copy');    # 5
    $dbh->do('DROP TABLE copy');

C<take(2)> stopped the run, but before the sink, so the sink got every
value it was going to get: its end was told C<done>, and it committed.

=head2 Row classes and functions that take stages

A row class of your own, for C<results>, is a subclass of
DBIx::Squirrel::Result with methods of your own: see L<Methods of your
own|/"Methods of your own">. A function that takes stages from its
caller hands them to C<iterate>: see L<A function that takes
stages|/"A function that takes stages">. Neither has pieces of its own.

=head1 Upgrading from 3.x

Version 4 takes Ekorn::Pipeline v0.4.0, where C<pipe> gives what a
pipeline of the same stages gives. One change meets code written for
3.x:

=over 4

=item C<< my $name = $dbh->pipe(...) >>, or C<< $sth->pipe(...) >>, in scalar context, for the first result

B<What happens now:> how many results came out, or a sink's result if a sink is last

B<How to move:> read it in list context, C<< my($name) = $dbh->pipe(...) >>, or give C<keep_first> last

=back

Everything else works as it did. Version 4.2 takes Ekorn::Pipeline
v0.4.3, whose iterator has C<next>.

=head1 Upgrading from 2.x

Version 3 builds on Ekorn::Pipeline v0.3.0, and makes one rule of what
a call gives: a statement is a source; DBIx::Squirrel's calls give an
iterator, and only a sink given last turns it into a result. These are
the changes code written for 2.x meets, and how to move:

=over 4

=item A Sugar statement given stages, read as a list: C<my @names = artist_names sub {...}>

B<What happens now:> gives an iterator, not every result

B<How to move:> give a sink last: C<artist_names sub {...}, keep_all>

=item A Sugar statement given stages in scalar context, for a count

B<What happens now:> gives an iterator

B<How to move:> give C<count_items> last

=item C<< $it->count >>

B<What happens now:> fails: the method is gone

B<How to move:> give C<count_items> last, or count as you go with C<count_into(\$n)>

=item C<< my $n = $it->all >>, for a count

B<What happens now:> an array reference

B<How to move:> C<count_items> given last

=item C<< $it->single >>, after C<next>

B<What happens now:> the next result, not a fresh run's only one

B<How to move:> C<< $it->reset->single >>

=item C<< $it->single >>, at a second result

B<What happens now:> a warning, and the first, not a croak

B<How to move:> check for the warning, or keep the croak with a stage of your own

=item C<< DBIx::Squirrel::Pipeline->new(...) >>

B<What happens now:> fails on a fresh install, as the module is no longer shipped; a copy that 2.x installed still loads, until it's deleted

B<How to move:> C<< Ekorn::Pipeline->new(...) >>, or C<pipeline(...)> from Ekorn::Pipeline::Factories

=item C<$x isa 'DBIx::Squirrel::Pipeline'>

B<What happens now:> false

B<How to move:> C<$x isa 'Ekorn::Pipeline'>

=item C<< DBIx::Squirrel::Stop->throw >>, or a subclass of DBIx::Squirrel::Stop

B<What happens now:> fails: it's no longer a class

B<How to move:> C<< Ekorn::Pipeline::Stop->throw >>, and subclass C<Ekorn::Pipeline::Stop>

=item C<ref $stage eq 'CODE'>, or C<is_coderef($stage)>, for a stage made by C<take>, C<gather> and the like

B<What happens now:> false: they're objects now, called as code references

B<How to move:> C<is_stage($stage)>, from Ekorn::Pipeline

=item A C<gather> block's second part, "the end function"

B<What happens now:> the same, now called the flush

B<How to move:> nothing; an end, told how the run ended, can follow it

=item C<iterator> in a pipeline of your own reading an iterator

B<What happens now:> C<undef>

B<How to move:> keep the iterator in a variable the stage can see

=item C<< my($first) = $sth->iterate->next >>, then using the handle

B<What happens now:> the handle is finished once the iterator goes

B<How to move:> keep the iterator while the handle is in use

=back

Everything else works as it did: C<iterate>, C<results>, and the select
methods and Sugar without stages or a sink last, C<pluck>, C<as_hash>,
C<take>, C<Stop>, and C<gather>. New: C<first>, C<ended>, sinks given last,
C<|> and C<@{}>, stages for the select methods, named pipelines in the
Sugar's definitions, and the run's context as a documented protocol.

=head1 Upgrading from 1.x

DBIx::Squirrel 2 was a rewrite, not an update, and version 3 builds on
it. Code written for 1.x needs changes before it runs. The ideas carry
over, so most changes are a rename or a simpler call. But some methods
keep their names and change what they do. They're marked B<in bold>
below.

To stay on 1.x, which supports Perl 5.10.1 and later, install the last
version by its number:

    cpanm DBIx::Squirrel@1.6.5

=head2 Requirements and loading

=over 4

=item Perl 5.10.1 or later.

Perl 5.36 or later.

=item Hard dependencies on Compress::Bzip2, Crypt::CBC, Dotenv, JSON::Syck, YAML::Syck and others.

DBI, Ekorn::Pipeline, Ref::Util, namespace::clean, and a few core modules.

=item Loading it read a C<.env> file in the current directory, through Dotenv.

Nothing is read. Load your environment yourself.

=head2 Importing and the entity helpers

=over 4

=item C<< use DBIx::Squirrel database_entities => [qw(db artists)]; >>

C<< use DBIx::Squirrel::Sugar database => {...}, statement => {...}; >>

=item A helper was associated at run time: C<< db(DBIx::Squirrel->connect(...)) >>.

A database is defined by the arguments to connect with, and connected when first used: C<< database => {db => [$dsn, $user, $pass]} >>.

=item A helper could hold a database, a statement or an iterator.

A function holds a database, or a statement on a database by name, with stages of its own.

=item A helper for a result set returned the iterator, so C<< artist('Aerosmith')->single->ArtistId >>.

A statement's function returns the statement handle, or, with stages, an iterator, or a sink's result: C<< artist('Aerosmith', sub ($row) { $row->[0] }, keep_single) >>.

=back

    use DBIx::Squirrel::Tooling qw(pluck);

    # 1.x
    use DBIx::Squirrel database_entities => [qw(db artist)];
    db(DBIx::Squirrel->connect($dsn, $user, $pass));
    artist(db->results('SELECT * FROM artists WHERE Name = ? LIMIT 1'));
    say artist('Aerosmith')->single->ArtistId;

    # Now
    use DBIx::Squirrel::Sugar
        database  => {db => [$ENV{DSN}, $ENV{USER}, $ENV{PASS}]},
        statement => {artist_id => [db => 'SELECT ArtistId FROM artists WHERE Name = ?', pluck]};
    use Ekorn::Pipeline::Sinks qw(keep_single);
    my $id = artist_id('Aerosmith', keep_single);

=head2 Placeholders and binding

=over 4

=item C<?>, C<?1>, C<:1>, C<$1> and C<:name>.

The same, and C<$name>.

=item Placeholders were found anywhere in the statement: in quoted strings, and in casts, so C<x::int> broke.

Not in quoted strings, comments, casts or PostgreSQL's dollar-quoted bodies, read by the database's rules. See L<What isn't a placeholder|/"What isn't a placeholder">.

=item Styles could be mixed.

One style to a statement. A mix croaks.

=item C<--> comments were removed before the statement reached the database.

Comments are passed on to the database.

=back

Binding by name, as pairs or in a hash reference, with or without the
sigil, works as it did.

=head2 do

=over 4

=item **In list context, C<do> returned the row count and the statement handle.**

C<do> returns what the DBI's returns, in any context. Use C<prepare> and C<execute> for the handle.

=back

=head2 Iterator and result set methods

=over 4

=item C<it> and C<iterator>, aliases of C<iterate>.

C<iterate> only.

=item C<rs> and C<resultset>, aliases of C<results>.

C<results> only.

=item C<< $dbh->iterate($sql, [@bind_values, @transforms]) >>: values and stages in one array reference.

Stages are at the end of the arguments: C<< $dbh->iterate($sql, @bind_values, @stages) >>.

=item **C<next> put the result in C<$_>**, as in C<< while ($it->next) { say $_->Name } >>.

Nothing is put in C<$_>: C<< while (my($row) = $it->next) { say $row->name } >>.

=item C<all> in scalar context returned a reference to the results.

The same.

=item **C<count> fetched the rest of the results and returned how many there were in all.**

Gone: give C<count_items> last, as C<< $dbh->iterate($sql, count_items) >>.

=item C<count_fetched>.

Gone: C<count_into(\$n)> as a stage, or C<result_number> in one.

=item C<single> and C<one> returned the first result, with a warning if there were more.

C<single> the same; C<one> is gone.

=item C<first>.

The same.

=item C<last> and C<last_fetched>.

Gone: C<keep_last> given last, or C<take_last> as a stage.

=item C<remaining>.

C<all>, which returns the results not yet handed out.

=item C<start> and C<iterate> on an iterator, to execute it with new bind values.

C<reset(@bind_values, @stages)>.

=item C<reset($slice, $cache_size)>, to change the slice or the cache size.

C<reset> takes bind values and stages. The slice is the C<ekorn_slice> attribute. Rows are fetched 2 at first, up to 64 at a time.

=item C<slice>, C<cache_size> and their package-wide defaults, C<$DBIx::Squirrel::it::DEFAULT_SLICE> among them.

The C<ekorn_slice> attribute, on C<connect> or C<prepare>.

=item C<is_active>, C<not_active> and C<rows>.

Gone: C<< $it->sth->{Active} >> and C<< $it->sth->rows >>.

=back

=head2 Rows as objects

=over 4

=item B<A column's method matched its name in any case:> C<< $row->ArtistId >> or C<< $row->artistid >>.

Methods are named in lower case only: C<< $row->artistid >>.

=item Methods were made the first time each was called.

A class with a method for each column is made for each list of columns. See L<Row objects|/"Row objects">.

=item A column whose name can't be a method's, such as C<COUNT(*)>, was reached by its position.

By its position still, as rows are arrays, or with C<get_column>, or given a name with C<AS>.

=back

=head2 Transformations, now stages

The stages work as transformations did. Each gets a value as its
argument and in C<$_>, and returns nothing to drop it, one value, or
several. These have changed:

=over 4

=item C<use DBIx::Squirrel::it qw(...)>, for what a stage can ask.

C<use DBIx::Squirrel::Context qw(...)>.

=item C<iterator>, C<result_number> and C<result_original>.

The same, from DBIx::Squirrel::Context.

=item C<database> and C<statement>.

C<< iterator->sth->{Database} >> and C<< iterator->sth >>, or the L<run's context|/"The run's context">.

=item C<result> and C<result_current>.

The stage's argument.

=item C<result_first>, C<result_prev>, C<result_previous> and C<result_offset>.

Gone. A stage that needs them keeps them itself, in a L<C<gather>|/"gather"> block.

=item C<DBIx::Squirrel::Transform::Data::Dumper>'s C<as_perl>, and C<DBIx::Squirrel::Transform::IO>'s C<stdout> and C<stderr>.

C<dump_to> and C<peek>, from DBIx::Squirrel::Stages::Taps. See L<Canned stages|/"Canned stages">.

=item No way to end a transformation early.

C<Stop>, from DBIx::Squirrel::Stop. See L<Stop|/"Stop">.

=back

=head2 Gone, out of scope

These have no place now. Any that come back will come back as
distributions of their own.

=over 4

=item C<DBIx::Squirrel::Crypt::Fernet>, and C<decrypt> from DBIx::Squirrel::util.

A Fernet module from CPAN.

=item C<DBIx::Squirrel::Transform::JSON::Syck> and C<DBIx::Squirrel::Transform::YAML::Syck>.

For JSON, C<from_json> and C<to_json>, from Ekorn::Pipeline::JSON, by Tooling's L<C<:json>|/"13. Import everything from one place">. For YAML, a stage of your own calling a YAML module: see L<Stages for others|/"Stages for others">.

=item C<get_file_contents>, C<slurp>, C<uncompress>, C<unmarshal> and C<utf8decode>, from DBIx::Squirrel::util.

Path::Tiny, IO::Uncompress::Bunzip2, a JSON module, and Encode.

=item C<load_tuples>, on a database handle.

C<prepare> and C<execute>, in a loop.

=item C<statement_digest>, C<statement_normalise>, C<statement_study> and C<statement_trim>, on a statement handle.

Gone. DBIx::Squirrel::Placeholders has C<study_sql> and C<trim_sql>, but they're internal, and may change.

=back

Every module, A to Z, and each of its functions and methods, A to Z,

=head2 DBIx::Squirrel

The class you connect with; a subclass of C<DBI>. C<use DBIx::Squirrel>
takes what the DBI exports, such as C<:sql_types>, and nothing else
(see L<Importing|/"Importing">).

=head3 connect

    $dbh = DBIx::Squirrel->connect($data_source, $username, $password);
    $dbh = DBIx::Squirrel->connect($data_source, $username, $password, \%attr);
    $dbh = DBIx::Squirrel->connect($data_source, \%attr);
    $dbh = DBIx::Squirrel->connect($dbh, \%attr);

C<connect> connects to a data source, as the DBI's C<connect> does, and
returns a database handle, a C<DBIx::Squirrel::db>. Its statement
handles are C<DBIx::Squirrel::st>s. Both are subclasses of the DBI's
own, so they do everything the DBI's handles do.

See L<connect|/"connect">.

=head3 connect_cached

    $dbh = DBIx::Squirrel->connect_cached($data_source, $username, $password);
    $dbh = DBIx::Squirrel->connect_cached($data_source, $username, $password, \%attr);
    $dbh = DBIx::Squirrel->connect_cached($data_source, \%attr);

As the DBI's C<connect_cached>: it returns the handle it connected with
before, given the same arguments, or connects, and keeps the handle.
It takes its arguments as C<connect> does, and croaks on failure, as
C<connect> does. DBIx::Squirrel's own attributes are part of the
cache's key, so a handle with other C<ekorn_> attributes is another
connection.

See L<connect_cached|/"connect_cached">.

=head2 DBIx::Squirrel::Context

What a stage can ask about the result it's making. Nothing by default;
each upon request, and in Tooling's C<:context>.

=head3 iterator

    use DBIx::Squirrel::Tooling qw(iterator);

    $it = iterator();

Returns the iterator running the stage, in an iterator's or result
set's own stages; elsewhere, and outside a stage, C<undef>. Through it
a stage can reach the rest: its C<sth> is the statement handle, the
statement handle's C<Database> is the database handle, and its
L<column_names|/"column_names"> are the statement's columns. Exported upon
request.

See L<Context|/"Context">.

=head3 result_number

    use DBIx::Squirrel::Tooling qw(result_number);

    $n = result_number();

Returns the number of the result being made, from 1. It counts
results, not rows: while a stage drops rows, the number stays the
same, and each value a stage returns in place of one row is a result
of its own. In a flush of a stage made with L<gather|/"gather">, it's
the number of the first value the flush returns. It works in any run,
each counting its own results, and is C<undef> outside one. It has an
empty prototype, so C<result_number + 1> adds one. Exported upon
request.

See L<Context|/"Context">.

=head3 result_original

    use DBIx::Squirrel::Tooling qw(result_original);

    $row = result_original();

Returns the row the result is being made from, as it was fetched,
before any stage changed it; for a result set, the row object. In a
flush of a stage made with L<gather|/"gather">, and the stages after it,
it's C<undef>, as what a flush gives comes from every row, not one. In
a run reading no statement, it's the value the run's source gave, or
that was pushed. It's Ekorn::Pipeline::Context's own, with an empty
prototype. Exported upon request.

See L<Context|/"Context">.

=head2 DBIx::Squirrel::db

The database handle class; a subclass of C<DBI::db>. Exports nothing.

=head3 do

    $rv = $dbh->do($statement);
    $rv = $dbh->do($statement, \%attr, @bind_values);
    $rv = $dbh->do($statement, undef, @bind_values);
    $rv = $dbh->do($statement, @bind_values);

Runs a statement, and returns what the DBI's C<do> returns: the number
of rows affected, C<0E0> for none, or C<undef> on an error without
C<RaiseError>. An error names C<do>, as the DBI's does:
C<DBD::SQLite::db do failed: ...>.

See L<do|/"do">.

=head3 iterate

    $it     = $dbh->iterate($statement, \%attr, @bind_values, @stages);
    $it     = $dbh->iterate($statement, @bind_values, @stages);
    @result = $dbh->iterate($statement, @bind_values, @stages, $sink);

On a database handle, C<iterate> prepares the statement, as C<prepare>
does, and returns a C<DBIx::Squirrel::Iterator> over its results. As
with C<do>, the attributes may be left out. On a statement handle, it
returns an iterator over that statement's results.

See L<iterate|/"iterate">.

=head3 pipe

    use DBIx::Squirrel::Tooling qw(keep_first);

    @results = $dbh->pipe(@stages);
    $count   = $dbh->pipe(@stages);
    ($first) = $dbh->pipe(@stages);
    $first   = $dbh->pipe(@stages, keep_first);

Runs the handle through the stages, and returns what comes out of the
last one, as a pipeline of the same stages does: all of it in list
context; in scalar context, how many results came out, or, if a sink
is last, the sink's result, a list sink's as an array reference. For
one value, read it in list context, or end with C<keep_first>. Until
v4.0.0, in scalar context, it gave the first result. With no stages, it
returns the handle, or, in scalar context, 1. A stage that dies makes C<pipe> croak, naming the stage (see
L<When a stage dies|/"When a stage dies">).

See L<pipe and tap|/"pipe and tap">.

=head3 prepare

    $sth = $dbh->prepare($statement);
    $sth = $dbh->prepare($statement, \%attr);

Prepares a statement, with placeholders in any of the
L<styles|/"The styles">, and returns a C<DBIx::Squirrel::st>.

The statement can be a string, an array reference of lines, which are
joined with spaces, a code reference returning either, or a statement
handle, whose statement is prepared again.

See L<prepare|/"prepare">.

=head3 prepare_cached

    $sth = $dbh->prepare_cached($statement);
    $sth = $dbh->prepare_cached($statement, \%attr);
    $sth = $dbh->prepare_cached($statement, \%attr, $if_active);

As C<prepare>, using the DBI's cache of statement handles. Its errors
name C<prepare_cached>, as the DBI's do. Like C<prepare>, it croaks
given a statement taking a L<list|/"Lists">.

Two statements can be rewritten the same: C<SELECT :a, :b> and
C<SELECT :b, :a> both become C<SELECT ?, ?>. Each still has a handle of
its own, as the statement as written is part of the cache's key.
DBIx::Squirrel's own attributes are part of the key too. So a
statement prepared with C<< {ekorn_slice => {}} >> and one prepared without
have different handles.

See L<prepare_cached|/"prepare_cached">.

=head3 results

    $results = $dbh->results($statement, \%attr, @bind_values, @stages);
    $results = $dbh->results($statement, @bind_values, @stages);
    @result  = $dbh->results($statement, @bind_values, @stages, $sink);

As L<C<iterate>|/"iterate">, returning a C<DBIx::Squirrel::Results>, or a
sink's result, if the last stage is a sink. A result set is an
iterator whose rows are objects, with a method for each column, named
in lower case. The stages see the objects. A result set has the
iterator's methods, and no others.

See L<results|/"results">.

=head3 selectall_array

    @rows    = $dbh->selectall_array($statement, \%attr, @bind_values);
    @rows    = $dbh->selectall_array($statement, @bind_values);
    @results = $dbh->selectall_array($statement, \%attr, @bind_values, @stages);
    $count   = $dbh->selectall_array($statement, \%attr, @bind_values, @stages);

Returns every row, as a list, the rows C<selectall_arrayref> gives, as
the DBI's does. Given stages, it pushes each row through them in turn,
which makes it the select method most like C<iterate>, but with every
row fetched first.

See L<The select methods|/"The select methods">.

=head3 selectall_arrayref

    $ary_ref = $dbh->selectall_arrayref($statement, \%attr, @bind_values);
    $ary_ref = $dbh->selectall_arrayref($statement, @bind_values);
    @results = $dbh->selectall_arrayref($statement, \%attr, @bind_values, @stages);

Returns every row, as an array reference of rows, each an array
reference, or a hash reference given the attribute C<< Slice => {} >>, as
the DBI's does. Given stages, it pushes that one reference through
them, so a stage gets all the rows at once.

See L<The select methods|/"The select methods">.

=head3 selectall_hashref

    $hash_ref = $dbh->selectall_hashref($statement, $key_field, \%attr, @bind_values);
    $hash_ref = $dbh->selectall_hashref($statement, $key_field, @bind_values);
    @results  = $dbh->selectall_hashref($statement, $key_field, \%attr, @bind_values, @stages);

Returns every row, in a hash reference keyed by the values of
C<$key_field>, each row a hash reference, as the DBI's does. The key
field comes before the attributes, and can be an array reference of
fields, for nested keys. Given stages, it pushes that one reference
through them.

See L<The select methods|/"The select methods">.

=head3 selectcol_arrayref

    $ary_ref = $dbh->selectcol_arrayref($statement, \%attr, @bind_values);
    $ary_ref = $dbh->selectcol_arrayref($statement, @bind_values);
    @results = $dbh->selectcol_arrayref($statement, \%attr, @bind_values, @stages);

Returns the first column of every row, as an array reference, or the
columns the attribute C<Columns> names, as the DBI's does. Given
stages, it pushes that one reference through them.

See L<The select methods|/"The select methods">.

=head3 selectrow_array

    @row_ary = $dbh->selectrow_array($statement, \%attr, @bind_values);
    @row_ary = $dbh->selectrow_array($statement, @bind_values);
    @results = $dbh->selectrow_array($statement, \%attr, @bind_values, @stages);

Returns the first row's values, as a list, or nothing if there's no
row. Given stages, it pushes each of the row's values through them.

See L<The select methods|/"The select methods">.

=head3 selectrow_arrayref

    $ary_ref = $dbh->selectrow_arrayref($statement, \%attr, @bind_values);
    $ary_ref = $dbh->selectrow_arrayref($statement, @bind_values);
    @results = $dbh->selectrow_arrayref($statement, \%attr, @bind_values, @stages);

Returns the first row, as an array reference, or C<undef> if there's no
row. Given stages, it pushes that one reference through them.

See L<The select methods|/"The select methods">.

=head3 selectrow_hashref

    $hash_ref = $dbh->selectrow_hashref($statement, \%attr, @bind_values);
    $hash_ref = $dbh->selectrow_hashref($statement, @bind_values);
    @results  = $dbh->selectrow_hashref($statement, \%attr, @bind_values, @stages);

Returns the first row, as a hash reference keyed by the column names,
as C<fetchrow_hashref> keys them, or C<undef> if there's no row. Given
stages, it pushes that one reference through them.

See L<The select methods|/"The select methods">.

=head3 tap

    $dbh = $dbh->tap(@stages);

Runs the handle through the stages for their side effects, drops what
comes out, and returns the handle, however the stages end: having run
out of values, stopped, or with no stages at all. So a chain of method
calls can carry on after it. A stage that dies makes C<tap> croak, as
C<pipe> does.

See L<pipe and tap|/"pipe and tap">.

=head2 DBIx::Squirrel::Errors

Reports errors at the caller's line. Internal, apart from what a
module of stages uses: C<croakf>, and C<@INTERNAL>, the packages an
error passes over, for a module's C<@CARP_NOT>. Nothing by default.

=head3 croakf

    use DBIx::Squirrel::Errors qw(croakf);

    croakf $format, @values;

Croaks with a message made by C<sprintf> from a format and its values,
reported at the line C<croak> would report it at. With C<@CARP_NOT> set
to C<@DBIx::Squirrel::Errors::INTERNAL>, that's the line that called
DBIx::Squirrel. It's the one function of DBIx::Squirrel::Errors for
others: the rest are for the handles. Exported upon request.

See L<Stages for others|/"Stages for others">.

=head2 DBIx::Squirrel::Gather

A stage made afresh for each run, with a flush and an end: Ekorn's
C<gather>, by default.

=head3 gather

    use DBIx::Squirrel::Gather;

    my $stage = gather { ...; return $step };
    my $stage = gather { ...; return ($step, $flush) };
    my $stage = gather { ...; return ($step, $flush, $end) };
    my $stage = gather { ...; return {step => $step, flush => $flush, end => $end} };

C<gather> makes a stage afresh at the start of each run, by calling its
block, so whatever the block declares is fresh each time. A run is
each execution of an iterator or result set, including after C<reset>,
each call of a Sugar statement, and each call of a pipeline. The block
returns the stage, and optionally a flush, called once the values run
out, and an end, told how the run ended. Exported by default.

See L<gather|/"gather">.

=head2 DBIx::Squirrel::Iterator

An iterator over a statement's results, and a source for
Ekorn::Pipeline. Where C<use Ekorn::Pipeline::Operators> is in force,
C<|> runs it through a sink or stages, and C<@{}> gives every result
(see L<16. Operators|/"16. Operators: E<verbar> and @{}">). Exports nothing.

=head3 all

    @results = $it->all;
    $results = $it->all;

Returns the results still to come, reading the run to its end: as a
list, or, asked for one value, an array reference of them, never a
count. Either way, the statement is then finished, and C<next> returns
nothing after, until L<reset|/"reset">.

See L<The iterator's methods|/"The iterator's methods">.

=head3 all_arrayref

    $results = $it->all_arrayref;

Returns the results still to come as an array reference, whatever the
context it's called in, so a hash constructor, an argument list or a
sub's return can't flatten them; an empty one if there are none.
Otherwise it's L<all|/"all">: it reads the run to its end, the statement
is then finished, and C<next> returns nothing after, until
L<reset|/"reset">.

See L<The iterator's methods|/"The iterator's methods">.

=head3 column_names

    @names = $it->column_names;

Returns the names of the statement's columns, as C<fetchrow_hashref>
would key them, following C<FetchHashKeyName>. If the statement hasn't
been executed, it's executed first. The names are read when it's
executed, as some drivers, such as DBD::mysql, give none once the last
row is fetched. A statement without columns has no names, and nor does
one that couldn't be executed. A stage can ask for them through
L<iterator|/"iterator">.

See L<The iterator's methods|/"The iterator's methods">.

=head3 EKORN_SOURCE

    ($step, $end, $context) = $it->EKORN_SOURCE;

The role method that makes an iterator a source: a pipeline's
C<iterator>, a chain made with C<|>, and C<@{}> call it, and you don't.
It returns what Ekorn::Pipeline's source protocol asks for: a step,
called for each next value, an end, told how the run ended, and the
run's context. Each call starts a fresh run of the statement, from its
first row, through the iterator's stages.

See L<The iterator as a source|/"The iterator as a source">.

=head3 ended

    $how = $it->ended;

Returns how the last run ended: C<done> when the rows ran out,
C<stopped> when it was cut short, by C<first>, by C<single> finding a
second result, or by a stage that stopped, and C<died> when a stage
died. While a run is going, and before one has started, it returns
nothing; L<reset|/"reset"> starts a new run, so it returns nothing after
one. A run read with C<|> or C<@{}> is the iterator's last run too (see
L<16. Operators|/"16. Operators: E<verbar> and @{}">).

See L<The iterator's methods|/"The iterator's methods">.

=head3 first

    $result = $it->first;

Returns the next result, or C<undef> if there's none, and finishes the
statement, so the rest aren't fetched. C<next> returns nothing after,
until L<reset|/"reset">. The run ends C<stopped>, as it was cut short.

See L<The iterator's methods|/"The iterator's methods">.

=head3 new

    $it = DBIx::Squirrel::Iterator->new($sth, @bind_values, @stages);

Returns an iterator over the rows of C<$sth>, a C<DBIx::Squirrel::st>,
without executing it. When it does, it's executed with C<@bind_values>,
in any form L<execute|/"execute"> takes, and each row runs through
C<@stages>, the stages at the end of the arguments. C<iterate> makes an
iterator this way, and is how you'd usually get one; a statement
handle that isn't DBIx::Squirrel's croaks, C<Expected a DBIx::Squirrel
statement handle>.

See L<The iterator's methods|/"The iterator's methods">.

=head3 next

    while (my($result) = $it->next) { ... }

Returns the next result, or an empty list when there are no more. The
first call executes the statement, if it hasn't been, and each call
fetches rows as they're wanted, running each through the iterator's
stages until one comes out.

See L<The iterator's methods|/"The iterator's methods">.

=head3 reset

    $it = $it->reset;
    $it = $it->reset(@bind_values, @stages);

Executes the statement again, ready to iterate from its first row, and
returns the iterator. If the statement is still active, it's finished
first, and whatever the run before held goes with it. Bind values
given replace those given before. Stages given are added to those
given when the iterator was made. Both are kept until others are
given.

See L<reset|/"reset">.

=head3 single

    $result = $it->single;

Returns the next result, or C<undef> if there's none, and finishes the
statement, as C<first> does. If there's another result, it warns,
C<Expected only one item, but there were more>, and returns the first.
It's for a statement that should give one result: the warning finds
one that lost its C<LIMIT 1>, or its C<WHERE>.

See L<The iterator's methods|/"The iterator's methods">.

=head3 sth

    $sth = $it->sth;

Returns the iterator's statement handle, a C<DBIx::Squirrel::st>. It
changes when L<reset|/"reset"> prepares a statement taking a
L<list|/"Lists"> again, for a list of another length.

See L<The iterator's methods|/"The iterator's methods">.

=head2 DBIx::Squirrel::Placeholders

Finds the placeholders in a statement, and matches values to them.
Internal: its functions are for the handles.

=head2 DBIx::Squirrel::Result

The base class of row objects. A row also has a method for each
column, as L<Row objects|/"Row objects"> says, and can have methods of
your own (see L<Methods of your own|/"Methods of your own">). Exports
nothing.

=head3 get_column

    $value = $row->get_column($name);
    $value = $row->get_column($position);

Returns a column's value by its name, in any case, or by its position,
from 0. It reaches every column, including those without a method. It
croaks if the row has no such column:
C<Expected a column of the row (x)>.

See L<get_column|/"get_column">.

=head2 DBIx::Squirrel::Results

A result set: an iterator handing out rows as objects, with the
iterator's methods and no others. C<results> makes one (see
L<results|/"results">). Exports nothing.

=head2 DBIx::Squirrel::st

The statement handle class; a subclass of C<DBI::st>. Exports nothing.

=head3 bind

    $sth = $sth->bind(@bind_values);
    $sth = $sth->bind(\@bind_values);
    $sth = $sth->bind(%values);
    $sth = $sth->bind(\%values);

Binds values to the statement's placeholders without executing it.
Returns the statement handle, or nothing if the DBI couldn't bind a
value. How values are matched to placeholders depends on the
L<style|/"The styles">.

See L<bind|/"bind">.

=head3 bind_param

    $rv = $sth->bind_param($placeholder, $value);
    $rv = $sth->bind_param($placeholder, $value, \%attr);
    $rv = $sth->bind_param($placeholder, $value, $bind_type);

Binds one value, as the DBI's C<bind_param> does, and returns what it
returns. The placeholder can be given by position, as with the DBI; by
number, for numbered placeholders, as C<1> or C<'$1'>; or by name, for
named ones, as C<'id'> or C<':id'>. The value is bound to every use of
the placeholder in the statement.

See L<bind_param|/"bind_param">.

=head3 bind_param_array

    $rv = $sth->bind_param_array($placeholder, \@values);
    $rv = $sth->bind_param_array($placeholder, $value);
    $rv = $sth->bind_param_array($placeholder, \@values, \%attr);

Binds an array of values to a placeholder, a value for each row
L<execute_array|/"execute_array"> executes, or one value for every
row, as the DBI's C<bind_param_array> does, and returns what it
returns. The placeholder is named as for L<bind_param|/"bind_param">:
by number or name, with or without the sigil, for numbered and named
placeholders. Attributes given are bound to every use of it.

See L<execute_array|/"execute_array">.

=head3 execute

    $rv = $sth->execute;
    $rv = $sth->execute(@bind_values);
    $rv = $sth->execute(\@bind_values);
    $rv = $sth->execute(%values);
    $rv = $sth->execute(\%values);

Executes the statement, as the DBI's C<execute> does, and returns what
it returns. Values given are bound first, as L<C<bind>|/"bind"> binds
them.

A statement with numbered or named placeholders, executed without
values, croaks unless each placeholder already has a value bound. The
value can come from L<C<bind>|/"bind">, L<C<bind_param>|/"bind_param"> or an
earlier C<execute>, as the DBI keeps them. The DBI would leave the
placeholder unbound, which most drivers read as C<NULL>. C<do>,
iterators and the select methods check the same way.

See L<execute|/"execute">.

=head3 execute_array

    $tuples = $sth->execute_array(\%attr, @arrays);
    ($tuples, $rows) = $sth->execute_array(\%attr, @arrays);
    $tuples = $sth->execute_array(\%attr);

Executes the statement once for each row of values, as the DBI's
C<execute_array> does, and returns what it returns: in a list, the
rows executed and the rows changed. The rows come from C<@arrays>, one
for each placeholder, in order, by number, or for names, in the order
each first appears; from those bound with
L<bind_param_array|/"bind_param_array">; or from C<ArrayTupleFetch> in
C<%attr>. Each row's status goes in C<ArrayTupleStatus>. A statement
with a list croaks.

See L<execute_array|/"execute_array">.

=head3 execute_for_fetch

    $tuples = $sth->execute_for_fetch($fetch);
    $tuples = $sth->execute_for_fetch($fetch, \@status);
    ($tuples, $rows) = $sth->execute_for_fetch($fetch, \@status);

Executes the statement once for each row C<$fetch> returns, until it
returns nothing, as the DBI's C<execute_for_fetch> does, and returns
what it returns. A row is an array of values, in the order
L<execute_array|/"execute_array"> takes them, or, for named
placeholders, a hash of them by name. A statement with a list croaks.

See L<execute_array|/"execute_array">.

=head3 iterate

    $it     = $sth->iterate(@bind_values, @stages);

On a database handle, C<iterate> prepares the statement, as C<prepare>
does, and returns a C<DBIx::Squirrel::Iterator> over its results. As
with C<do>, the attributes may be left out. On a statement handle, it
returns an iterator over that statement's results.

See L<iterate|/"iterate">.

=head3 pipe

    use DBIx::Squirrel::Tooling qw(keep_first);

    @results = $sth->pipe(@stages);
    $count   = $sth->pipe(@stages);
    ($first) = $sth->pipe(@stages);
    $first   = $sth->pipe(@stages, keep_first);

Runs the handle through the stages, and returns what comes out of the
last one, as a pipeline of the same stages does: all of it in list
context; in scalar context, how many results came out, or, if a sink
is last, the sink's result, a list sink's as an array reference. For
one value, read it in list context, or end with C<keep_first>. Until
v4.0.0, in scalar context, it gave the first result. With no stages, it
returns the handle, or, in scalar context, 1. A stage that dies makes C<pipe> croak, naming the stage (see
L<When a stage dies|/"When a stage dies">).

See L<pipe and tap|/"pipe and tap">.

=head3 results

    $results = $sth->results(@bind_values, @stages);

As L<C<iterate>|/"iterate">, returning a C<DBIx::Squirrel::Results>, or a
sink's result, if the last stage is a sink. A result set is an
iterator whose rows are objects, with a method for each column, named
in lower case. The stages see the objects. A result set has the
iterator's methods, and no others.

See L<results|/"results">.

=head3 tap

    $sth = $sth->tap(@stages);

Runs the handle through the stages for their side effects, drops what
comes out, and returns the handle, however the stages end: having run
out of values, stopped, or with no stages at all. So a chain of method
calls can carry on after it. A stage that dies makes C<tap> croak, as
C<pipe> does.

See L<pipe and tap|/"pipe and tap">.

=head2 DBIx::Squirrel::Stages::Batch

Canned stages gathering values. Both by default, and in Tooling's
C<:batch>.

=head3 batch

    use DBIx::Squirrel::Tooling qw(batch);

    batch($n)

Passes values on in batches of C<$n>, each a new array reference. Once
the values run out, the last batch goes on, which may be shorter.
There's never an empty batch: with no values, there's no batch at all.
It holds no more than one batch at a time, so it suits loading or
sending rows in groups. It croaks, C<Expected a batch size of 1 or
more>, if C<$n> isn't a whole number above 0. Exported by default.

See L<Batching and collecting|/"Batching and collecting">.

=head3 collect

    use DBIx::Squirrel::Tooling qw(collect);

    collect
    collect { ... }
    collect(\&code)

Holds every value. Once they run out, it passes on an array reference
of them. Given a block, it calls the block once, with the values as
its arguments, and passes on what the block returns: nothing, one
value, or several, as a stage does. The block is called even with no
values, so C<collect> always gives a result. It holds every value until
the end, so the whole result is in memory at once. It croaks,
C<Expected a code reference>, if it's given something other than a
block or code reference. Exported by default.

See L<Batching and collecting|/"Batching and collecting">.

=head2 DBIx::Squirrel::Stages::Flow

Canned stages taking or dropping values. C<take> and C<drop> by default,
the others upon request; all in Tooling's C<:flow>.

=head3 drop

    use DBIx::Squirrel::Tooling qw(drop);

    drop($n)

Drops the first C<$n> values, and passes on the rest. With C<take>, it
gives a page: C<drop(20), take(10)> passes on values 21 to 30. It
croaks, C<Expected a count of 0 or more>, if C<$n> isn't a whole number.
Exported by default.

See L<Taking and dropping|/"Taking and dropping">.

=head3 drop_if

    use DBIx::Squirrel::Tooling qw(drop_if);

    drop_if { ... }
    drop_if(\&code)

Drops each value the block is true of, and passes on the rest:
C<take_if>'s opposite. The block gets each value in C<$_> and as its
argument. It croaks, C<Expected a code reference>, if it isn't given a
block or code reference. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 drop_while

    use DBIx::Squirrel::Tooling qw(drop_while);

    drop_while { ... }
    drop_while(\&code)

Drops values while the block is true of them, then passes on the rest,
from the first it's false of. After that, the block isn't called again
on that run. The block gets each value in C<$_> and as its argument. It
croaks, C<Expected a code reference>, if it isn't given a block or code
reference. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take

    use DBIx::Squirrel::Tooling qw(take);

    take($n)

Passes on the first C<$n> values, then stops the run, so the statement
is finished and no more rows are fetched. The last value it passes on
goes with the stop. If there are fewer values, it passes them all on.
It croaks, C<Expected a count of 0 or more>, if C<$n> isn't a whole
number. Exported by default.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take_first

    use DBIx::Squirrel::Tooling qw(take_first);

    take_first

Passes on the first value, then stops the run: C<take(1)>, named as the
stage of the sink C<keep_first>. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take_if

    use DBIx::Squirrel::Tooling qw(take_if);

    take_if { ... }
    take_if(\&code)

Passes on each value the block is true of, and drops the rest, testing
every one, as C<grep> does; it never stops the run. The block gets each
value in C<$_> and as its argument. A plain stage ending in a test
passes on what the test returns, true or false; C<take_if> passes on
the value. It croaks, C<Expected a code reference>, if it isn't given a
block or code reference. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take_last

    use DBIx::Squirrel::Tooling qw(take_last);

    take_last

Passes on the last value, once there are no more, reading every one to
find it; nothing if there were none. If a stage before it stops the
run, it passes on the last value to reach it. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take_single

    use DBIx::Squirrel::Tooling qw(take_single);

    take_single

Passes on the one value. At a second, it warns, C<Expected only one
item, but there were more>, and stops the run, so only the first goes
on: for a statement meant to give one row, whose limit was forgotten.
Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head3 take_while

    use DBIx::Squirrel::Tooling qw(take_while);

    take_while { ... }
    take_while(\&code)

Passes on values while the block is true of them. At the first it's
false of, it stops the run, and doesn't pass that value on. Unlike
C<take_if>, it reads no further, so it suits rows in an order the test
follows. The block gets each value in C<$_> and as its argument. It
croaks, C<Expected a code reference>, if it isn't given a block or code
reference. Exported upon request.

See L<Taking and dropping|/"Taking and dropping">.

=head2 DBIx::Squirrel::Stages::Rows

Canned stages reshaping rows. Both by default, and in Tooling's
C<:rows>.

=head3 as_hash

    use DBIx::Squirrel::Tooling qw(as_hash);

    as_hash
    as_hash(@names)

Gives each row as a hash, keyed by the column names as
C<fetchrow_hashref> would key them, following C<FetchHashKeyName>, so it
gives what plain DBI does. An array row, or a row object, is made into
a new hash; a hash row is passed on unchanged. As with
C<fetchrow_hashref>, of two columns with the same name, the hash has
the last. Given column names, found in any case, the hash has only
those columns, keyed as it would be without them; a hash row is made
into a new hash, and a name the row hasn't got croaks, C<Expected a
column of the row (age)>. It leaves the run's context as it is, so
C<to_csv>, after it, takes a header of the same names. It finds the
names in the L<run's context|/"The run's context">, so
it needs a statement to be what the run reads; elsewhere it croaks,
C<Expected a statement to read, for the column names>. Exported by
default.

See L<Reshaping rows|/"Reshaping rows">.

=head3 pluck

    use DBIx::Squirrel::Tooling qw(pluck);

    pluck($name)
    pluck($position)
    pluck

Gives one column of each row, by its name, in any case, or by its
position, from 0, whether the row is an array, a hash (with the
C<ekorn_slice> attribute) or a row object (from C<results>). Given no
column, it gives each row's only column, counted from the row: an
array of one element, a hash of one key, a row object of one column. A
row of more columns, or of none, croaks, C<Expected one column to
pluck, not 2>, rather than give the first, which would go wrong
silently when a query gains a column; C<pluck(0)> gives the first. A
column the row hasn't got croaks, C<Expected a column of the row
(age)>, and C<pluck(undef)> or C<pluck('')> croaks, C<Expected a column,
by name or position>. Exported by default.

See L<Reshaping rows|/"Reshaping rows">.

=head2 DBIx::Squirrel::Stages::Taps

Canned stages run for their side effects. C<peek> and C<count_into> by
default, C<dump_to> and C<tee> upon request; all in Tooling's C<:taps>.

=head3 count_into

    use DBIx::Squirrel::Tooling qw(count_into);

    count_into(\$n)

Counts the values into C<$n>, and passes them on. It sets C<$n> to 0 at
the start of each run, so after a run it holds how many values went
by, even if none did. It croaks, C<Expected a reference to a scalar>,
if it isn't given one. Exported by default.

See L<Taps|/"Taps">.

=head3 dump_to

    use DBIx::Squirrel::Tooling qw(dump_to);

    dump_to($fh)
    dump_to

Writes each value to C<$fh>, or to STDERR, with Data::Dumper, keys
sorted and indented by two, and passes it on. It croaks, C<Expected an
open filehandle>, if C<$fh> isn't one. Exported upon request.

It's for debugging. Where Text::Redact::Secrets v1.x is installed, it
writes each secret that module's rules find as C<*REDACTED*>, in the
text it writes only: the value passed on is as it came. The rules find
a long, random password, token or key, such as the password in a DSN,
but not a short or ordinary password, so a dump can still hold
secrets. Without the module, or while
C<local $DBIx::Squirrel::Stages::Taps::DumpSecrets = 1> is set, it
writes each value in full; with the module there but broken, it
croaks rather than write a dump. It doesn't escape control characters
in strings, so a value from outside can send escape sequences to a
terminal.

See L<Taps|/"Taps">.

=head3 peek

    use DBIx::Squirrel::Tooling qw(peek);

    peek { ... }
    peek(\&code)

Calls the block with each value, in C<$_> and as its argument, and
passes the value on, whatever the block returns: for logging, or
looking. It croaks, C<Expected a code reference>, if it isn't given a
block or code reference. Exported by default.

See L<Taps|/"Taps">.

=head3 tee

    use DBIx::Squirrel::Tooling qw(tee);

    tee(@stages)

Runs each value through a branch of C<@stages>, for what they do on the
side, and passes the value on unchanged. What comes out of the branch
is dropped. The branch is a run of its own beside the main run, so its
stages keep their state across the values, and each main run gets a
fresh branch. A stop after the tee closes the branch, so its flushes
run. Exported upon request.

See L<Taps|/"Taps">.

=head2 DBIx::Squirrel::Stop

Ends a pipeline early: Ekorn's C<Stop>, by default, and tells a stop
from other errors with C<is_stop>, upon request.

=head3 is_stop

    use DBIx::Squirrel::Stop qw(is_stop);

    $is = is_stop($error);

True if C<$error> is a stop, however it was thrown, and false of any
other error. Exported upon request.

See L<Catch errors, but let a stop through|/"Catch errors, but let a stop through">.

=head3 Stop

    use DBIx::Squirrel::Stop;

    Stop();
    Stop(@values);
    Ekorn::Pipeline::Stop->throw(@values);

Called from a stage, C<Stop> ends the run early and quietly. Exported
by default.

See L<Stop|/"Stop">.

=head2 DBIx::Squirrel::Sugar

A function for each database and statement, which runs it with the
values and stages it's given (see L<The function a database is
given|/"The function a database is given"> and L<The function a
statement is given|/"The function a statement is given">). C<use> with
C<database>, C<statement> or C<pipeline>, and a hash of definitions after
each, defines them as the program compiles (see L<Defining them on
use|/"Defining them on use"> and L<The Sugar's
pipelines|/"The Sugar's pipelines">).

=head3 database

    $dbh      = database($name);
    $function = database($name, @connect_args);

Given a name, returns the handle of the database defined by that name,
anywhere in the program, connecting to it if it isn't connected. Given
a name and the arguments C<connect> takes, it defines a database by
that name, gives the calling package a function of that name, and
returns the function. A database defined with a database handle, in
place of a data source, is a clone of it, as C<connect> makes, made
when the database is first used. Each database is defined once in a
program. Its name must be one a function can have, and the package
mustn't have a function of that name already. Given by C<use> with its
name.

See L<Defining them as the program
runs|/"Defining them as the program runs">.

=head3 statement

    $function = statement($name, $database, $statement, @stages);
    $function = statement($name, $database, $statement, \%attr, @stages);

Defines a statement by that name, on the database of that name. The
attributes are those to prepare it with, and the stages are its own.
It gives the calling package a function of that name, and returns the
function. The database is found when the function runs, so it can be
defined after the statement. Given by C<use> with its name.

See L<Defining them as the program
runs|/"Defining them as the program runs">.

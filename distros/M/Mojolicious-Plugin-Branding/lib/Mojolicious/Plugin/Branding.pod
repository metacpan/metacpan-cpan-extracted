=head1 SYNOPSIS

   # Mojolicious::Lite

   # individual branding: the application decides the brand of each
   # request and puts it in the stash
   my %brand_for = (
      'acme.example.com'     => 'acme',
      'umbrella.example.com' => 'umbrella',
   );
   hook before_dispatch => sub {
      my $c = shift;
      $c->brand($brand_for{$c->req->url->to_abs->host // ''});
   };

   plugin Branding => {

      # global branding: these directories override the application's
      # own templates/ and public/, first listed wins
      global => [ '/etc/myapp/look-and-feel' ],

      # individual branding: the directories of each brand
      individual => {
         brands => {
            acme     => 'brands/acme',
            umbrella => [ 'brands/umbrella', '/srv/shared/umbrella' ],
         },
      },
   };


=head1 DESCRIPTION

This plugin lets you change the templates and public files of a
L<Mojolicious> application without touching its source code. It
supports two styles of branding, which can be used separately or
together.

=over

=item Global branding

A project ships its own "brand-neutral" templates and public files,
and whoever deploys it can customize the look and feel by pointing the
plugin to one or more directories with the same layout:

   /etc/myapp/look-and-feel/templates/layouts/default.html.ep
   /etc/myapp/look-and-feel/public/css/site.css
   /etc/myapp/look-and-feel/public/img/logo.png

Files found there take precedence over the application's own; anything
else falls back to the application. See L</global>.

=item Individual branding

In a multi-tenant setup the brand is decided for each request, e.g.
from the C<Host> header, and each brand keeps its own files in one or
more directories:

   brands/acme/templates/index.html.ep
   brands/acme/public/css/site.css
   brands/umbrella/public/img/logo.png

Again, only the files that a brand overrides need to be there,
everything else falls back to the (possibly globally branded)
application files. Deciding the brand of a request is up to the
application, see L</individual> and L</How the brand is applied>.

=back

Templates and public files are looked up at the same URLs and with the
same names as usual, so C<< stylesheet '/css/site.css' >> or
C<< render(template => 'index') >> pick the branded version
automatically. This includes layouts and partial templates.


=head1 CONFIGURATION

The plugin accepts a hash reference with the following keys, both
optional. Any other key makes the plugin croak.

=head2 global

   global => '/path/to/dir',
   global => [ 'dir1', $mojo_file, ... ],
   global => {
      paths  => '/etc/myapp/look-and-feel',
      public => '/srv/myapp/static',
   },

A specification as for a brand (see L</brands>), except that
L</ignore_app_paths> is not allowed: e.g. one directory or an array of
directories, each with C<templates> and C<public> sub-directories (if
present). The resulting directories are put in front of the
application's renderer and static paths; the order among them, and the
handling of C<undef> items and missing directories, are the same as
for a brand. This allows using the same configuration across
environments, e.g. C<< global => [ $ENV{MYAPP_LOOK} ] >> (an empty
variable makes the plugin croak, see L</brands>).

When the plugin is registered more than once with C<global>, the
directories of each registration are put in front of those of the
earlier ones (last in, first out): a later C<global> wins, while the
earlier ones are still used for the files it does not have.

=head2 individual

A hash reference with the following keys, both optional (any other
key makes the plugin croak):

=over

=item brands

   brands => {
      acme     => 'brands/acme',
      umbrella => [ 'brands/umbrella', '/srv/shared/umbrella' ],
      special  => {
         paths     => 'brands/special',
         templates => { paths => '/srv/special/views', ignore_app_paths => 1 },
         public    => '/srv/special/static',
      },
   },

A hash reference from brand names to their specification. The name is
what the application puts in the stash (see L</stash_key>) and does
not need to match any directory name. A specification is either:

=over

=item *

one directory or an array of directories, short for C<< { paths => ... } >>;

=item *

a hash reference with the following keys, all optional:

=over

=item paths

One directory or an array of directories, each holding the files of
the brand in its C<templates> and C<public> sub-directories (both
optional):

   <dir>/templates/...
   <dir>/public/...

=item templates

=item public

Further directories of templates or public files, used I<directly>
(i.e. they are not expected to have C<templates> or C<public>
sub-directories). Either one directory, an array of directories, or a
hash reference with keys:

=over

=item paths

one directory or an array of directories;

=item ignore_app_paths

if true, the application's own directories (including the L</global>
ones) are not used for this brand, e.g. a template or public file that
the brand does not have is not found, instead of falling back to the
application's one. Files embedded in C<__DATA__> sections and the
files bundled with Mojolicious are still found. If the brand ends up
with no directories of that kind, e.g. because they are missing on
this installation, a warning is logged at startup: the brand would
have no templates or public files at all.

=back

=back

=back

For each brand, templates and public files are searched in this order:
the directories in L</templates> or L</public>, then the matching
sub-directories of the directories in L</paths>, then the
application's directories (unless L</ignore_app_paths>). In each
list, the first directory wins.

Directories are given as strings or L<Mojo::File> objects; relative
paths are resolved from the application home. C<undef> items and
directories that do not exist are silently skipped. A brand whose
specification is C<undef> is not configured, and is removed if an
earlier registration configured it: this allows e.g.
C<< acme => $ENV{ACME_LOOK} >> when the variable is not set (an empty
one makes the plugin croak). A brand whose directories are all
skipped is still a valid brand, it just has no files of its own.

The plugin croaks on empty strings, on references other than
L<Mojo::File> objects where a directory is expected, and on unknown
keys in a specification, so that a typo like C<ignore_app_path> does
not go unnoticed.

=item stash_key

   stash_key => 'tenant',

The stash key where the application puts the brand of the request,
C<branding.brand> by default. See L</How the brand is applied>.

=back

The plugin can be registered more than once. Brands from all
registrations are collected; when a brand is configured again, the
later specification replaces the earlier one entirely (unlike
L</global>, see there).

Individual branding is set up by the first registration whose
C<individual> has a L</stash_key> or names at least one brand in
L</brands>, even with an C<undef> specification: this applies roles to
the application's renderer and static file server and adds the
L</brand> helper. Registrations without C<individual>, or whose
C<individual> is empty or has only an empty L</brands>, leave them
alone. L</stash_key>
is set by the registration that sets up individual branding (to
C<branding.brand> if not given); later registrations can omit it or
repeat the same value, any other value makes the plugin croak.


=head1 How the brand is applied

The plugin does not decide the brand of a request: the application
puts it in the stash key L</stash_key> (C<branding.brand> by default),
e.g. with the L</brand> helper from a C<before_dispatch> hook. The
brand can come from anywhere: the C<Host> header (as in the
L</SYNOPSIS>), a header set by a reverse proxy, a cookie, a
database...

Each brand gets its own L<Mojolicious::Renderer> and
L<Mojolicious::Static>, created the first time they are needed (a
brand with no directories of its own, and not ignoring the
application's ones, just uses the application's). Their
directories are those of the brand followed by the application's ones
(see L</brands>), the other settings are copied from the
application's renderer and static file server at that moment: the
handlers and the helpers are shared, and each brand gets its own
template cache, of the same class and size as the application's.
Roles already applied to the application's renderer or static file
server apply to the brand ones too, but attributes added by those
roles are not copied and start from their defaults. When a
request has a brand, the application's renderer and static file server
just hand the work over to the brand ones, which then follow the usual
Mojolicious rules.

Public files are served by Mojolicious itself, at the usual point of
the request: after all C<before_dispatch> hooks, whatever the order in
which they and the plugin were registered, and only if none of them
has already rendered a response or called C<render_later>. The static
C<prefix>, C<after_static> hooks and C<< reply->static >> all work as
for the application's files. Hence, the brand must be in the stash by
the end of the C<before_dispatch> hooks for public files to be
branded.

Templates are rendered according to the brand in the stash at the time
of rendering. This covers layouts, partial templates (C<include>) and
the pages for exceptions and missing resources too, e.g. a brand can
override just C<layouts/default.html.ep> and keep the application's
pages. The brand can also be set later than for public files, e.g. by
a route with C<< $c->brand('acme') >>; this changes the brand of the
templates, but not of the public files, which are served before
routing. Brand templates can use any handler (e.g. C<.ep> or C<.epl>),
independently of the application's template with the same name.

The brand and C<variant> are independent: the application can keep
using variants (e.g. C<phone>) and brands can provide their own
variant templates (e.g. C<index.html+phone.ep>). As usual in
Mojolicious, a variant template found in I<any> directory wins over a
plain template, so a variant template of the application is preferred
over a plain template of the brand: a brand overriding a page should
also override its variants.

Only brands listed in L</brands> are ever used: any other value in the
stash, including one coming straight from the request, just means "no
branding". There is no need to validate the brand against path
traversal, although the application should still make sure that it is
I<allowed> for the request.


=head1 INTERFACE

=head2 brand

   my $brand = $c->brand;
   $c->brand('acme');
   $c->brand('acme')->render(template => 'index');

Helper to get or set the brand of the request, i.e. the stash value at
L</stash_key>. Setting C<undef>, or a brand that is not in
L</brands>, means no branding. When setting, it returns the controller,
so that calls can be chained. The helper is only available once
individual branding is set up (see L</individual>).

=head2 register

   $plugin->register($app, \%config);

Registers the plugin in the application, see L</CONFIGURATION>. Called
by L<Mojolicious/plugin>, you should not need to call it directly.


=head1 BUGS AND LIMITATIONS

Minimum perl version 5.24, minimum Mojolicious version 9.34.

=over

=item *

C<url_for_asset> uses the application's static files and ignores the
brand.

=item *

Mojolicious computes ETags of static files from their modification time
only. When the brand does not come from the host (e.g. from a cookie),
a browser switching brand may get a C<304 Not Modified> for a file of
the previous brand. In that case, put the brand in the URL.

=item *

Directories, both global and of brands, are checked at startup: adding
a new directory, or a C<templates> or C<public> sub-directory to an
existing one, requires a restart.

=item *

The renderer and static file server of a brand copy the application's
directories and settings (e.g. the static C<prefix>) when they are
created, i.e. at the first request for that brand in each process.
Later changes to the application's directories and to settings like
the static C<prefix> are not seen by the brand, while handlers,
helpers and classes are shared, so additions to them are. Attributes
added by roles are not copied at all: a role that needs
configuration on the application's renderer or static file server
gets its defaults in the brand ones.

=item *

As Mojolicious does for the application at startup, the renderer of a
brand indexes its templates when it is created: new templates with a
handler other than the default one, and new variant templates, need a
restart. Changes to existing files and new public files are picked up
as usual. Note that C<morbo> only watches C<lib> and C<templates> by
default: use e.g. C<morbo -w brands> during development.

=item *

Each brand compiles and caches the templates it renders, including the
application's ones, separately from the application and from other
brands. This happens once per brand and process, at the first
rendering of each template, and the cache of each brand is limited
like the application's one.

=item *

Only rendering and serving files are branded: calling methods of the
application's renderer or static file server directly (e.g.
C<< $app->renderer->template_path(...) >>) ignores the brand, and so
would a template handler that uses C<< $app->renderer >> instead of the
renderer it is given.

=item *

Setting up individual branding applies roles to the application's
renderer and static file server, which changes their class. Applying
further roles to them later with the C<+Name> shorthand of
L<Mojo::Base/with_roles> then looks for the role under the new class
name and fails: apply such roles before registering the plugin, or use
the full role name.

=item *

As in plain Mojolicious, a leading C</> in a template name is ignored,
but only for templates with the default handler: e.g.
C<< render(template => '/page') >> does not find C<page.html.epl>.

=back

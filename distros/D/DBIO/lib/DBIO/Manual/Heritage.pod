=head1 NAME

DBIO::Manual::Heritage - Everything that changed from DBIx::Class to DBIO

=head1 VERSION

version 0.900005

=head1 OVERVIEW

DBIO is a fork of L<DBIx::Class>. It retains the relational-mapping model
and most of the API surface, but replaces, extends, and integrates a
significant number of components. This document is the definitive reference
for everyone migrating from DBIx::Class, or anyone who needs to understand
what DBIO is relative to its ancestor.

=head2 Naming

B<DBIO> stands for I<DBI Objects>. The namespace C<DBIO::> replaces
C<DBIx::Class::> throughout. Every module, every test, every tool has been
renamed accordingly.

DBIO is a clean break - there is no runtime C<DBIx::Class> compatibility
shim. Existing code is migrated by mechanical rename (C<DBIx::Class::*>
to C<DBIO::*>) plus the targeted API updates listed in
L<DBIO::Manual::Migration>.

=head1 FUNDAMENTAL ARCHITECTURE CHANGES

=head2 DBIO::Base - the new meta-infrastructure base

DBIx::Class distributed its meta-level machinery across several internal
packages. DBIO consolidates it into L<DBIO::Base>, which every internal
class uses as its root:

=over 4

=item C<use mro 'c3'> - MRO forced to C3 for the entire inheritance tree

=item L<DBIO::Componentised> - the C<load_components()> machinery

=item L<Class::Accessor::Grouped> - C<mk_group_accessors()>

=item Perl subroutine attributes via C<MODIFY_CODE_ATTRIBUTES>

=item C<_skip_namespace_frames> for clean stack traces

=back

B<Do not use C<DBIO::Base> directly in application code.> It is the
machinery that everything else stands on. For your Result classes use
L<DBIO::Core>; for ResultSet classes use L<DBIO::ResultSet>; for schema
classes use L<DBIO::Schema>.

=head2 SQL::Abstract replaces SQL::Abstract::Classic

DBIx::Class depended on L<SQL::Abstract::Classic>, an older fork.
DBIO uses the canonical L<SQL::Abstract> (>= 2.000001) instead. The query API
is compatible; the internal extensions required small adjustments in the
SQLMaker layer.

=head2 apply_limit replaces limit_dialect

DBIx::Class used a C<sql_limit_dialect> string and an C<emulate_limit()>
dispatch table inside the storage layer. DBIO removes both. The SQLMaker's
C<apply_limit($sql, $rs_attrs, $rows, $offset)> method renders the limit
instead. The default implementation emits C<LIMIT ? OFFSET ?>; a driver
whose database needs another syntax overrides it in its SQLMaker subclass.

If you had custom C<emulate_limit()> overrides, override C<apply_limit>
on your SQLMaker subclass.

=head2 Driver distributions split out of core

All database-specific storage classes have been removed from the DBIO core
distribution and moved into dedicated CPAN distributions:

  DBIO-PostgreSQL    DBIO::PostgreSQL    (most advanced: pg_catalog introspect,
                                          enums, schemas, RLS, indexes)
  DBIO-MySQL         DBIO::MySQL
  DBIO-SQLite        DBIO::SQLite
  DBIO-DuckDB        DBIO::DuckDB        (embedded analytical; UUID, Arrow,
                                          Appender, quack RPC)
  DBIO-DB2           DBIO::DB2
  DBIO-Firebird      DBIO::Firebird
  DBIO-Informix      DBIO::Informix
  DBIO-MSSQL         DBIO::MSSQL
  DBIO-Oracle        DBIO::Oracle
  DBIO-Sybase        DBIO::Sybase

Install only the driver you need. Every driver ships its own native
introspection, diff, and deploy modules (the test-and-compare strategy) and
does not require L<SQL::Translator>.

Async is an explicit, per-connection mode whose queries return C<Future>
objects; each mode's transport is its own distribution. There is also a GraphQL
projection layer:

  DBIO-Forked             DBIO::Forked              (mode 'forked': fork per
                                                     query, any driver, no loop)
  DBIO-Async              DBIO::Async               (mode 'future_io': the
                                                     driver's own async DBD
                                                     binding via Future::IO)
  DBIO-PostgreSQL-EV      DBIO::PostgreSQL::EV      (mode 'ev': libpq via EV::Pg)
  DBIO-MySQL-EV           DBIO::MySQL::EV           (mode 'ev': MariaDB via
                                                     EV::MariaDB)
  DBIO-GraphQL            DBIO::GraphQL             (Result classes -> GraphQL)

=head2 Replicated storage is now in core

C<DBIx::Class::Replicated> was an external distribution. L<DBIO::Replicated>
ships in the core distribution. Load it as a Schema component; it forces
C<+DBIO::Replicated::Storage> and coordinates a master backend plus optional
replicants:

  package MyApp::Schema;
  use DBIO 'Schema', -pg;
  __PACKAGE__->load_components('Replicated');

  my $schema = MyApp::Schema->connect($dsn, $user, $pass, {
      balancer_type => 'DBIO::Replicated::Balancer::First',
  });
  $schema->storage->connect_replicants([ $replica_dsn, $user, $pass ]);

Writes, transactions and deploy go through the master; reads are delegated to
the balancer (default C<DBIO::Replicated::Balancer::First>). The internals
live in L<DBIO::Replicated::Pool>, L<DBIO::Replicated::Backend>, and
L<DBIO::Replicated::Balancer>.

=head2 SQL::Translator is optional

Every driver ships its own native Deploy, Introspect, and Diff modules.
C<DBIO::Schema-E<gt>deploy()> checks the active storage class for a
C<dbio_deploy_class()> method; if present it routes to the native class,
which deploys by introspecting both the live database and the desired schema
and diffing the two models (test-and-compare). If a storage declares no
native class, C<deploy()> does not silently translate the schema for you: it
falls through to C<deployment_statements()>, which reads a pre-existing DDL
file and throws if none is present. Core's deploy path never calls
L<SQL::Translator>, so SQL::Translator is an optional dependency rather than a
required one.

=head1 RESULT CLASS STYLES

DBIx::Class had one way to write a Result class: the explicit
C<__PACKAGE__-E<gt>method()> style. DBIO keeps that (called I<Vanilla>)
and adds two sugar layers.

=head2 Vanilla (classic, unchanged API)

  package MyApp::Schema::Result::Artist;
  use base 'DBIO::Core';
  __PACKAGE__->table('artist');
  __PACKAGE__->add_columns(
      artistid => { data_type => 'integer', is_auto_increment => 1 },
      name     => { data_type => 'varchar', size => 100 },
  );
  __PACKAGE__->set_primary_key('artistid');
  __PACKAGE__->has_many(cds => 'MyApp::Schema::Result::CD', 'artistid');
  1;

See L<DBIO::Core> and L<DBIO::Manual::ResultClass>.

=head2 Candy (import-sugar, method renaming)

L<DBIO::Candy> removes the C<__PACKAGE__-E<gt>> boilerplate and exports
short aliases. It also infers the table name from the package name.

  package MyApp::Schema::Result::Artist;
  use DBIO::Candy;
  column artistid => { data_type => 'integer', is_auto_increment => 1 };
  column name     => { data_type => 'varchar', size => 100 };
  primary_key 'artistid';
  has_many cds => 'MyApp::Schema::Result::CD', 'artistid';
  1;

Key aliases exported by Candy:

  column             -> add_columns
  primary_key        -> set_primary_key
  unique_constraint  -> add_unique_constraint
  relationship       -> add_relationship

Candy is derived from C<DBIx::Class::Candy>, which has been integrated into
the core distribution.

=head2 Cake (DDL-like DSL - most concise)

L<DBIO::Cake> reads like schema DDL. Type functions (C<integer>, C<varchar>,
C<serial>, C<uuid>, C<json>, C<jsonb>, C<text>, C<boolean>, ...) replace the
verbose column-info hashref.

  package MyApp::Schema::Result::Artist;
  use DBIO::Cake;
  col artistid => serial, auto_inc;
  col name     => varchar(100);
  primary_key 'artistid';
  has_many cds => 'MyApp::Schema::Result::CD', 'artistid';
  1;

Cake modifiers:

  null        auto_inc     fk($target)
  default     unsigned     on_create    on_update

Driver shortcuts activate driver-specific column types and components in one
import flag:

  use DBIO::Cake -Pg;       # PostgreSQL defaults (uuid, jsonb, ...)
  use DBIO::Cake -MySQL;
  use DBIO::Cake -SQLite;

Other import flags:

  -inflate_datetime    load InflateColumn::DateTime automatically
  -inflate_json        inflate json columns to hashrefs
  -inflate_jsonb       inflate jsonb columns (PostgreSQL)
  -retrieve_defaults   fetch server-side defaults after insert

The type registry on the active Storage class (C<cake_defaults()>,
C<type_info($name)>) drives driver-aware column type resolution.

=head1 INTEGRATED COMPONENTS

The following features were previously separate CPAN distributions or
required C<load_components>. In DBIO they are part of core and need no
explicit loading unless noted.

=head2 DBIO::Timestamp (was DBIx::Class::TimeStamp)

Automatic C<created_at> / C<updated_at> timestamps. Configure per column:

  col created_at => timestamp, on_create;
  col updated_at => timestamp, on_update;

Or use the helpers available in all three styles:

  col_created 'created_at';        # set on insert
  col_updated 'updated_at';        # set on insert and update
  cols_updated_created();          # both with default names

Available via L<DBIO::Timestamp>. No C<load_components> needed in Cake or
Candy; Vanilla code can still load it explicitly.

=head2 Row helpers (was DBIx::Class::Helpers)

The following helpers from C<DBIx::Class::Helpers> are integrated directly
into L<DBIO::Row> and require no C<load_components> call:

=over 4

=item L<DBIO::Row/TO_JSON> - serializable hashref, excludes blob/text columns

=item L<DBIO::Row/serializable_columns> - list of serializable column names

=item L<DBIO::Row/self_rs> - a ResultSet scoped to this row

=item L<DBIO::Row/get_storage_value> - original DB value before in-memory changes

=item L<DBIO::Row/before_column_change> - fire a callback before a column is modified

=item L<DBIO::Row/after_column_change> - fire a callback after a column is modified

=item L<DBIO::Row/around_column_change> - wrap a column update with an around-style hook

=item L<DBIO::Row/proxy_resultset_method> - expose a ResultSet C<with_*> method as a row accessor

=back

These come from C<DBIx::Class::Helper::Row::StorageValues>,
C<DBIx::Class::Helper::Row::OnColumnChange>, and
C<DBIx::Class::Helper::ResultSet::ProxyResultSetMethod>.

=head2 ResultSet helpers (was DBIx::Class::Helpers)

The C<DBIx::Class::Helper::ResultSet::*> family is integrated into
L<DBIO::ResultSet> and likewise needs no C<load_components>. Upstream these
are components loaded per ResultSet class; in DBIO they are core API.

Attribute shortcuts, each of them a chainable C<< ->search(undef, {...}) >>:

=over 4

=item L<DBIO::ResultSet/order_by> - C<!col> means DESC, C<< -desc => 'col' >> too

=item L<DBIO::ResultSet/columns>, L<DBIO::ResultSet/add_columns>, L<DBIO::ResultSet/remove_columns>, L<DBIO::ResultSet/no_columns>

=item L<DBIO::ResultSet/distinct>, L<DBIO::ResultSet/group_by>, L<DBIO::ResultSet/prefetch>, L<DBIO::ResultSet/hri>

=item L<DBIO::ResultSet/rows>, L<DBIO::ResultSet/limit>, L<DBIO::ResultSet/limited_page>, L<DBIO::ResultSet/has_rows>

=back

Search shortcuts. A leading dot qualifies the column with the current source
alias, so C<< ->null('.title') >> means C<me.title>:

=over 4

=item L<DBIO::ResultSet/null>, L<DBIO::ResultSet/not_null>, L<DBIO::ResultSet/like>, L<DBIO::ResultSet/not_like>

=item L<DBIO::ResultSet/search_or> - OR together several ResultSets

=item L<DBIO::ResultSet/me> - the current source alias with a dot appended

=back

Set operations, existence and the rest:

=over 4

=item L<DBIO::ResultSet/union>, L<DBIO::ResultSet/union_all>, L<DBIO::ResultSet/intersect>, L<DBIO::ResultSet/intersect_all>, L<DBIO::ResultSet/except>, L<DBIO::ResultSet/except_all>

=item L<DBIO::ResultSet/results_exist>, L<DBIO::ResultSet/results_exist_as_query> - cheaper than C<count>

=item L<DBIO::ResultSet/correlate> - a related ResultSet as a correlated subquery

=item L<DBIO::ResultSet/one_row>, L<DBIO::ResultSet/bare>, L<DBIO::ResultSet/rand>, L<DBIO::ResultSet/explain>

=back

Two divergences worth knowing. C<rand> and C<explain> are built on the storage
hooks C<_random_function> and C<_explain_query> rather than upstream's
C<DBIx::Introspector>, so a driver declares its own dialect. And C<page> is
B<not> the upstream shortcut - DBIO kept the DBIx::Class core method, which
builds its ResultSet directly instead of routing through C<search>.

C<DBIx::Class::Helper::ResultSet::IgnoreWantarray> was deliberately not taken
over; DBIO removes C<search>'s context-dependent return type outright instead.
Also not integrated: C<DateMethods1>, C<Errors>, C<AutoRemoveColumns>,
C<ResultClassDWIM>, and the upstream-deprecated C<VirtualView> and C<Union>.
The reasoning for each is recorded in ADR 0011.

=head2 IntrospectableM2M (was DBIx::Class::IntrospectableM2M)

Many-to-many introspection is integrated into
L<DBIO::Relationship::ManyToMany>. The C<_m2m_metadata> structure is
populated automatically when you declare a C<many_to_many> relationship. No
C<load_components> needed.

Accessible fields: C<accessor>, C<relation>, C<foreign_relation>,
C<rs_method>, C<add_method>, C<set_method>, C<remove_method>.

=head2 DBIO::UUIDColumns (was DBIx::Class::UUIDColumns)

Auto-generate UUID values on insert. Load the component and flag the
columns with C<uuid_on_create>:

  __PACKAGE__->load_components('UUIDColumns');
  __PACKAGE__->add_columns(
      id => { data_type => 'varchar', size => 36, uuid_on_create => 1 },
  );

Cake's C<uuid> type function is a column type only
(C<< data_type => 'uuid' >>); it does not generate a value.

The default generator makes random version 4 UUIDs from L<Crypt::URandom>.
C<uuid_class()> selects C<Data::UUID> or C<UUID> explicitly.

See L<DBIO::UUIDColumns>.

=head2 DBIO::EncodedColumn

One-way encoding of column values (passwords with Bcrypt or Argon2, tokens
with Digest). Unlike the other
components in this chapter it must be loaded:

  __PACKAGE__->load_components('EncodedColumn');

Then mark a column:

  __PACKAGE__->add_columns(
      password => {
          data_type       => 'varchar',
          size            => 100,
          encode_column   => 1,
          encode_check_method => 'check_password',
      },
  );

The column is encoded transparently on write. The C<check_password>
(or whatever name you give C<encode_check_method>) method is generated
automatically on the Result class.

The default C<encode_class> is C<Bcrypt> (cost 12, stored as C<$2b$...>);
C<Argon2> stores C<$argon2id$...>; C<Digest> (SHA-256, SHA-384, SHA-512 or
SHA3-*) stores C<dbio$E<lt>algoE<gt>$E<lt>salt_b64E<gt>$E<lt>digest_b64E<gt>>.
An unknown C<encode_class>, an unknown C<encode_args> key of the class or a
Digest algorithm outside that list is refused when the class is loaded. A
stored value without hash format matches only with
C<< accept_unencoded =E<gt> 1 >> in C<encode_args>.

See L<DBIO::EncodedColumn>.

=head2 DBIO::HashAccessor

Accessor generation for serialized hash columns (JSON, YAML, MessagePack):

  __PACKAGE__->add_hash_accessor('metadata', 'metadata_col');

Generates: C<metadata()>, C<metadata_hash()>, C<metadata_hash_delete()>,
C<metadata_push()>, C<metadata_shift()>.

See L<DBIO::HashAccessor>.

=head2 InflateColumn::Serializer (JSON, YAML, MessagePack)

Serialize complex Perl structures to a text/blob column. Available via
C<load_components('InflateColumn::Serializer')>. Serializer options:
C<JSON>, C<YAML>, C<MessagePack>.

=head2 PopulateMore (was DBIx::Class::Schema::PopulateMore)

L<DBIO::PopulateMore> adds C<populate_more()>, which fills several sources
in one call and lets a row refer to one created earlier in the same call.
Load it on the schema class:

  __PACKAGE__->load_components('PopulateMore');

  $schema->populate_more([
      { Gender => {
          fields => 'label',
          data   => { male => 'male', female => 'female' },
      } },
      { Person => {
          fields => [ 'name', 'gender' ],
          data   => { john => [ 'john', '!Index:Gender.male' ] },
      } },
  ]);

Values starting with C<!> are inflated: C<!Index:Source.key> is the row
created under that key, C<!Env:NAME> a value from C<%ENV>, and
C<!Find:Source.[key=val]> an existing row. C<< $schema->populate >> is the
plain per-source L<DBIO::Schema/populate>.

=head1 NEW CONCEPTS

These features did not exist in DBIx::Class in any form.

=head2 DBIO::ChangeLog - audit trail per Result class

Automatic row-level change tracking. Add to a Result class:

  __PACKAGE__->load_components('ChangeLog');

and to the schema class:

  __PACKAGE__->load_components('ChangeLog::Schema');

The schema component registers a companion source
C<E<lt>SourceE<gt>_ChangeLog> (table C<E<lt>tableE<gt>_changelog>) for every
tracked source; C<< $schema->deploy_changelog >> deploys those tables.
By default every column change is recorded (INSERT, UPDATE, DELETE).
Exclude sensitive columns with the C<changelog> column flag:

  __PACKAGE__->add_columns(
      password_hash => { data_type => 'varchar', size => 255, changelog => 0 },
  );

Changes are stored as JSON. Methods on a row of a tracked Result class:

  $row->changelog;                    # ResultSet of this row's log entries
  $row->changelog_serialize_changes($hashref);
  $row->changelog_deserialize_changes($json_str);

The C<changes> column is C<text>. A driver or application component can
override C<changelog_column_definitions> to use a native type (e.g. C<jsonb>
on PostgreSQL).
The DBIx::Class::Schema::Versioned-style standalone versioning (DBIO::Version)
was dropped in favour of L<DBIO::DeploymentHandler>; there is no
C<dbio_schema_versions> table. The L<DBIO::DeploymentHandler> version table
was renamed from its upstream name C<dbix_class_deploymenthandler_versions>
to C<dbio_deploymenthandler_versions> (fork-rename); databases deployed with
an older DBIO must be migrated manually (see
L<DBIO::DeploymentHandler/COMPATIBILITY: VERSION TABLE RENAME>).

See L<DBIO::ChangeLog> and L<DBIO::ChangeLog::Schema>.

=head2 DBIO::AccessBroker - credential source interface

A storage-agnostic interface for credential lifecycle management. A broker
is a B<CredentialSource>: it supplies the connect info for one backend
identity. It does not route and does not own a host list - read/write
routing and the master/replicant topology belong to L<DBIO::Replicated>.
Pass a broker to C<connect()> in place of a DSN; the storage detects it
and attaches it:

  my $schema = MyApp::Schema->connect(
      DBIO::AccessBroker::Static->new(
          host     => $host,
          dbname   => $dbname,
          username => $user,
          password => $pass,
      )
  );

The storage calls C<connect_info_for_storage($storage)> on the broker
before each connection. C<Static> answers connection parameters, not a DSN:
the storage builds the DSN for its driver, so the schema must load its driver
component. One credential can serve many servers: the application builds a
C<< $broker->for_host($host) >> view per server and hands each to the
connection on that host (L<DBIO::Replicated> passes the views through).

Built-in broker classes:

=over 4

=item L<DBIO::AccessBroker::Static> - one fixed set of connection parameters

=item L<DBIO::AccessBroker::Vault> - rotating credentials with TTL

=item L<DBIO::AccessBroker::HostBound> - one credential identity pinned to one host

=back

Build a custom broker by subclassing L<DBIO::AccessBroker> and implementing
C<connect_info_for_storage>, C<needs_refresh>, and C<refresh>.

=head2 DBIO::Moo and DBIO::Moose - OO framework bridges

Use Moo or Moose attributes alongside DBIO column accessors in the same
Result, ResultSet, or Schema class.

  package MyApp::Schema::Result::Artist;
  use DBIO::Moo;
  use DBIO::Cake;

  col artistid => serial, auto_inc;
  col name     => varchar(100);
  primary_key 'artistid';

  has display_name => (is => 'lazy');
  sub _build_display_name { 'Artist: ' . $_[0]->name }

  1;

L<DBIO::Moo> and L<DBIO::Moose> wire the framework constructor
(C<FOREIGNBUILDARGS> for Moo, C<BUILDARGS> for Moose) into DBIO's C<new()>
so that DBIO column data is routed correctly and Moo/Moose attributes are
filtered from DBIO's column constructor.

Combinations with Cake and Candy are fully supported. Use
L<DBIO::Cake> with C<use DBIO::Moo> in the same file.

See L<DBIO::Moo> and L<DBIO::Moose>.

=head2 Async storage interface

L<DBIO::Storage::Async> defines a storage-agnostic async interface
(Phase 1 + 2). Queries return C<Future> objects. Async is an explicit,
per-connection mode -- C<< connect($dsn, $user, $pass, { async => 'forked' |
'future_io' | 'ev' | 'immediate' }) >> -- and the C<ev> mode bypasses DBI
entirely through a per-driver native client:

=over 4

=item C<DBIO::PostgreSQL::EV> (C<DBIO-PostgreSQL-EV>) - C<libpq> via
C<EV::Pg>; adds COPY IN/OUT and request pipelining.

=item C<DBIO::MySQL::EV> (C<DBIO-MySQL-EV>) - the MariaDB client via
C<EV::MariaDB>, which pipelines consecutive queries automatically at the
wire level.

=back

The core async interface is in C<DBIO::Storage::Async>. It includes
transaction pinning: C<txn_do_async> takes one connection from the pool and
runs the whole transaction on it, and every pooled transport inherits that --
C<future_io> and both C<ev> backends alike. It also includes
LISTEN/NOTIFY (ADR 0056): core owns the self-healing listen machinery, and
PostgreSQL carries it on both the C<future_io> and the C<ev> transport.
Application code that targets multiple backends should program against that
interface; the modes and their transports are described in
L<DBIO::Manual::AsyncStorage>.

=head2 Type registry on Storage

Each driver's Storage class exposes:

  $schema->storage->cake_defaults()        # hashref of driver-preferred options
  $schema->storage->type_info($type_name)  # { components => [...], cake_options => {...} }

The Cake DSL reads this registry when resolving column types so that, for
example, C<col data =E<gt> jsonb> on a PostgreSQL storage automatically
activates C<InflateColumn::JSONB>.

=head2 DBIO::Storage::DateTimeFormat - shared driver datetime base

DBIx::Class drivers each hand-rolled a private C<DateTime::Format::*> wrapper
package inside their storage class, typically C<require>-ing
L<DateTime::Format::Strptime> at runtime. DBIO replaces these with a shared
base, L<DBIO::Storage::DateTimeFormat>. A driver's datetime format class
declares its strptime patterns as class data and may name a preferred CPAN
C<DateTime::Format::*> class:

  package DBIO::DriverName::DateTime::Format;
  use base 'DBIO::Storage::DateTimeFormat';
  __PACKAGE__->preferred_format_class('DateTime::Format::DriverName'); # optional
  __PACKAGE__->datetime_parse_pattern('%Y-%m-%d %H:%M:%S');
  __PACKAGE__->datetime_format_pattern('%Y-%m-%d %H:%M:%S');

When the preferred class is installed it handles parsing and formatting;
otherwise the declared patterns are used via L<DateTime::Format::Strptime>
(a hard dependency of core, so drivers declare nothing extra). The pattern
fallback round-trips identically to the preferred class.

=head1 UTILITY CHANGES

=head2 DBIO::Util replaces DBIx::Class::_ENV_

The internal C<DBIx::Class::_ENV_> pseudo-package has been removed. All runtime
constants and utility functions are now in L<DBIO::Util>:

  use DBIO::Util qw( is_windows help_url scope_guard ... );

Exported functions include:

  is_windows   is_dev_release   old_mro   has_ithreads
  dbiotest     peepeeness       shuffle_unordered_resultsets
  help_url     iv_size          os_name

  sigwarn_silencer   modver_gt_or_eq   assert_no_list_context
  refdesc  refcount  hrefaddr  scope_guard
  quote_sub  qsub  perlstring  serialize  dump_value
  UNRESOLVABLE_CONDITION

  dir_path   file_path   parent_dir   slurp_file   write_file
  mkpath     rmtree      class_path

  firstidx  uniq  apply  array_eq
  is_plain_value   is_literal_value

C<Path::Class> is no longer a dependency; use the C<DBIO::Util> path helpers
instead.

=head2 DBIOx namespace

The C<DBIOx::> namespace is reserved for official DBIO extensions that are
not part of the core distribution - analogous to C<DBIx::> but scoped to the
DBIO ecosystem.

=head1 REMOVED FEATURES

=head2 Class::DBI compatibility (CDBICompat)

The C<DBIx::Class::CDBICompat> layer and the legacy C<DB.pm> shim have been
removed entirely. There is no replacement. If you depend on C<Class::DBI>
compatibility, stay on DBIx::Class or port your code.

=head2 Hide-from-PAUSE package trick

Internal packages no longer use the C<package # hide from PAUSE\nFoo::Bar;>
trick. L<Meta::NoIndex> in the distribution's C<META.yml> handles PAUSE
exclusion instead.

=head2 Removed external dependencies

=over 4

=item C<SQL::Abstract::Classic> - replaced by C<SQL::Abstract>

=item C<Path::Class> - replaced by helpers in L<DBIO::Util>

=item C<Sub::Name> - no longer used

=item C<SQL::Abstract::Util> - merged into L<SQL::Abstract> core

=back

=head1 TESTING INFRASTRUCTURE

=head2 DBIO::Test - database-free unit testing

Core tests B<must not> use a real database. L<DBIO::Test> provides a mock
storage back-end:

  use DBIO::Test;
  my $schema = DBIO::Test->init_schema();    # fake storage, no DBI

  my $storage = $schema->storage;
  $storage->mock(qr/SELECT .* FROM artist/, [
      { artistid => 1, name => 'Tori Amos' },
  ]);

Driver-specific tests (real SQL, real DBI) belong in the driver distributions.

=head2 Shared test schemas

The test schema shared across the core and driver distributions is
L<DBIO::Test::Schema> under C<dbio/lib/>, with its result classes in
C<DBIO::Test::Schema::*>:

  DBIO::Test::Schema::Artist
  DBIO::Test::Schema::CD
  DBIO::Test::Schema::Track
  ...

The optional OO-framework demo schemas are standalone schema classes and
live as B<siblings> of (not under) C<DBIO::Test::Schema>. Keeping them out
of the C<DBIO::Test::Schema::*> namespace is deliberate: a no-arg
C<load_classes> sweep of that namespace would otherwise try to load them
and die on any box lacking the optional dependency (Moose / MooseX::NonMoose
/ Moo). Tests that use them guard with C<eval { require ... }>.

  DBIO::Test::MooSchema         # Moo result classes
  DBIO::Test::MooseSchema       # Moose result classes
  DBIO::Test::MooCakeSchema     # Moo + Cake DDL
  DBIO::Test::MooseSugarSchema  # Moose + Cake DDL

Load driver-specific result classes with the hashref form:

  DBIO::Test::Schema->load_classes({
      'DBIO::PostgreSQL::Test' => ['SequenceTest'],
  });

Never redefine a shared schema class inline inside a driver test.

=head2 Environment variables renamed

All test environment variables were renamed from C<DBICTEST_*> to
C<DBIO_TEST_*>:

  DBIO_TEST_PG_DSN         PostgreSQL DSN
  DBIO_TEST_MYSQL_DSN      MySQL/MariaDB DSN

There is no SQLite equivalent. SQLite needs no connection configuration,
so DBIO defines no C<DBIO_TEST_SQLITE_DSN> and nothing reads one: in
L<DBIO::Optional::Dependencies> every server engine's live-test group is
gated on its own C<DBIO_TEST_*_DSN>, while SQLite carries a plain
C<rdbms_sqlite> group with no gate at all.

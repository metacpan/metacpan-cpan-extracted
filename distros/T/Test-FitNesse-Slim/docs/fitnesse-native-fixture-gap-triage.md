# Native-suite fixture gap triage

## Executive findings

The audit examined every one of the 93 native-suite pages whose baseline has at least one wrong, ignored, or exception result: **24 pages**. No protocol-engine defect was demonstrated. The native suite’s 321 exception assertions are not 321 defects: 2 are deliberate v0.5 ignore-control responses, while the remaining 319 are execution failures caused by unavailable fixture classes/methods, Java-only FitNesse utilities, or Java runtime features. The 51 wrong assertions group into known FitNesse expression behavior (21), nested-request context loss (5), Java reflection/conversion fixtures (14), harness startup preconditions (6), and one unavailable Table Table fixture (5).

The highest-value gap from this triage has since been implemented: a dedicated ordinary `TableTableIncFirstCol` adapter for `SymbolsInTableTable`. It remains separate from the consumer adapter, which manages symbol changes inside the fixture. The implementation also prefers a more-specific imported package over its parent, so the managed-symbol mode remains selectable when both namespaces appear in the page context.

The discrepancy inventory and root-cause group counts below describe the original 525/51/4/321 baseline. The implementation results section records the verified post-change state.

This inventory separates fixture availability from protocol compatibility. A Java class failing to load proves that the page cannot reach its intended test, not that the Perl wire implementation is wrong. The full per-page data, estimated gains, confidence, and evidence references are in [`fitnesse-native-fixture-gap-triage.json`](fitnesse-native-fixture-gap-triage.json).

## Scope and evidence

The native baseline is pinned to FitNesse v20251025 and contains 93 full page paths, 525 right, 51 wrong, 4 ignored, and 321 exceptions. Its runner validates exact per-page result counts and confirms external Perl request/response traffic. This triage selects all baseline pages with nonzero wrong, ignored, or exception counts; it does not mistake intentional ignore results for failures.

The direct Perl backend was verified from the runner’s execution logs and balanced listener trace. For ambiguous fixture and Java-client pages, I ran selected leaves using a fresh FitNesse process with `/opt/fitnesse/fitnesse.jar`; every captured execution log named `java -cp /opt/fitnesse/fitnesse.jar fitnesse.slim.SlimService 1`. The Java and Perl counts below are separate observations, not claims that their nested fixture contexts are equivalent. Java direct references were run for 15 pages, including the three nested-context pages documented in [`fitnesse-rendering-comparator-compatibility.md`](fitnesse-rendering-comparator-compatibility.md). `SystemExitIsPrevented` was not run against Java: its own page says it should be removed or pruned on Java 21+, and the environment runs OpenJDK 25.

## Root-cause groups

- **Intentional ignored outcomes and control markers:** 4 pages; 4 ignored assertions and 2 intentional ignore exceptions. The pages are `HowtoIgnoreResultValues`, `QueryTableSuite.SetContextValue`, `TestIgnoreAll`, and `TestIgnoreInScriptTable`.
- **Missing or mismatched Perl fixture adapters:** 6 pages: `ChainTest`, `DefineTableTypeTest`, `HybridDecisionTable`, `SystemUnderTestTest`, `TableTableSuite.SymbolsInTableTable`, and `TableTableSuite.TestReturnsNull`. These explain 67 exception outcomes plus the 5 wrong table-symbol checks; the exact recoverable portion varies by whether the expected fixture behavior is a useful Perl adapter or Java-only test scaffolding.
- **FitNesse Java utilities / Java test-system behavior:** 6 pages: `DisgracerTest`, `HybridDecisionTable.MethodExtractorRuleTest`, `SystemExitIsPrevented`, `TestExceptionIsDisplayed.ParameterConversionExceptions`, `TestExceptionIsDisplayed.SlimExceptionResult`, and `JavaSlimServer.CallStaticJavaMethod`. Most are specifically about Java class loading, reflection, JVM process control, or FitNesse-side result presentation.
- **Known FitNesse expression extension:** 1 page; 21 wrong assertions. Nashorn expression evaluation remains outside the SLiM protocol and is deferred.
- **Nested-request context loss:** 3 pages; 5 wrong assertions. A FitNesse-side context-aware bridge is required; explicitly excluded from this workstream.
- **Controlled startup configuration:** 4 pages; 6 wrong assertions. Requires an isolated runner topology, not fixture changes.

The categories cover 24 pages, 51 wrong assertions, 4 ignored assertions, and 321 exception results. The only exception results established as intentional controls are the 2 ignore-marker exceptions. The other 319 exception results are not equivalent to 319 defects; they are cascades or unsupported Java/test-harness cases, with the small fixture gaps identified above.

## Recommended next increment (completed)

Investigate and implement only the `TableTableSuite.SymbolsInTableTable` fixture-adapter gap. First establish the exact class import, SLiM instruction exchange, and where each table-cell symbol is substituted or assigned; then add a default-namespace Perl adapter for the page’s *ordinary* symbol behavior and regression coverage for row isolation and post-table values. Do not alias the existing consumer-managed fixture, change general import lookup, or alter the upstream page. The 15-assertion managed-symbol page is a contrast case, not a substitute implementation.

This outranked the larger exception counts because its failure had a precise fixture-resolution cause, its adjacent implementation already existed, and success exercises meaningful SLiM table/symbol traffic. Hybrid Properties remains a tempting 46-exception target, but that number mostly reflects an absent Java standard-library fixture and is not a protocol defect. Java method extraction, Disgracer, static invocation, exception-result parsing, and JVM exit prevention belong to FitNesse/Java. SUT delegation already has direct Perl unit coverage. The single ChainTest method is easy but offers only one assertion. The three nested-context pages and four startup pages remain separate harness work.

## Table Table implementation evidence

The pinned Java fixture is `fitnesse.slim.test.TableTableIncFirstCol`, constructed with no arguments. Its `doTable(List<List<?>>)` iterates input rows in order and returns `"no change"` plus `"pass:" + (Integer.parseInt(firstCell.toString()) + 1)`. It keeps no row or session state. The bundled class signature/constants match the upstream source; a clean Java SlimService run on FitNesse v20251025 reports 13 right, 0 wrong, 0 ignored, 0 exceptions.

The target page assigns A=99, B=5, C=14, constructs the ordinary fixture, and calls `doTable` once with `$A/$resultA=`, `$B/$resultB=`, and `$C/$C=` rows. Both Java and Perl return a successful table result; the following checks observe 100, 6, and 15. Its included same-table example also passes with Z=45, not 201. The existing executor substitutes the full nested input before the one fixture call. FitNesse applies output-cell symbol assignments after the complete returned table, so later row inputs cannot see assignments made by earlier output cells.

The Java and Perl v20251025 XML instruction logs agree on the relevant exchange. Both report `callAndAssign(A, scriptTableActor, echoInt, 99) → $A<-[99]`, then B=5 and C=14 similarly; `make(tableTable_44, TableTableIncFirstCol) → pass(table: Table Table Inc First Col)`; and one `call(tableTable_44, doTable, [[$A,$resultA=],[$B,$resultB=],[$C,$C=]]) → pass()`. The following calls `echoInt($resultA)`, `echoInt($resultB)`, and `echoInt($C)` return `pass(100)`, `pass(6)`, and `pass(15)` in both runs. In the included row-isolation example, the returned checks are `echoInt($Z) → pass(45)` and the running page name → `pass(13)`. FitNesse's [Table Table implementation guide](https://fitnesse.org/FitNesse/UserGuide/WritingAcceptanceTests/SliM/TableTable.html) documents the list-of-rows `doTable` contract and how returned cells are evaluated and assigned by the client.

The managed page's trace stays distinct: after X=99 and Y=44, it calls a fixture from `statementexecutorconsumer` with six `$X` rows. Its first result is 100, the fixture updates X within each row, and the final values are X=104 and Y=105. This page returns 15 right in Java and Perl. The Java execution logs positively identify `java -cp /opt/fitnesse/fitnesse.jar fitnesse.slim.SlimService 1`; the Perl native-suite run verifies its runner-owned loopback service and 724 balanced request/response exchanges.

The Perl adapter is `Fitnesse::Slim::Test::TableTableIncFirstCol` in `t/lib/`; it has no executor hook or mutable table state. It follows Java signed-int parsing/increment boundaries, including null and malformed/empty input failures. `StatementExecutor` tries a more-specific imported package before its parent, with later imports first among equally specific prefixes. This keeps `Statementexecutorconsumer::TableTableIncFirstCol` independent when the parent namespace is also imported. Focused instruction tests cover construction, dispatch, symbol substitution, row order, repeated and independent symbols, isolation, null/empty values, integer boundaries, and the managed-mode contrast.

### Null-returning Table Table fixture

The pinned fixture is `fitnesse.slim.test.DummyTableTableReturnsNull`: it has a no-argument constructor and `doTable(List<List<String>>)` returns Java `null` for the complete table. FitNesse sends `call tableTable_42 doTable [[]]`; the result is `ignore(No results from table)`, not an empty list, empty string, or exception. Java SlimService positively identified from the execution log reports 1/0/1/0. Perl initially reported 1/0/0/2 because its matching fixture adapter was absent: construction failed with `Could not find class Fitnesse::Slim::Test::DummyTableTableReturnsNull`, and the following call failed because that instance did not exist. The new `Fitnesse::Slim::Test::DummyTableTableReturnsNull` returns `undef`; the existing `StatementExecutor` and `Test::FitNesse::Slim::List` encode the protocol null without changes. The external Perl execution now also reports 1/0/1/0. Focused coverage in `t/null-table-fixture.t` exercises serialized make/call instructions, result serialization, blank and empty-list differences, missing methods, repeated calls, and executor isolation.

Imported fixture-class selection now has direct regression tests in `t/import-resolution-precedence.t`: the longest package import prefix wins regardless of order, later imports win on equal prefix length, reversed ties select the reversed class, and an absent class candidate falls through to a later valid candidate. These tests drive `StatementExecutor` and use fixture methods with distinguishable results.

The first ordinary-symbol fixture run detected only that target-page delta: right 0→13, wrong 5→0, exceptions 4→0. The later null-fixture run changed only `TestReturnsNull`: 1/0/0/2→1/0/1/0; the other 92 page results stayed exact. Current native totals are 538 right, 46 wrong, 5 ignored, and 315 exceptions across 93 pages. FitNesse's suite final counts are 72 right, 9 wrong, 1 ignored, and 11 exceptions. The separate 50-page individual baseline remains unchanged at 45 conformant, 373 right, 7 wrong, 2 ignored, and 0 exceptions.

## Deferred functionality and limitations

- JavaScript/Nashorn expression evaluation remains deferred and is not part of SLiM protocol conformance.
- A FitNesse `FitnesseFixtureContext` nested-request bridge remains a substantial separate harness change.
- Java `Disgracer`, `MethodExtractor`, `SlimExceptionResult`, static Java reflection, and JVM `System.exit` interception will not be emulated in the Perl core.
- Startup tests require controlled ports and child-runner lifecycle; do not alter fixture behavior to fake expected errors.
- A Java `Properties` imitation is not justified solely by one acceptance page.
- A fixture adapter that loads successfully is not automatically evidence that all its table assertions or protocol behavior are correct; focused tests and exact acceptance results are required.

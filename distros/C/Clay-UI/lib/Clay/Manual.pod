=head1 ABOUT THIS MANUAL

This manual explains how to lay out user interfaces, images and
documents from Perl with the Clay layout engine. It introduces every

=head1 INTRODUCTION

=head2 What Clay does

Clay is a layout engine written in C (L<https://github.com/nicbarker/clay>,
version 0.14 is vendored in this distribution). You describe a tree of
rectangular I<elements> - boxes that contain other boxes and text - with
rules such as "grow to fill the space", "16 pixels of padding" or
"children from top to bottom". Clay computes where every element goes
and how big it is, and returns a flat list of I<render commands>:
"draw a rectangle here", "draw this text there", "start clipping".

Clay does B<not> draw anything, open windows, load fonts or read the
keyboard. Your program, the I<renderer>, turns the render commands into
pixels, PDF operators, SVG elements, terminal cells or whatever output
you need. Because of that, the same layout code can produce a PNG image,
a PDF page and a live window.

Clay is fast enough to recompute the whole layout every time something
changes ("immediate mode"). You do not update elements; you describe the
whole tree again and Clay works out the result.

=head2 The two layers

The distribution contains two Perl APIs on top of Clay:

=over 4

=item L<Clay::XS> - the low-level binding

Every Clay function under its exact C name (C<Clay_BeginLayout>,
C<Clay_GetElementData>, ...). You declare elements one by one, in order,
on every frame. Structs are Perl hashes with Clay's camelCase field
names (C<backgroundColor>, C<childGap>). Use it when you want full
control, want to port C examples, or prefer to describe the whole tree
in code on every frame.

=item L<Clay::UI> - the widget layer

A tree of long-lived Perl objects (I<widgets>) built from Object::Pad
roles. You build the tree once, change it when your data changes, and
call C<< $ui->render >> for every frame. Clay::UI also turns pointer
input into events (hover, press, release, scroll), manages keyboard
focus, and tells you when a frame needs to be redrawn. Attribute names
are snake_case (C<background_color>, C<child_gap>).

=back

Both layers produce the same render commands, so a renderer works with
either. Clay::UI is built on Clay::XS; you can mix the two, for example
call a Clay::XS function on the render commands Clay::UI returns.

Choosing a layer:

=for highlighter language=text

    You want to ...                                  Use
    -----------------------------------------------  ---------------------------
    render a document or image from data             either; Clay::UI is shorter
    build an interactive UI with events and focus    Clay::UI
    animate elements with transitions                either
    port a C Clay example                            Clay::XS
    reuse a tree between frames                      Clay::UI

=head1 GETTING STARTED

=head2 A first layout with Clay::UI

The script below lays out a 400x200 area with a header bar and two
coloured columns, and prints the render commands.

=for highlighter language=perl

    use v5.22;
    use warnings;
    use feature 'signatures';
    no warnings 'experimental::signatures';

    use Object::Pad 0.800;
    use Clay::XS qw(:all);
    use Clay::UI;
    use Clay::UI::Box;
    use Clay::UI::Text;

    # 1. Widget classes. Clay::UI ships roles, not classes: a class
    #    is one line that composes the role you want.
    class My::Box  :strict(params) :does(Clay::UI::Box)  {}
    class My::Text :strict(params) :does(Clay::UI::Text) {}

    # 2. The widget tree.
    my $root = My::Box->new(
    	id     => 'root',
    	layout => {
    		sizing           => { width => sizing_grow(), height => sizing_grow() },
    		layout_direction => CLAY_TOP_TO_BOTTOM,
    		padding          => padding_all(8),
    		child_gap        => 8,
    	},
    	background_color => [240, 240, 240, 255],
    );
    my $header = My::Box->new(
    	layout           => { sizing => { width => sizing_grow() }, padding => padding_all(8) },
    	background_color => [40, 60, 90, 255],
    );
    $header->add_child(My::Text->new(
    	text       => 'Hello, Clay',
    	font_size  => 20,
    	text_color => [255, 255, 255, 255],
    ));

    my $columns = My::Box->new(
    	layout => {
    		sizing    => { width => sizing_grow(), height => sizing_grow() },
    		child_gap => 8,
    	},
    );
    $columns->add_child(
    	My::Box->new(
    		layout => {
    			sizing => { width => sizing_fixed(120), height => sizing_grow() },
    		},
    		background_color => [200, 80, 60, 255],
    	),
    	My::Box->new(
    		layout => {
    			sizing => { width => sizing_grow(), height => sizing_grow() },
    		},
    		background_color => [60, 160, 90, 255],
    	),
    );
    $root->add_child($header, $columns);

    # 3. A Clay::UI owns the Clay context and lays the tree out.
    my $ui       = Clay::UI->new(width => 400, height => 200, root => $root);
    my $commands = $ui->render;

    # 4. Your renderer would draw these. Here we print them.
    for my $command (@$commands) {
    	my $box = $command->{boundingBox};
    	printf "%-10s %-14s x=%3d y=%3d w=%3d h=%3d\n",
    		ref $ui->widget_for($command->{userData}),
    		command_name($command->{commandType}),
    		@$box{qw(x y width height)};
    }

    sub command_name ($type) {
    	return $type == CLAY_RENDER_COMMAND_TYPE_RECTANGLE ? 'RECTANGLE'
    	     : $type == CLAY_RENDER_COMMAND_TYPE_TEXT      ? 'TEXT'
    	     :                                               "type $type";
    }

Output:

=for highlighter language=text

    My::Box    RECTANGLE      x=  0 y=  0 w=400 h=200
    My::Box    RECTANGLE      x=  8 y=  8 w=384 h= 36
    My::Text   TEXT           x= 16 y= 16 w=220 h= 20
    My::Box    RECTANGLE      x=  8 y= 52 w=120 h=140
    My::Box    RECTANGLE      x=136 y= 52 w=256 h=140

What happened:

=over 4

=item *

C<sizing_grow()> made the root fill the 400x200 viewport, and the green
column fill what the fixed-width red column left over.

=item *

The header has no height rule, so it uses the default, C<FIT>: it is as
tall as its content (the text) plus its padding.

=item *

The text is 220 units wide because Clay::UI's default text measurement
assumes every character is C<font_size> wide (11 characters x 20). A
real program installs a measure function that asks its font library;
see L</TEXT>.

=item *

C<widget_for> maps each render command back to the widget that
produced it. To ask where an element widget ended up, call
C<< $ui->bounding_box($widget) >>; text widgets have no bounding box of
their own, their position is the C<boundingBox> of their C<TEXT>
commands.

=back

=head2 The same layout with Clay::XS

With the low-level binding you create a context yourself and declare
every element, in order, between C<Clay_BeginLayout> and
C<Clay_EndLayout>. Each element is opened, configured once, given its
children, and closed:

=for highlighter language=perl

    use v5.22;
    use warnings;
    use feature 'signatures';
    no warnings 'experimental::signatures';

    use Clay::XS qw(:all);

    my $ctx = Clay_Initialize(
    	Clay_MinMemorySize(),
    	{ width => 400, height => 200 },
    	sub ($error, $userdata) { die "Clay error: $error->{errorText}\n" },
    );
    Clay_SetMeasureTextFunction(sub ($text, $config, $userdata) {
    	return { width => length($text) * $config->{fontSize}, height => $config->{fontSize} };
    });

    sub element ($id, $declaration, $children = sub {}) {
    	Clay__OpenElementWithId(Clay_GetElementId($id));
    	Clay__ConfigureOpenElement($declaration);
    	$children->();
    	Clay__CloseElement();
    }

    Clay_BeginLayout();
    element(root => {
    	layout => {
    		sizing          => { width => sizing_grow(), height => sizing_grow() },
    		layoutDirection => CLAY_TOP_TO_BOTTOM,
    		padding         => padding_all(8),
    		childGap        => 8,
    	},
    	backgroundColor => [240, 240, 240, 255],
    }, sub {
    	element(header => {
    		layout => {
    			sizing  => { width => sizing_grow() },
    			padding => padding_all(8),
    		},
    		backgroundColor => [40, 60, 90, 255],
    	}, sub {
    		Clay__OpenTextElement('Hello, Clay', {
    			fontSize  => 20,
    			textColor => [255, 255, 255, 255],
    		});
    	});
    	element(columns => {
    		layout => {
    			sizing   => { width => sizing_grow(), height => sizing_grow() },
    			childGap => 8,
    		},
    	}, sub {
    		element(red => {
    			layout => {
    				sizing => { width => sizing_fixed(120), height => sizing_grow() },
    			},
    			backgroundColor => [200, 80, 60, 255],
    		});
    		element(green => {
    			layout => {
    				sizing => { width => sizing_grow(), height => sizing_grow() },
    			},
    			backgroundColor => [60, 160, 90, 255],
    		});
    	});
    });
    my $commands = Clay_EndLayout();

    printf "%d render commands\n", scalar @$commands;    # 5

Note the differences: keys are camelCase (C<layoutDirection>,
C<childGap>, C<backgroundColor>), and an element that should keep its
identity between frames needs an id from C<Clay_GetElementId>. The
helper sub C<element> plays the role of Clay's C C<CLAY()> macro; see
L<Clay::XS/MAPPING C MACROS TO PERL>.

=head1 FRAMES

=head2 What a frame is

A I<frame> is one complete layout computation. With Clay::XS it is
everything from C<Clay_BeginLayout()> to C<Clay_EndLayout($delta_time)>,
which returns the render commands. With Clay::UI it is one call of
C<< $ui->render(%input) >>.

Clay keeps a little state from one frame to the next: the bounding box
of every element (used for pointer tests), scroll positions, hover
callbacks and running transitions. Everything else - the tree itself,
sizes, colours, text - is declared fresh in every frame. To change what
is shown, declare something different in the next frame (Clay::XS) or
change the widgets before the next C<render> (Clay::UI).

For a static image or document, one frame is all you need. An
interactive program runs one frame per input event or per display
refresh.

=head2 The order of a Clay::XS frame

    Clay_SetLayoutDimensions(\%size);          # only when the viewport changed
    Clay_SetPointerState(\%position, $down);   # pointer input, tested against the previous frame
    Clay_UpdateScrollContainers($drag, \%wheel, $delta_time);   # scrolling
    Clay_BeginLayout();
    # ... open, configure and close elements ...
    my $commands = Clay_EndLayout($delta_time);
    # ... draw $commands ...

Pointer and scroll functions work on the layout of the last I<completed>
frame, so they croak between C<Clay_BeginLayout> and C<Clay_EndLayout>.
See L<Clay::XS/ELEMENTS AND FRAMES> for every rule.

=head2 The order of a Clay::UI frame

C<< $ui->render(pointer_state => ..., scroll_delta => ..., delta_time => ...) >>
does all of this in one call:

=over 4

=item 1.

Hands the pointer position and the scroll wheel to Clay, which tests
them against the layout of the previous C<render>.

=item 2.

Fires widget events: C<OnHoverStopped>, C<OnHoverStart>, C<OnPress>,
C<OnRelease>, C<OnScroll>. Your listeners may change the widget tree
here.

=item 3.

Lets widgets that asked for it rebuild their children
(L<Clay::UI::Role::Core::Preparable>).

=item 4.

Declares the whole widget tree to Clay (the I<layout pass>) and returns
the render commands.

=back

Changes made in steps 2 and 3 show up in the commands of the same
C<render>. Details are in L<Clay::UI/render>.

=head1 COORDINATES AND UNITS

Clay works in abstract I<layout units>. They become whatever your
renderer says: pixels for a PNG, points (1/72 inch) for a PDF, CSS
pixels for SVG. Clay never converts units; the measure function and the
renderer only have to agree.

The origin (0, 0) is the top left corner of the layout area. X grows to
the right, Y grows downwards. A bounding box is a hash
C<< { x, y, width, height } >> with C<x> and C<y> at its top left
corner. All four values are floating point numbers; they are often, but
not always, whole numbers. Renderers that draw into a Y-up coordinate
system (PDF) must flip the Y axis:
C<< $pdf_y = $page_height - $box->{y} - $box->{height} >>.

The size of the layout area (the I<viewport>) is passed to
C<Clay_Initialize> or C<< Clay::UI->new(width => ..., height => ...) >>
and can be changed later with C<Clay_SetLayoutDimensions> or
C<< $ui->width($w) >> / C<< $ui->height($h) >>. Elements may extend
beyond it; Clay only omits render commands for elements that lie
completely outside it (see L</Culling>).

Colours are four numbers C<[r, g, b, a]>. Clay does not interpret them;
by convention each channel is 0 to 255, and every example in this
distribution uses that convention.

=head1 THE LAYOUT MODEL

This section explains how Clay decides where elements go. The keys
named here belong to the C<layout> part of an element declaration. The
full list, with types, ranges and defaults, is in
L<Clay::XS::Structs/layout>. In Clay::UI, you pass them in the
C<layout> attribute (L<Clay::UI::Role::Layout::HasLayout>), spelled
in snake_case.

=for highlighter language=text

    Clay::XS (camelCase)   Clay::UI (snake_case)
    ---------------------  ---------------------
    sizing                 sizing
    padding                padding
    childGap               child_gap
    childAlignment         child_alignment
    layoutDirection        layout_direction
    lineGap                line_gap
    lineSizing             line_sizing

=head2 Elements and children

Every element is a rectangle. Its children are placed inside it, after
each other along one axis, the I<layout axis> (often called the main
axis elsewhere). C<layoutDirection> picks
that axis:

=over 4

=item C<CLAY_LEFT_TO_RIGHT> (the default)

Children form a row, left to right.

=item C<CLAY_TOP_TO_BOTTOM>

Children form a column, top to bottom.

=item C<CLAY_LEFT_TO_RIGHT_WRAP>

Children form rows that wrap onto a new line when the next child does
not fit. See L</Flow layout>.

=item C<CLAY_BACK_TO_FRONT>

Children are stacked on top of each other. See L</Stack layout>.

=back

The other axis is the I<off axis> (the cross axis). A text element is a leaf: it has no
children and its size comes from the measure function (see L</TEXT>).

=head2 Sizing: FIT, GROW, FIXED and PERCENT

Each axis of an element has a I<sizing rule>, given as
C<< sizing => { width => ..., height => ... } >>. Build the rules with
these helper functions from Clay::XS (the defaults of C<$min> and
C<$max> are 0, and a C<$max> of 0 means "no maximum"):

=over 4

=item C<sizing_fit($min, $max)> - FIT (the default)

The element is as large as its content: its children, the gaps between
them and its padding. It is never smaller than C<$min> or larger than
C<$max>.

=item C<sizing_grow($min, $max)> - GROW

The element first takes the size of its content, like FIT, then takes
its share of the free space left in its parent along the parent's layout
axis. On the off axis it fills the parent's inner size. Several GROW
siblings share the free space: Clay grows the smallest ones first, so
GROW siblings with small content end up the same size.

=item C<sizing_fixed($size)> - FIXED

Exactly C<$size>, whatever the content. C<sizing_fixed(0)> is the
exception: a maximum of 0 means "no maximum", so it behaves like FIT.
Use a tiny size such as 1 for an element that must take no space.

=item C<sizing_percent($fraction)> - PERCENT

A fraction (0 to 1) of the parent's inner size: the parent's size minus
its padding and, on the layout axis, minus all its child gaps. C<0.5> is
50%. A value above 1 is reported to the error handler as
C<CLAY_ERROR_TYPE_PERCENTAGE_OVER_1>.

=back

Example: a 300 wide row with 10 units of padding and C<childGap> 10 and
four children (GROW, FIXED 50, PERCENT 0.5, GROW with a maximum of 30)
gives:

    inner width            300 - 2*10 padding = 280
    space for children     280 - 3*10 gaps    = 250
    PERCENT 0.5            0.5 * 250          = 125
    FIXED                                     =  50
    GROW (max 30)                             =  30
    GROW                   250 - 125 - 50 - 30 = 45

=for text Figure: images/sizing.png in the distribution.

=begin html

<p><img src="https://raw.githubusercontent.com/davenonymous/perl-clay-xs/v0.06/images/sizing.png" alt="A 300 wide row with padding 10 and childGap 10 holding four coloured children. The labels under them give each sizing rule and the width Clay computed: GROW 45, FIXED 50 is 50, PERCENT 0.5 is 125, GROW with max 30 is 30."></p>

=end html

When the content of a parent is larger than the parent (for example a
FIXED parent with too many children), Clay I<compresses> the children
along the layout axis: it shrinks the largest FIT and GROW children
first, never below their C<$min> and never below their minimum content
size (the longest word wide, one line of text tall). If they still
do not fit, the content overflows the parent. Clip the parent (see
L</Clipping and scrolling>) if overflow must not be visible.

=head2 Padding and childGap

C<padding> is empty space between an element's edge and its children:
C<< { left, right, top, bottom } >>, each an integer 0 to 65535.
C<padding_all($n)> builds one with the same value on all four sides.

C<childGap> (Clay::UI: C<child_gap>) is the space between neighbouring
children along the layout axis. There is no gap before the first or after
the last child.

=for highlighter language=perl

    layout => { padding => { left => 16, right => 16, top => 8, bottom => 8 }, childGap => 4 }

Padding and gaps count as content: a FIT element includes them in its
size.

=head2 childAlignment

C<< childAlignment => { x => ..., y => ... } >> (Clay::UI:
C<child_alignment>) positions the children inside the element when they
do not fill it:

=for highlighter language=text

    x: CLAY_ALIGN_X_LEFT (default), CLAY_ALIGN_X_CENTER, CLAY_ALIGN_X_RIGHT
    y: CLAY_ALIGN_Y_TOP  (default), CLAY_ALIGN_Y_CENTER, CLAY_ALIGN_Y_BOTTOM

Along the layout axis the children move as one block; along the off
axis each child is aligned on its own. To right-align the content of a
table cell, give the cell C<< child_alignment => { x => CLAY_ALIGN_X_RIGHT } >>.

=head2 Flow layout

C<CLAY_LEFT_TO_RIGHT_WRAP> lays children out left to right and starts a
new line whenever the next child does not fit into the remaining width,
like words in a paragraph. It is meant for tag lists, toolbars and
galleries. Two extra layout keys control the lines:

=over 4

=item C<lineGap> (Clay::UI: C<line_gap>)

Vertical space between lines. C<childGap> is still the space between
neighbours on a line.

=item C<lineSizing> (Clay::UI: C<line_sizing>)

What happens when the container is taller than its lines:
C<CLAY_LINE_SIZING_GROW> (the default) adds an equal share of the extra
height to every line; C<CLAY_LINE_SIZING_FIT> keeps every line as tall
as its tallest child.

=back

A wrap container whose width is FIT prefers a single line. Give it a
GROW, FIXED or PERCENT width to make it wrap inside its parent.
Wrapping is horizontal only. The full rules (alignment per line,
borders between children) are in L<Clay::XS/FLOW LAYOUT>; see
F<examples/07-ui-flow.pl>.

=head2 Stack layout

C<CLAY_BACK_TO_FRONT> places all children on top of each other inside
the padding. Later children are drawn over earlier ones; C<childGap> is
ignored. A FIT stack is as large as its largest child. C<childAlignment>
positions each child on both axes, so a stack is the tool for "badge in
the top right corner of an avatar" or "caption at the bottom of a
picture". See L<Clay::XS/STACK LAYOUT> and F<examples/08-ui-stack.pl>.

=head2 Floating elements

A I<floating> element is taken out of the normal layout: it does not
take space in its parent, and its siblings do not move for it. It is
positioned relative to another element (or the layout root) and drawn
above the normal content. Tooltips, dropdown menus, modal dialogs and
badges are floating elements.

=for text Figure: images/floating.png in the distribution.

=begin html

<p><img src="https://raw.githubusercontent.com/davenonymous/perl-clay-xs/v0.06/images/floating.png" alt="A row of three buttons Edit, View and Help. The View button has a dark tooltip above it, a white menu with the entries Zoom in and Zoom out hanging below it and a red badge on its top right corner; Edit and Help stay where they are. The legend gives the attach points: tooltip, element CENTER_BOTTOM at parent CENTER_TOP with offset y -6; menu, element LEFT_TOP at parent LEFT_BOTTOM with offset y 4; badge, element CENTER_CENTER at parent RIGHT_TOP."></p>

=end html

=for highlighter language=perl

    floating => {
    	attachTo     => CLAY_ATTACH_TO_PARENT,
    	attachPoints => {
    		element => CLAY_ATTACH_POINT_LEFT_TOP,
    		parent  => CLAY_ATTACH_POINT_LEFT_BOTTOM,
    	},
    	offset       => { x => 0, y => 4 },
    	zIndex       => 10,
    }

This places the element's top left corner 4 units below its parent's
bottom left corner - a dropdown. The keys:

=over 4

=item C<attachTo>

What to attach to: C<CLAY_ATTACH_TO_PARENT> (the element it is declared
in), C<CLAY_ATTACH_TO_ELEMENT_WITH_ID> (any element, named by
C<parentId>), C<CLAY_ATTACH_TO_ROOT> (the layout area) or
C<CLAY_ATTACH_TO_NONE> (the default: the element is B<not> floating).

=item C<attachPoints>

Which point of the floating element (C<element>) meets which point of
the target (C<parent>). Each is one of the nine
C<CLAY_ATTACH_POINT_*> constants (C<LEFT_TOP> ... C<RIGHT_BOTTOM>).

=item C<offset>, C<expand>

Move the element after attaching (C<< { x, y } >>), and enlarge it
(C<< { width, height } >>).

=item C<zIndex>

Drawing order between floating elements; higher is on top. Render
commands carry it as C<zIndex>.

=item C<pointerCaptureMode>, C<clipTo>, C<parentId>

Whether the pointer passes through to elements below, whether a
clipping ancestor also clips the floating element, and the target for
C<CLAY_ATTACH_TO_ELEMENT_WITH_ID>.

=back

Every key is described in L<Clay::XS::Structs/floating>. In Clay::UI,
give the widget the L<Clay::UI::Role::Layout::HasFloating> role (a
L<Clay::UI::Box> has it) and pass C<floating> with snake_case keys
(C<attach_to>, C<attach_points>, C<z_index>, ...). A tooltip is usually
added as a child of the widget it describes when the pointer enters it,
and removed when the pointer leaves; see L<Clay::Cookbook/Show a
tooltip on hover>.

=head2 Clipping and scrolling

C<< clip => { horizontal => $bool, vertical => $bool } >> makes an
element a I<clip container>: nothing of its children is drawn outside
its bounding box on the clipped axes. Clay wraps the children's render
commands in a C<SCISSOR_START> / C<SCISSOR_END> pair that your renderer
turns into a clip region.

=for text Figure: images/clipping-and-scrolling.png in the distribution.

=begin html

<p><img src="https://raw.githubusercontent.com/davenonymous/perl-clay-xs/v0.06/images/clipping-and-scrolling.png" alt="Two lists of eight coloured rows in parents of the same size. Without clipping, rows 5 to 8 are drawn below the parent's bottom edge. With vertical clipping and a scroll position of y -44, only rows 2 to 6 are visible, the first and the last of them cut off at the parent's edges."></p>

=end html

C<childOffset> shifts all children by C<< { x, y } >>; that is how
scrolling works. Clay can track the offset for you:

=over 4

=item *

Give the element an id and C<< clip => { vertical => 1, childOffset => Clay_GetScrollOffset() } >>.
C<Clay_GetScrollOffset> returns the stored offset of the element that is
currently open.

=item *

Before each frame, call C<Clay_SetPointerState> and
C<Clay_UpdateScrollContainers($drag_enabled, \%wheel_delta, $delta_time)>.
The container under the pointer scrolls by ten times the wheel delta
(a delta of C<< { y => -4 } >> moves the content 40 units up); Clay
keeps the position within the content. Wheel input moves the content at
once; with drag scrolling enabled, a drag that is released keeps
gliding for a few frames (momentum).

=item *

C<Clay_GetScrollContainerData($id)> reports position, visible size and
content size; C<set_scroll_position($id, \%position)> scrolls from code.

=back

In Clay::UI all of that is automatic for widgets with the
L<Clay::UI::Role::Layout::HasScroll> role: pass C<scroll_delta> (and
optionally C<enable_drag_scrolling>) to C<render>, read
C<< $ui->scroll_state($widget) >>, move with
C<< $ui->scroll_to($widget, { y => ... }) >>, and listen for
C<OnScroll>. Scroll positions are 0 at the top left and become
B<negative> as the content moves up (scrolling down).

C<< aspectRatio => $width_divided_by_height >> keeps an element's

content) or a FIXED height; an empty FIT element without a FIXED height

=head1 STYLING

Clay knows a few visual properties. It passes them on to the renderer in
the render commands; it never draws them itself. All of them are
described in L<Clay::XS::Structs>.

=over 4

=item C<backgroundColor> (Clay::UI: C<background_color>)

Fills the element's box. Produces a C<RECTANGLE> render command. An
element without a background colour (or with alpha 0) produces no
rectangle. The same holds for C<overlayColor>: alpha 0 produces no
overlay commands.

=item C<cornerRadius> (Clay::UI: C<corner_radius>)

Rounds the corners of the background and the border: a number for all
corners, or C<< { topLeft, topRight, bottomLeft, bottomRight } >>.
C<corner_radius_all($r)> builds the hash.

=item C<border> (Clay::UI: C<border_color>, C<border_width>)

A line along the inside of the element's edges:
C<< { color => [...], width => { left, right, top, bottom, betweenChildren } } >>.
Borders are drawn B<inside> the box, over the content; they do not take
space, so add padding if content must not be covered. A C<BORDER>
command is emitted whenever a width is above 0, even when the colour's
alpha is 0; to hide a border, set its width to 0.
C<betweenChildren> draws separator lines between children; Clay emits
those as ordinary C<RECTANGLE> commands, so your renderer needs nothing
extra for them. C<border_outside($w)> builds a width hash for the four
edges; C<border_all($w)> also sets C<betweenChildren>.

=item C<overlayColor>

Tints an element I<and its children> with a colour (for example a
semi-transparent white for a "hovered" highlight). Clay brackets the
affected commands with C<OVERLAY_COLOR_START> / C<OVERLAY_COLOR_END>.

=item C<image>

C<< image => { imageData => $key } >> marks the element as an image.
Clay emits an C<IMAGE> render command instead of a C<RECTANGLE>.
C<$key> is an unsigned integer that Clay hands back unchanged; use it to
look the picture up in your own table; it must not be 0 (Clay emits no
command for C<< imageData => 0 >>). Combine with C<aspectRatio>. Do not
give an image element a C<backgroundColor>: Clay then emits a
C<RECTANGLE> I<after> the C<IMAGE> command, which covers the picture
(put the background on a parent instead; the same holds for C<custom>).

=item C<custom>

C<< custom => { customData => $key } >> produces a C<CUSTOM> render
command: anything your renderer knows how to draw (a chart, a QR code,
a logo). Like C<imageData>, C<$key> is your own integer.

=back

Clay::UI covers C<backgroundColor>, C<cornerRadius>, C<border> and
C<floating> through roles. For C<image>, C<custom>, C<aspectRatio> and
C<overlayColor> a widget class adds a method of its own; see
L</Writing your own widget class>.

=head1 TEXT

=head2 Text elements

A text element shows one string. With Clay::XS:

    Clay__OpenTextElement('Total: 42 EUR', { fontSize => 14, textColor => [0, 0, 0, 255] });

With Clay::UI, compose L<Clay::UI::Text> into a class and add it as a
child:

    $box->add_child(My::Text->new(text => 'Total: 42 EUR', font_size => 14));

The text configuration keys (L<Clay::XS::Structs/Clay_TextElementConfig>):

=for highlighter language=text

    Clay::XS        Clay::UI          Meaning
    --------------  ----------------  ------------------------------------------------
    fontId          font_id           your number for a font; Clay passes it on
    fontSize        font_size         font size in layout units
    textColor       text_color        [r, g, b, a]
    letterSpacing   letter_spacing    extra space between characters
    lineHeight      line_height       height of one line; 0 = measured height
    wrapMode        wrap_mode         CLAY_TEXT_WRAP_WORDS (default), _NEWLINES, _NONE
    textAlignment   text_alignment    CLAY_TEXT_ALIGN_LEFT (default), _CENTER, _RIGHT

C<fontId>, C<fontSize>, C<letterSpacing> and C<lineHeight> are integers
from 0 to 65535 (Clay stores them as 16-bit numbers); a fractional size
such as 8.5 is rejected. If you need fractional sizes, scale your
layout units, for example lay out a PDF in tenths of a point and divide
by 10 in the renderer. Border widths are integers too.

Text is Perl character strings, any Unicode. Clay breaks lines only at
ASCII spaces and newlines.

=head2 Measuring text

Clay cannot know how wide a piece of text is in your font, so it asks a
I<measure function> you provide. The function receives the text and its
configuration and returns the size:

=for highlighter language=perl

    Clay_SetMeasureTextFunction(sub ($text, $config, $userdata) {
    	my $font = $fonts{ $config->{fontId} };
    	return {
    		width  => $font->width($text) * $config->{fontSize},
    		height => $config->{fontSize},
    	};
    });

In Clay::UI, pass it to the constructor:
C<< Clay::UI->new(measure_text => sub ($text, $config, $userdata) { ... }, ...) >>.
The C<$config> hash has camelCase keys (C<fontSize>, C<fontId>, ...) in
both layers.

Clay calls the function for single words and caches the results, so it
must return the same size for the same input. A Clay::XS context
without a measure function makes C<Clay_EndLayout> croak
(C<Clay::XS: text measured but no measure_text function is installed for this context>)
as soon as it lays out text. Clay::UI has a default that estimates every character as
C<fontSize> wide and one line as C<fontSize> tall; it is good enough for
tests, not for real output.

Measure functions for common Perl libraries:

    # Imager (raster images)
    my $bbox = $imager_font->bounding_box(string => $text, size => $size);
    return { width => $bbox->advance_width, height => $size };

    # PDF::Builder / PDF::API2 (PDF)
    return { width => $pdf_font->width($text) * $size, height => $size };

See F<examples/15-og-card.pl> and F<examples/16-invoice-pdf.pl> for
complete versions. The measure function runs inside Clay; it must not
call Clay functions that change state (see
L<Clay::XS/What a callback may do>). If it dies, the frame's
C<Clay_EndLayout> (or C<render>) dies with that error.

=head2 Wrapping and line breaks

With C<CLAY_TEXT_WRAP_WORDS> (the default), a text element that does not
fit into its parent's width breaks at spaces and at newline characters.
With C<CLAY_TEXT_WRAP_NEWLINES>, it breaks only at newlines. With
C<CLAY_TEXT_WRAP_NONE>, it never breaks: the whole text, newlines
included, is one line.

Each line becomes its own C<TEXT> render command with its own bounding
box, so a renderer simply draws every C<TEXT> command at its position.
A parent with a FIT width takes the width of the longest line it does
not have to break; give the parent a FIXED, GROW or PERCENT width (or a
C<$max> on FIT) to make text wrap.

=for text Figure: images/text-wrapping.png in the distribution.

<p><img src="https://raw.githubusercontent.com/davenonymous/perl-clay-xs/v0.06/images/text-wrapping.png" alt="The same text, which contains one newline, in three grey parents 200 wide. With CLAY_TEXT_WRAP_WORDS it breaks at a space and at the newline into three lines inside the parent. With CLAY_TEXT_WRAP_NEWLINES it breaks only at the newline and the first line runs past the parent's right edge. With CLAY_TEXT_WRAP_NONE it is one line that runs far past the parent."></p>

=head2 Fonts

C<fontId> is a number with no meaning to Clay. Pick one per font face
or weight (0 = regular, 1 = bold, ...), use it to choose the font in
the measure function, and use the same mapping in the renderer, which
finds C<fontId> and C<fontSize> in each C<TEXT> command's C<renderData>.

=head1 RENDER COMMANDS AND RENDERERS

=head2 The render command list

C<Clay_EndLayout> and C<< $ui->render >> return an array reference of
hashes. Each hash describes one drawing step:

    {
    	commandType => CLAY_RENDER_COMMAND_TYPE_RECTANGLE,
    	boundingBox => { x => 8, y => 8, width => 384, height => 36 },
    	renderData  => {
    		backgroundColor => { r => 40, g => 60, b => 90, a => 255 },
    		cornerRadius    => { ... },
    	},
    	id          => 2307226574,    # the element id number
    	zIndex      => 0,
    	userData    => 0,             # set by you (Clay::XS) or by Clay::UI
    }

The complete description of every command type and its C<renderData> is
in L<Clay::XS/RENDER COMMANDS>.

=head2 Writing a renderer

A renderer is a loop over the commands, B<in array order>, with one
branch per C<commandType>:

    for my $command (@$commands) {
    	my ($type, $box, $data) = @$command{qw(commandType boundingBox renderData)};
    	if ($type == CLAY_RENDER_COMMAND_TYPE_RECTANGLE) {
    		fill_rounded_rect($box, $data->{backgroundColor}, $data->{cornerRadius});
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_BORDER) {
    		stroke_border($box, $data->{color}, $data->{width}, $data->{cornerRadius});
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_TEXT) {
    		draw_text($box, $data);
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_IMAGE) {
    		draw_image($box, $images{ $data->{imageData} });
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_CUSTOM) {
    		$painters{ $data->{customData} }->($box);
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_SCISSOR_START) {
    		push_clip($box);
    	}
    	elsif ($type == CLAY_RENDER_COMMAND_TYPE_SCISSOR_END) {
    		pop_clip();
    	}
    }

Rules that keep a renderer correct:

=over 4

=item *

Draw in array order. Clay has already sorted the commands: parents
before children, and floating elements after the normal content in
increasing C<zIndex>. You do not need to sort by C<zIndex> yourself.

=item *

Clip regions nest. Keep a stack: C<SCISSOR_START> pushes its bounding
box (intersected with the current clip), C<SCISSOR_END> pops. The
C<SCISSOR_END> command's bounding box is not meaningful.

=item *

A C<BORDER> command comes after the element's children and is drawn
inside the element's bounding box: a left border of width 2 covers the
two leftmost columns of the box.

=item *

C<OVERLAY_COLOR_START> / C<OVERLAY_COLOR_END> bracket the commands that
should be tinted. A renderer that does not support tinting may ignore
them.

=item *

Ignore types you do not understand, and C<CLAY_RENDER_COMMAND_TYPE_NONE>.

=back

The distribution contains complete renderers you can copy: SVG
(F<examples/03-svg-render.pl>, F<examples/11-xs-images-custom.pl>),
PNG with Imager (F<examples/06-png-render.pl>,
F<examples/15-og-card.pl>) and PDF with PDF::Builder
(F<examples/16-invoice-pdf.pl>).

=head2 Finding the element behind a command

Every command carries the numeric C<id> of the element that produced
it, and C<userData>, an unsigned integer copied from the element's
declaration. Clay::UI fills C<userData> for you: C<< $ui->widget_for($command->{userData}) >>
returns the widget, so a renderer can ask the widget for anything it
needs (for example which picture to draw, or a style that Clay does not
know about). With Clay::XS, set C<userData> to a key into a table of
your own.

=head2 Culling

Clay leaves out the render commands of elements that are completely
outside the viewport. This is called I<culling> and is on by default.
Turn it off with C<Clay_SetCullingEnabled(0)> when you lay out a page
larger than the viewport on purpose. Culling compares with the
viewport, not with clip containers: children of a clip container that
lie inside the viewport are still emitted, and the scissor region hides
them. A clip container emits its scissor commands even when it is
culled itself, so such children stay clipped.

=head1 ELEMENT IDS

An I<element id> identifies an element across frames. Clay needs one to
remember an element's bounding box, scroll position, hover callback or
transition. With Clay::XS:

    my $id = Clay_GetElementId('sidebar');               # from a string
    my $id = Clay_GetElementIdWithIndex('row', $i);      # 'row' + index, for lists
    Clay__OpenElementWithId($id);

An id is a hash C<< { id, offset, baseId, stringId } >>; C<id> is the
number Clay uses (it appears in render commands). The same string always
gives the same id. Two elements with the same id in one frame are an
error (C<CLAY_ERROR_TYPE_DUPLICATE_ID>). Elements opened with
C<Clay__OpenElement> (no id) get an automatic id that can change between
frames.

Ids are also how you ask Clay about an element:

    my $data = Clay_GetElementData(Clay_GetElementId('sidebar'));
    say "sidebar is $data->{boundingBox}{width} wide" if $data->{found};

In Clay::UI, the C<id> attribute is optional. A widget without one gets
an id derived from its position in the tree, which stays the same as
long as no widget is inserted or removed before it or before one of its
id-less ancestors. Give an id to every widget whose
identity matters across tree changes; scroll containers require one.
User ids must not start with C<anon:>. Duplicate ids make C<render> die.

=head1 POINTER INPUT

=head2 How Clay tests the pointer

Clay checks the pointer against the bounding boxes of the B<previous>
completed frame: the layout the user is looking at when they click. A
consequence: an element can only be hovered from the frame after it was
first laid out. Tests and scripts that simulate clicks therefore render
one frame before they send pointer input.

=head2 With Clay::XS

    Clay_SetPointerState({ x => $mouse_x, y => $mouse_y }, $button_down);

    if (Clay_PointerOver(Clay_GetElementId('save'))) { ... }   # one element
    my $ids = Clay_GetPointerOverIds();                       # all elements under the pointer

While declaring an element you can also ask C<Clay_Hovered()> (is the
pointer over the element that is open now) or register a callback with
C<Clay_OnHover(sub ($id, $pointer, $userdata) { ... })>. The pointer
hash passed to the callback has a C<state>: one of
C<CLAY_POINTER_DATA_PRESSED_THIS_FRAME>, C<CLAY_POINTER_DATA_PRESSED>,
C<CLAY_POINTER_DATA_RELEASED_THIS_FRAME> and
C<CLAY_POINTER_DATA_RELEASED>. Hover callbacks must be registered again
in every frame.

=head2 With Clay::UI: events

Pass the pointer to C<render> and listen on widgets:

    $button->on(OnPress => sub ($event) {
    	say "pressed at ", $event->x, ",", $event->y;
    	return Clay::UI::Enum::Result->HANDLED;
    });

    my $commands = $ui->render(pointer_state => { x => $x, y => $y, down => $down });

Which widgets receive which events depends on their roles:

=for highlighter language=text

    Role                                       Events
    -----------------------------------------  ------------------------------
    Clay::UI::Role::Interaction::Hoverable     OnHoverStart, OnHoverStopped
    Clay::UI::Role::Interaction::Pressable     OnPress, OnRelease (and hover)
    Clay::UI::Role::Interaction::Focusable     OnFocus, OnBlur
    Clay::UI::Role::Layout::HasScroll          OnScroll

=over 4

=item *

B<OnHoverStart> / B<OnHoverStopped>: the pointer entered / left the
widget. Every hovered widget gets its own event; hover events do not
travel to ancestors.

=item *

B<OnPress>: the pointer went down. Exactly one widget gets it: the
Pressable under the pointer that is drawn on top (a button inside a
pressable card, not the card).

=item *

B<OnRelease>: the pointer went up over a Pressable that the press
started on - a completed click. There is no separate "click" event.

=item *

B<OnScroll>: a scroll container moved; the event carries C<delta_x>
and C<delta_y>.

=back

=head2 Bubbling

OnPress, OnRelease, OnScroll, OnFocus and OnBlur I<bubble>: after the
listeners of the target widget have run, the event may travel to the
widget's parent, then the grandparent, and so on. By default it travels
on only when B<every> listener of the current widget returned
C<< Clay::UI::Enum::Result->CONTINUE >>. Returning anything else,
including nothing (C<undef>), stops it. So a listener that handles an
event simply returns; a listener that only observes returns C<CONTINUE>.

=for highlighter language=perl

    $card->on(OnPress => sub ($event) {
    	say "something inside the card was pressed: ", $event->target->id;
    	return Clay::UI::Enum::Result->CONTINUE;
    });

The rules, and how to fire events of your own, are in
L<Clay::UI::Role::Events::Emitter> and L<Clay::UI::Events::Event>.

=head2 Interaction states

Widgets do not store hover or press flags. Ask the UI instead:
C<< $widget->is_hovered >>, C<< $widget->is_pressed >>,
C<< $widget->is_focused >>, or C<< $ui->interaction >> (a
L<Clay::UI::Interaction>). Widgets with
L<Clay::UI::Role::Style::HasStates> also answer
C<< $widget->has_state('hovered') >> for the I<derived states>
C<hovered>, C<pressed>, C<focused> and C<disabled>, next to states you
set yourself (C<< $widget->add_state('selected') >>). A widget class can
use them to pick its colours; see L<Clay::Cookbook/Style a widget by its
hover and pressed state>.

=head1 FOCUS AND KEYBOARD

Clay has no keyboard support, and neither does Clay::UI: your program
reads keys from its window toolkit or terminal. Clay::UI manages
I<focus> - which widget keys should go to - so your key handler can
route keys:

    my $interaction = $ui->interaction;
    if    ($key eq 'Tab')       { $interaction->focus_next }
    elsif ($key eq 'Shift-Tab') { $interaction->focus_previous }
    elsif (my $focused = $interaction->get_focused_widget) {
    	$focused->handle_key($key) if $focused->can('handle_key');    # your own method
    }

Only widgets with the L<Clay::UI::Role::Interaction::Focusable> role can
take the focus. The default Tab order is the order of the widget tree
(depth first); a container with
L<Clay::UI::Role::Interaction::HasFocusOrder> can define its own order.
A widget with L<Clay::UI::Role::Interaction::Disableable> that is
disabled cannot take the focus and cannot be pressed (a press over it
goes to the nearest enabled Pressable under the pointer instead). Focus changes fire
C<OnBlur> on the old and C<OnFocus> on the new widget. Clicking does not
move the focus by itself; call C<set_focused_widget> from an C<OnPress>
listener if you want that. See L<Clay::UI::Interaction/FOCUS>.

The tracker also answers questions about a part of the tree, a I<focus
scope>: C<< $interaction->has_focus_within($panel) >> tells whether the
focused widget is C<$panel> or below it, and
C<< $interaction->focusables(within => $panel) >> lists the widgets below
it that can take the focus now. A modal dialog keeps Tab inside itself
by stepping within its own subtree:

    class My::Dialog :strict(params)
    	:does(Clay::UI::Box)
    	:does(Clay::UI::Role::Interaction::HasFocusOrder)
    {
    	method get_next_focus ()     { return $self->default_next_focus(within => $self) }
    	method get_previous_focus () { return $self->default_previous_focus(within => $self) }
    }

A widget class whose C<accepts_focus> answer depends on its own state
calls C<focus_eligibility_changed> when that state changes (see
L<Clay::UI::Role::Interaction::Focusable/focus_eligibility_changed>).

=head1 WIDGETS

=head2 Widget classes are built from roles

Apart from L<Clay::UI::Grid::Cell>, Clay::UI ships no ready-made widget
classes. It ships I<roles> (L<Object::Pad> roles, similar to mixins)
that each add one ability, and three ready-made combinations of
roles. A widget class is an
Object::Pad class that composes the roles it needs:

    use Object::Pad 0.800;
    use Clay::UI::Box;
    use Clay::UI::Role::Interaction::Pressable;
    use Clay::UI::Role::Interaction::Focusable;

    class My::Button :strict(params)
    	:does(Clay::UI::Box)
    	:does(Clay::UI::Role::Interaction::Pressable)
    	:does(Clay::UI::Role::Interaction::Focusable) {}

C<:strict(params)> makes a misspelled constructor argument die instead
of being ignored; use it on every widget class.

Note: Object::Pad's C<class> block starts a new package, so functions
imported with C<use Clay::XS qw(...)> at the top of the file are not
visible inside it. Call them fully qualified
(C<Clay::XS::sizing_grow()>) or import them inside the class block.

=head2 Widget roles

The three ready-made combinations:

=over 4

=item L<Clay::UI::Box>

A styled container: children, C<layout>, C<background_color>,
C<border_color>, C<border_width>, C<corner_radius>, C<floating>, and
C<fire_event>. Most widgets start from it.

=item L<Clay::UI::Text>

A text leaf: C<text>, C<font_id>, C<font_size>, C<text_color>,
C<letter_spacing>, C<line_height>, C<wrap_mode>, C<text_alignment>.

=item L<Clay::UI::Grid>

A table that sizes columns and rows to their content.

=back

=head2 Building and changing the tree

Widgets are created empty and connected with the methods of
L<Clay::UI::Role::Core::Container>:

=for highlighter language=perl

    $panel->add_child($title, $body);         # returns $panel, so calls chain
    $panel->remove_child($body);              # the widget itself
    $panel->remove_child_with_id('body');     # by id
    $panel->remove_children_with(sub { ($_->id // '') =~ /^tmp-/ });   # text widgets: id undef
    $panel->clear_children;

A widget has at most one parent. Attaching a widget that still has a
parent dies; remove it first. Removed widgets can be attached again.
Every attribute is a read/write accessor (C<< $box->background_color([255, 0, 0, 255]) >>);
values are checked when they are set, so mistakes die at the line that
made them, not later in C<render>. Only problems Clay detects during
layout make C<render> die instead: a C<sizing_percent> above 1,
duplicate ids, sizing-group cycles and too many elements. Changes take effect at the next
C<render>.

=head2 Writing your own widget class

A widget's element declaration is assembled by its C<to_config> method
from methods named C<contribute_I<name>>: each role adds one (for
example HasBackground's adds C<background_color>), and C<to_config> calls
all of them. A class can add its own to put anything Clay supports into
the declaration - for example an image with a fixed aspect ratio:

    class My::Picture :strict(params) :does(Clay::UI::Box) {
    	field $image_key :param :reader;     # key into the renderer's image table
    	field $ratio     :param = 1;

    	method contribute_picture ($config) {
    		$config->{image}        = { image_data => $image_key };
    		$config->{aspect_ratio} = $ratio;
    		return;
    	}
    }

Write keys in snake_case, the spelling stored slices use; Clay::UI
converts them to Clay's camelCase. The methods run in alphabetical
order of their names, so two methods must not write the same key: the
result would depend on that order. In particular, a class that writes C<background_color> itself
must not also use the C<background_color> attribute. The one exception
is C<layout>: the built-in methods merge their keys into it, so your
method may add keys to C<< $config->{layout} >> as well. The name must not
clash with a C<contribute_> method of a composed role
(C<contribute_layout>, C<contribute_background>, C<contribute_border>,
C<contribute_corner_radius>, C<contribute_floating>, C<contribute_clip>,
C<contribute_sizing_group>, C<contribute_grid_defaults>); Object::Pad
dies on such a clash. A setter that changes what such a method returns must call
C<< $self->mark_changed >> so renderers that skip unchanged frames
notice. Do not set C<user_data>: Clay::UI uses it to map render commands
back to widgets. Full details: L<Clay::UI::Role::Core::Element/to_config>.

A widget whose children follow from its own data (a list, a table)
composes L<Clay::UI::Role::Core::Preparable>: its setters call
C<request_prepare>, and C<render> calls its C<prepare_layout> once
before the layout pass, however many changes came before.

A widget that must react when its place in a tree changes (it joined a
tree, left one, or its tree became a UI) overrides the hook
C<tree_changed> in a subclass. Clay::UI calls it on every widget of
the moved subtree once the move is complete, so C<parent> and C<ui>
already answer the new place. A class cannot override a method of a
role it composes itself, so the override goes into a subclass:

    class My::ListBase :strict(params)
    	:does(Clay::UI::Box)
    	:does(Clay::UI::Role::Core::Preparable)
    {
    	method prepare_layout () { return }    # builds the items
    }

    class My::List :strict(params) :isa(My::ListBase) {
    	method tree_changed :override () {
    		$self->SUPER::tree_changed;
    		$self->request_prepare;    # rebuild the items for the new place
    		return;
    	}
    }

See L<Clay::UI::Role::Layout::HasParent/tree_changed> for the details.

=head1 TRANSITIONS

Clay can animate changes of an element's position, size and colours
between frames. The steps below use Clay::XS; the Clay::UI variant
follows them.

=over 4

=item 1.

Give the element a stable id and a C<transition> declaration, which says
how long the animation takes and which properties it animates:

    transition => {
    	duration   => 0.3,
    	properties => CLAY_TRANSITION_PROPERTY_BACKGROUND_COLOR | CLAY_TRANSITION_PROPERTY_POSITION,
    }

=item 2.

Install one set of handlers for the context. The handler moves
C<< $args->{current} >> towards C<< $args->{target} >>;
C<Clay_EaseOut> does the arithmetic for you:

    Clay_SetTransitionHandlers(sub ($args, $userdata) {
    	my $eased = Clay_EaseOut($args);
    	$args->{current} = $eased->{current};
    	return $eased->{complete};
    });

=item 3.

Pass the time since the previous frame, in seconds, to
C<Clay_EndLayout($delta_time)>, and run frames until the animation is
done.

=back

Every frame that animates an element moves the revision (see
L</REDRAWING ONLY WHEN SOMETHING CHANGED>), so a renderer that redraws
only on a changed revision keeps drawing until the animation is over.

Without handlers nothing is animated: the C<transition> key does
nothing, and a changed value shows at once.

An element whose C<transition> has an C<exit> part stays on screen
after it is no longer declared, until its exit animation ends. Clay
keeps a copy of every such element, with its subtree, between frames;
the copies count against the element count, and a frame whose elements
and copies do not fit drops the exit animations (see
L<Clay::XS/FUNCTIONS: TRANSITIONS>).

With Clay::UI, add the C<transition> key from a C<contribute_> method
(see L</Writing your own widget class>), give the widget an C<id>, and
install the handlers right after C<< Clay::UI->new >>, while the new
UI's context is current; they stay with that context. Pass
C<delta_time> to every C<render>:

    class My::FadingBox :strict(params) :does(Clay::UI::Box) {
    	method contribute_transition ($config) {
    		$config->{transition} = {
    			duration   => 0.3,
    			properties => Clay::XS::CLAY_TRANSITION_PROPERTY_BACKGROUND_COLOR(),
    		};
    		return;
    	}
    }

    my $ui = Clay::UI->new(width => 400, height => 300, root => $root);
    Clay_SetTransitionHandlers(sub ($args, $userdata) {
    	my $eased = Clay_EaseOut($args);
    	$args->{current} = $eased->{current};
    	return $eased->{complete};
    });
    $ui->render(delta_time => 1 / 60) while $running;

Elements can also animate when they appear (C<enter>) and disappear
(C<exit>). See L<Clay::XS/CALLBACKS>, L<Clay::XS::Structs/transition>
and F<examples/10-xs-transitions.pl>.

=head1 REDRAWING ONLY WHEN SOMETHING CHANGED

An interactive program does not have to redraw when nothing changed.
Clay::UI keeps a process-wide counter, the I<revision>
(L<Clay::UI::Revision>), that grows whenever something that affects a
frame changes: a widget attribute, the children, a hover or press state,
a scroll position. Call C<render> for every input event (it is what
turns input into events), but draw only when the revision moved:

    my $drawn = -1;
    while (my $input = next_input()) {
    	my $commands = $ui->render(%$input);
    	next if $ui->laid_out_revision == $drawn;
    	$drawn = $ui->laid_out_revision;
    	draw($commands);
    }

C<laid_out_revision> is the revision the last C<render> laid out,
including changes made by event listeners during that C<render>.

A running transition (see L</TRANSITIONS>) moves the revision in every
frame that animates an element, so this loop redraws the animation too.

=head1 ERRORS AND VALIDATION

The distribution checks input where it enters, so a mistake dies at the
line that made it, with a message that names the problem.

=over 4

=item Wrong struct values

In Clay::XS, a wrong type or an out-of-range number dies with a
C<Clay::XS::StructError> object whose message names the path, for
example
C<Clay_ElementDeclaration.layout.padding.left: expected an integer in 0..65535, got '-8'>.
In Clay::UI, attribute setters and constructors die with a plain string
that names the attribute path, for example
C<Clay::UI: 'layout.padding.left' expected an integer in 0..65535, got '-5'>;
an unknown key also dies there, and the message lists the allowed keys.
C<check_struct> validates a hash without laying anything out. See
L<Clay::XS/STRUCT ERRORS>.

=item Misuse of the frame API

Closing more elements than were opened, configuring an element twice,
or sending pointer input in the middle of a frame croaks with a message
naming the function.

=item Errors Clay reports

Clay reports layout problems (duplicate ids, too many elements, a
percentage over 1) to the I<error handler> passed to C<Clay_Initialize>
or C<< Clay::UI->new(error_handler => ...) >>. Clay::UI's default
handler dies with C<Clay error: ...>.

=item Exceptions in your callbacks

An exception in a measure function, error handler, hover callback,
transition handler or event listener is not lost: it is held while Clay
finishes its work and then re-thrown by the function you called
(usually C<Clay_EndLayout> or C<render>). See
L<Clay::XS/ERRORS FROM CALLBACKS> and L<Clay::UI/render>.

=back

=head1 PERFORMANCE AND LIMITS

=over 4

=item Element count

A context holds a fixed number of elements, 8192 by default. Every
element and every text element counts. Raise it with
C<Clay_SetMaxElementCount> before C<Clay_Initialize>, while no context
is current (with a context current, the setter changes that context's
count and makes it unusable until it is initialised again), or with
C<< Clay::UI->new(max_element_count => $n) >>. C<Clay_MinMemorySize>
reports the memory needed for the current settings.

=item Text measurement cache

Clay caches measured words; C<Clay_SetMaxMeasureTextCacheWordCount>
sizes the cache (16384 words by default, twice the element count), or
C<< Clay::UI->new(max_measure_text_cache_word_count => $n) >>. Every
text laid out in a frame counts, visible or not, and the words of the
last few frames stay cached; past the capacity Clay reports
C<CLAY_ERROR_TYPE_TEXT_MEASUREMENT_CAPACITY_EXCEEDED> and lays the rest
out with no size. Clay also wraps at most as many text lines per frame
as the element count allows and silently stops wrapping past that.
After changing fonts, call
C<Clay_ResetMeasureTextCache> (Clay::UI does this when you set
C<measure_text>).

=item Debug view

C<Clay_SetDebugModeEnabled(1)> makes Clay add its own inspector panel
to the render commands. Your renderer draws it like any other content;
it needs a working measure function.

=item Threads

A context belongs to the Perl interpreter (thread) that created it.
Several contexts can be used from one thread, one at a time; see
L<Clay::XS/CONTEXTS>.

=back

=head1 GLOSSARY

=over 4

=item bounding box

The rectangle an element occupies after layout: C<< { x, y, width, height } >>.

=item context

One independent Clay instance (a C<Clay::XS::Context>), with its own
memory, viewport, callbacks and state. A Clay::UI owns one.

=item declaration

The hash passed to C<Clay__ConfigureOpenElement> that describes an
element's layout and style. Its keys are listed in L<Clay::XS::Structs>.

=item derived state

A widget state computed from interaction (C<hovered>, C<pressed>,
C<focused>, C<disabled>) rather than stored.

=item element

A rectangle in Clay's layout tree. A I<text element> is a leaf that
shows text.

=item frame

One layout computation: C<Clay_BeginLayout> to C<Clay_EndLayout>, or one
C<< $ui->render >>.

=item layout pass

The part of C<< $ui->render >> that declares the widget tree to Clay
and collects the render commands.

=item measure function

Your callback that tells Clay how large a piece of text is.

=item render command

One drawing instruction in the list a frame returns.

=item renderer

Your code that draws render commands.

=item revision

Clay::UI's counter of changes, used to skip drawing unchanged frames.

=item viewport

The layout area, given as width and height.

=item widget

A Clay::UI object in the widget tree. An I<element widget> becomes a
Clay element; a I<text widget> becomes a text element.

=back
